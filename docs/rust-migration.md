# Rust migration log

The log of the move from Go to Rust ([#634](https://github.com/shgew/togi/issues/634), [ADR 0048](adr/0048-rust.md)). The rules are in [`porting.md`](porting.md). Every stage appends an entry for what its pull requests measured and found: dates, lines removed and added, compile and test times next to Go's, comparison failures and what they caught, regressions, review findings, and agent cost where known. Stage 12 ([#647](https://github.com/shgew/togi/issues/647)) turns this file into a retrospective.

Append entries below the last one, newest last. State what was measured and how, and name what was not measured.

## Stage 0: the probe (2026-10-10)

**Question.** Is Rust worth porting togi for, and how much of the cost in a heavy simulated session is the language rather than the code's design?

**Setup.** Branch [`rust-probe`](https://github.com/shgew/togi/tree/rust-probe/prototype/rustprobe), commit 4b20b151, `prototype/rustprobe/`. It is throwaway and never merges. It ports the hottest allocating path of a simulated session: simulated trial conditions → `session.sampleEvidence` → `requests.Summarize`. The input is all 30,177 trials listed in `trials.tsv`, drawn from the `flat-hazard` session at seed 102 (217,192 journal events). Five variants produce byte-identical output; hyperfine ran each for 10 runs.

- `go-verbatim`: the Go code as on `main` at the time, a fresh map per sample.
- `go-tuned`: the same logic without per-sample allocation.
- `rust-verbatim-std`: a straight port of `go-verbatim` with std `HashMap`.
- `rust-verbatim-fx`: the same port with the Fx hasher.
- `rust-tuned`: mirrors `go-tuned` line for line.

**Code size.** The probe adds 609 lines in its Go implementation and 653 in its Rust implementation, containing both verbatim and tuned variants; it removes no production code. This is an experiment's size, not a production port's reduction.

**Session profile on `main`** (the profile that picked the path): background garbage collection took about 30% of user CPU, 2.24 s against 1.57 s with `GOGC=off`, and the process peaked at 405 MB.

**Results** (`single.md`; peak memory is the largest `memory_usage_byte` of the 10 runs):

| Variant | Mean wall [s] | Min [s] | Max [s] | Relative | Peak memory [MB] |
|:---|---:|---:|---:|---:|---:|
| `go-verbatim` | 4.209 ± 0.219 | 3.991 | 4.501 | 13.80 ± 0.77 | 14.8 |
| `rust-verbatim-std` | 2.495 ± 0.038 | 2.463 | 2.598 | 8.18 ± 0.21 | 5.7 |
| `rust-verbatim-fx` | 1.258 ± 0.100 | 1.184 | 1.411 | 4.12 ± 0.34 | 5.3 |
| `go-tuned` | 0.469 ± 0.014 | 0.457 | 0.503 | 1.54 ± 0.06 | 12.0 |
| `rust-tuned` | 0.305 ± 0.006 | 0.300 | 0.320 | 1.00 | 5.4 |

**Findings.**

- Design dominates. Removing the per-sample allocation took Go from 4.21 s to 0.47 s, 9×. [#629](https://github.com/shgew/togi/issues/629) applied that fix to the Go code (PR [#648](https://github.com/shgew/togi/pull/648)): on the same session, user CPU fell from 2.48 s to 1.87 s and total allocation from 2.49 GB to 1.25 GB, with every journal and `samples.jsonl` byte-identical.
- The language adds about 1.5× (`go-tuned` 0.469 s against `rust-tuned` 0.305 s) and about half the peak memory on this path.
- A straight Rust port is not fast by itself: with std `HashMap` it took 2.50 s, 8× the Rust-native version. The decision to port Rust-native rather than verbatim (ADR 0048) rests on this.
- Rust is not free of the same design flaw: swapping the hasher alone halved the verbatim port's time, which is why dense per-core arrays replace `map[int]…` in the port guide.

**Limits.** One path, one session and one build of each language. It measures wall time and peak memory of that kernel, not compile time, test time, the effect on agent-driven development, or a whole-session Rust comparison. Comparison failures, regressions, independent review findings and agent cost were not recorded for the probe. The pilot (stage 2, [#637](https://github.com/shgew/togi/issues/637)) records compile and test times against Go's.

**Decisions.** The owner decided on 2026-10-10 to migrate ([#634](https://github.com/shgew/togi/issues/634)), and that agents merge migration pull requests once CI and the `review` check pass and every thread is resolved, except the cutover and changes to the protected comparison assets. The same day, the Go structure-only issues the port replaces were closed ([#104](https://github.com/shgew/togi/issues/104), [#124](https://github.com/shgew/togi/issues/124), [#321](https://github.com/shgew/togi/issues/321), [#322](https://github.com/shgew/togi/issues/322), [#323](https://github.com/shgew/togi/issues/323), [#550](https://github.com/shgew/togi/issues/550), [#552](https://github.com/shgew/togi/issues/552), [#562](https://github.com/shgew/togi/issues/562), [#565](https://github.com/shgew/togi/issues/565) to [#568](https://github.com/shgew/togi/issues/568), [#573](https://github.com/shgew/togi/issues/573), [#575](https://github.com/shgew/togi/issues/575), [#577](https://github.com/shgew/togi/issues/577)) and [#541](https://github.com/shgew/togi/issues/541)'s type cut was superseded; their designs are in the porting guide.

## Stage 2: the start (2026-10-11)

The owner started stage 2 ([#637](https://github.com/shgew/togi/issues/637)) on 2026-10-11, and the run continues unattended under the rules of [#634](https://github.com/shgew/togi/issues/634) (**Running unattended**), recorded in [ADR 0057](adr/0057-running-the-rust-migration-unattended.md). This entry opens the stage's log; its pull requests append their measurements below it.

**The plan council.** Before the start, a two-reviewer plan council reviewed the epic and stages 2–12 ([#637](https://github.com/shgew/togi/issues/637)–[#647](https://github.com/shgew/togi/issues/647)). Its findings were applied to the issue bodies, each marked "(orchestrator, 2026-10-11, plan council)" ([summary](https://github.com/shgew/togi/issues/634#issuecomment-6108195762)):

- A `guard` status runs from `main` through `pull_request_target`, so a pull request cannot unregister or rewire the comparison checks that judge it.
- The cutover gains a persistent backup, a rollback procedure, a live-session gate beside the live-journal gate, evidence renewed on every push, and closing only after the release.
- Offset write targets and raw observed offsets become separate types, and the claims for typestate narrow: it proves order and authority, not that a readback or teardown happens.
- The SMU write transaction lives in the session crate (stage 4), with the `smu.intent` receipt minted by the journal crate, so stage 5 reshapes nothing the simulations link.
- Stage 5's async ownership follows the owning object, with Go's single non-cancellable PM-table reader kept as the one exception.
- Hazard 9 names Go's amd64 assembly paths (`archExp` with its FMA branch, `archLog`), and a flake check regenerates every Go-generated vector file.
- Dependabot's `nix` and `github-actions` updates pause until stage 9, a red `main` stops merges until its Linux jobs are green again (a revert of the breaking merge comes first), the integration owner is defined, and the CI-budget fallback no longer halts the run.
- The stop list applies to merged code and to defects Go shares; findings in an open pull request are fixed there.

**Decisions this stage's first pull request records** ([#691](https://github.com/shgew/togi/issues/691)). ADR 0057 partly supersedes ADR 0048 and ADR 0046. Protected comparison assets change by the additive rule, the append-only hash manifest and the `guard` status, with the owner-only `owner-approved` label for the rest. The suite is every session of `tools/bench/suite.json`, 220 today (the dev and holdout seeds of its 11 scenarios, counted from the file), where ADR 0048's text says 252. On `main`, the macOS job also builds the Rust workspace and runs its tests.

**Not measured yet.** Compile and test times, the comparison's CI time and the heavy-job cap come from stage 2's measurements pull request.

## Stage 2: Go-compatible float formatting (2026-10-11)

The `togi-gocompat` crate reproduces Go's float formatting byte for byte ([#697](https://github.com/shgew/togi/issues/697)), checked against vectors that Go's own output generates. It covers these Go format sites:

- `encoding/json` of a `float64` (journal events, machine and facts files, bench results, caches) maps to `json_f64`.
- Explicit `(verb, precision)` pairs map to `format_float`: `f` with -1, 0, 1, 2, 3, 4 and 6, and `g` with -1, 6, 9 and 17. The runtime uses them in `internal/config/config.go`, `internal/sim/sim.go`, `internal/journal/payloads.go`, `internal/tuner/r7.go`, `internal/watch/story.go` and `internal/trial/run.go`, and the tools in `tools/bench`, `tools/fit`, `tools/forecast`, `tools/modelcheck`, `tools/stats` and `tools/audit`. Widths and `+` flags are padding and sign handling that the tool ports add.
- `fmt` `%v` of a scalar float maps to `format_v`. The simulator's seed parts (hazard 6) would need it for float parts, although no caller passes one today. Composite `%v` (slices, maps) belongs to stage 4.
- `encoding/json` of a `float32` (the PM-table arrays in samples, `internal/machine/pm_table.go`) is not covered and lands with its first consumer.

## Stage 2: Go's exp and log in `togi-gocompat` (#698, 2026-10-11)

**What it ports.** `togi_gocompat::math` has `exp`, `expm1`, `log` and `log1p` returning the bits Go 1.27.1's `math` returns on the target the crate is built for (hazard 9 of [`porting.md`](porting.md)). On amd64 Go runs assembly for `Exp` (`archExp`, with an FMA branch taken when the CPU has AVX and FMA) and `Log` (`archLog`), and pure Go without fusion for `Expm1` and `Log1p`. On arm64 Go runs assembly for `Exp` with fused multiply-adds, and pure Go fused as the arm64 compiler fuses it for the other three. The amd64 code picks the `archExp` branch at run time with `is_x86_feature_detected!`. Fused operations go through `f64::mul_add`, which is correctly rounded by contract, so the bits do not depend on whether it becomes the instruction or libm's `fma`. No transcendental libm function is called, and the crate has no `unsafe`.

**Size.** The library is 671 lines (`math/{mod,amd64,arm64,go}.rs`), its tests 356, and the math modes of the Go vector generator `tools/gocompat-vectors` 490 lines (`math.go` and the CPU feature files, including a few lines of assembly; `main.go` came with the float formatting entry above) (counted from the files after the review round below).

**Vectors.** `tools/gocompat-vectors` runs Go's own `math` functions on a fixed input set (specials, thresholds, grids, powers of two, a seeded PRNG, and the ranges togi's Go code calls them with) and writes `function input-bits output-bits` lines. `math-amd64-fma` and `math-amd64-nofma` (the latter under `GODEBUG=cpu.fma=off`, `exp` only) run natively; `math-arm64` is cross-built and run under `qemu-aarch64` on amd64, and natively on arm64. The committed files are 75,680, 21,909 and 75,696 lines. The `gocompat-vectors-math` flake check regenerates them and requires them byte-identical to the committed files; on aarch64-darwin it regenerates and compares `math-arm64.txt` natively, and the darwin `rust-nextest` depends on it, so `main`'s macOS job runs it. The Rust tests require every vector to match bit for bit, with no tolerance, and the amd64 tests also require the two `archExp` branches to differ on the vectors that were found to tell them apart.

**What the vectors caught.** Three operand choices of the arm64 fusions, guessed from `ARM64.rules`, were wrong, and each failed on the vectors before it was corrected. Some coefficient fusions change no vector and rest on the disassembly of Go's arm64 build.

**Review findings of the first round, and their outcomes.**

- The FMA instruction was reached through `core::arch` intrinsics and `#[target_feature]` in `unsafe`, which AGENTS.md allows only in the crates for `internal/trial` and `internal/hardware`, against the decision in #637 to fuse through `f64::mul_add`. Replaced: one `fma` helper calls `f64::mul_add` on every target, and the crate has no `unsafe`, `target_feature` or intrinsic. The FMA-branch and arm64-port tests no longer need an FMA host; only `dispatch_follows_the_cpu` reads the CPU.
- Go's own tests of these functions were not mapped (#698 Acceptance). The inputs of `TestExp`, `TestExpm1`, `TestLog` and `TestLog1p` (`vf[i]`, `vf[i]/100`, `vf[i]*10`, `Abs(vf[i])`, `10`, `9` and the `vf*SC` special lists) are now in the generator, each set citing its test and lines of Go's `all_test.go`, and in `go_test_exp`, `go_test_expm1`, `go_test_log` and `go_test_log1p`. Each requires the input to be in the vector file for its function and the port to return the vector's bits, and `log(10)` and `log1p(9)` to equal `LN_10` exactly as Go's tests do, on the amd64 and arm64 ports. Regenerating added 61 lines each to `math-amd64-fma` and `math-arm64` (15 `exp`, 22 `expm1`, 12 `log`, 12 `log1p`) and 15 `exp` lines to `math-amd64-nofma`, and removed none. `TestLog1p` iterates `vflog1pSC` with `len(vflogSC)`, 7 of its 8 entries, so the eighth (4503599627370496.5) is not added. Go's `testExp` also runs `ExpGo`, the pure-Go fallback, which no path of the crate runs.
- Native arm64 regeneration was added to `main`'s macOS job, through the darwin `rust-nextest`'s dependency on `gocompat-vectors-math`.
- Setting the CPU feature with `GODEBUG` in the Rust binary was rejected: togi never sets `GODEBUG`, and the Rust binary has no `GODEBUG` contract. The Go generator sets it only to force Go's non-FMA branch.

**Not measured.** Compile and test times of the crate wait for the stage's measurements pull request. `cargo test` and `cargo test --release` of the crate each passed all nine tests on one x86_64 host; neither run was timed.

## Stage 2: `internal/trialfiles` (2026-10-11)

The `togi-trialfiles` crate ports `internal/trialfiles` ([#695](https://github.com/shgew/togi/issues/695)): 1,923 lines of library and 1,555 of tests against Go's 140 and 295, with the Go package unchanged. Most of the library is not the port itself: `goerr.rs` holds Go's errno tables, `goos.rs` Go's `os.Remove`, `Rename`, `ReadDir` and checked close, and `gzip.rs` with its `flate` module Go's `gzip.Reader` and `compress/flate` decompressor (including `flate: corrupt input before offset N` and the bytes delivered before an error), so that the errors `Compress` writes verbatim into the journal (`session.warning.error`) and `Open`'s header errors read as Go's do. It removes the placeholder crate and the `--no-tests=pass` flags the empty workspace needed.

- **One departure from Go: the compressed bytes.** `Compress` writes the same gzip container, with Go's default header (`1f 8b 08 00 00 00 00 00 00 ff`), but flate2's DEFLATE encoder chooses different blocks than Go's `compress/gzip`, so the same input compresses to different bytes. No spec, comparison (`tools/bench/same.go` skips trial directories), golden file or consumer depends on those bytes; the spec freezes the gzip container and the decompressed content.
- **Dependencies this crate introduces.** `flate2` with its pure-Rust `miniz_oxide` backend, because std has no DEFLATE: it supplies the compressor and the CRC-32. Its decoders are not used, because they differ from Go's observably (a stream decoder can drop already decoded bytes when it meets corrupt data, where Go hands them over before the error), so the decoder is the port above. `nix` as a safe wrapper where rustix has no safe API: the checked close (rustix's `close` is `unsafe`, std's `File` drops the close error, and `unsafe_code` is denied here) and `mkfifo` for the tests on Apple. `rustix` for `unlink`, `rmdir`, `rename` and the open flags; `thiserror` for the error enums.
- **Go's error text.** `goerr.rs` renders each failure like the `*os.PathError` or `*os.LinkError` Go returns (`op path: errno text`, the ops Go uses at each call), with the errno strings of Go's tables for Linux (amd64 and arm64, which differ only by errno 133) and Apple, `errno N` for an unknown one, and paths as `filepath.Join` cleans them, and `invalid argument` for a path with an embedded NUL. The errors keep Go's raw path bytes, because a workload chooses its directory names and Go's JSON encoder writes an invalid byte as the escape `\ufffd` but a real U+FFFD as UTF-8: `go_text()` on `Error` and `Errors` returns Go's exact `err.Error()` bytes for the journal encoder to serialize with Go's JSON rules, while `Display` shows each invalid byte as the character U+FFFD. It moves to `togi-gocompat` when a second crate needs it. `Remove` also removes an empty directory, and `Rename` refuses to replace a directory (EEXIST), as Go's `os` does; `ReadDir` skips an entry that vanished before its type lookup.
- **Not measured yet.** Compile and test times wait for the stage's measurements pull request.

## Stage 2: Go's Pow in `togi-gocompat` (#699, 2026-10-11)

**What it ports.** `togi_gocompat::math::pow` returns the bits Go 1.27.1's `math.Pow` returns. Go runs the pure-Go `pow` on amd64 and arm64 (`haveArchPow` is true only on s390x), with `Frexp`, `Ldexp` and `Modf` in pure Go too, so the port follows `pow.go` statement for statement, including its special cases, evaluation order and the repeated squaring on `Frexp`'s fraction. It contains no product feeding an addition, so the arm64 compiler fuses nothing in it. The two targets differ only through the `Exp` and `Log` that `pow` calls for a fractional exponent, which the port takes from the target's `exp` and `log`. `Sqrt` is the hardware instruction on both, and the sign of the NaN it returns for a negative operand differs between them.

**Vectors.** `pow-amd64-fma`, `pow-amd64-nofma` and `pow-arm64` of `tools/gocompat-vectors` hold `pow base-bits exponent-bits output-bits` lines: the inputs of Go's `TestPow` (`Pow(10, vf[i])` and the whole `vfpowSC` table), the `Growth` values and integer exponents of `internal/sim/hazard.go` and `tools/fit/fit.go`, the miss probabilities of the tuner's rerun test, integer exponents past the overflow and underflow of float64, the thresholds at 4096 and 2^53 and 2^63, fractional exponents around one half, and subnormal bases. The nofma file holds only the pairs that reach `Exp`. The `gocompat-vectors-pow` flake check regenerates the three files like `gocompat-vectors-math`, and the darwin `rust-nextest` depends on it.

## Stage 2: integer, `float32` and duration conversions in `togi-gocompat` (#702, 2026-10-11)

Hazard 9 of [`porting.md`](porting.md) names integer powers, `float32` intermediates and float-to-duration rounding. The inventory below covers the Go code that gets ported, which is everything except `tools/release`, `tools/board`, `tools/reviews` and `tools/cover`, found by grep over non-test files, so a conversion hidden behind a helper or an inferred type may be missing. `togi_gocompat::convert` and the generator modes `convert`, `convert-amd64` and `convert-arm64` of `tools/gocompat-vectors` cover it.

**Integer powers and power loops.**

- `math.Pow(Growth, float64(d-1))` in `internal/sim/hazard.go` (`loadedRate`, `unloadedRate`) and `math.Pow(model.Growth, float64(-delta))` in `tools/fit/fit.go`. Go's `Pow` splits an integer exponent by repeated squaring on `Frexp` parts, so `powi` and `powf` are not substitutes. It belongs to the `Pow` pull request of #637 and adds no helper here.
- No repeated-multiplication power loop and no `1<<n` converted to float exists. `1<<n` appears only as an integer mask or step: `internal/machine/per_core.go`, `internal/sim/hazard.go`, `internal/tuner/hunt.go` (`1<<failed`) and `internal/watch/canvas.go`.

**`float32`.**

- The PM-table lanes (`internal/machine/pm_table.go`) are decoded with `math.Float32frombits` in `internal/smu/pm_table.go` and narrowed from float64 in `internal/sim/shared_voltage.go` (`float32(v.IdleV)`, `float32(request)`). They are compared and widened to float64 in `internal/session/samples.go`, `internal/requests/requests.go` and `tools/bench/metrics.go`. The only `float32` arithmetic is the comparison and `max` in those loops.
- `as f32` is Go's `float32(x)` for every input checked (round to nearest even, overflow to infinity, subnormals, NaN with several payloads), and `f32` `+ - * /` equal Go's on amd64 in debug and release. The arm64 file records Go's arm64 results; the native Rust comparison runs in macOS CI and was not run here. There is no helper for these operations. The bits of an invalid operation differ between the architectures (`0/0` is `ffc00000` on amd64 and `7fc00000` on arm64), so every `f32` and `f32-ops` row with a NaN input or result is in the per-architecture files, and the Rust tests compare raw bits, never "any NaN".
- Encoding a `float32` as JSON stays out of scope, as the float formatting entry says.

**Float to `time.Duration` and Duration methods.**

- `time.Duration(script.AtS * float64(time.Second))` and `time.Duration((afterS + seconds) * float64(time.Second))` in `internal/sim/model.go`; `time.Duration(float64(span)*0.5*float64(threads))` in `internal/trial/run.go`; `time.Duration(scaled)` in `tools/replay/main.go`. These map to `duration_from_secs_f64` and `f64_to_i64`. The conversion is architecture-dependent: amd64 returns `i64::MIN` for NaN and every out-of-range value and arm64 saturates (see Float to int); `internal/sim/model.go` `scriptedFailure` with `AtS=1e10` is the case that reaches it.
- `Duration.Seconds()` in `internal/session/trial.go`, `internal/sim/hazard.go`, `internal/sim/model.go`, `internal/trial/run.go`, `internal/trial/samples.go`, `tools/bench`, `tools/forecast` and `tools/stats`; `Hours()` in `tools/bench/metrics.go`, `tools/forecast/forecast.go` and `tools/stats/hunts.go`. Go converts whole units and the remainder apart, so `duration_seconds`, `duration_minutes` and `duration_hours` do the same; dividing the nanosecond count as a float differs.
- `Milliseconds()` in `internal/journal/journal.go`, `internal/sim/samples.go`, `internal/trial/run.go` and `internal/trial/samples.go` is an integer division, equal to Rust's `/`.
- `time.Duration(n) * time.Second` and the other integer multiplications (many sites in `internal/session`, `internal/watch`, `internal/sim`, `tools/fit`) wrap on overflow in Go; Rust's `*` panics in a debug build, so the port uses `wrapping_mul`.
- `Round(time.Millisecond)` prints elapsed times in `tools/bench/same.go`, `tools/fit/anchor.go`, `tools/fit/forward.go` and `tools/fit/main.go`; those lines and the `%s` of a hang limit in `tools/bench/main.go` print a `Duration`. `duration_round` and `duration_string` reproduce Go's `Round` and `String`. No Go code calls `Duration.Truncate`; `duration_truncate` exists only because the vectors cover it with `Round`.
- `Duration.String` also writes journal bytes and a subprocess argument, through `duration_string`: `internal/machine/loadsteps.go` (`DutyPeriod` via `%s`, and each of `LoadStepPeriods` through `String`, in `LoadSchedule.String`), which `internal/session/trial.go` stores in `journal.TrialSignal.Schedule`; `internal/session/watchdog.go` (`waited` via `%s` into `journal.PreflightCheck.Detail`); `tools/audit/sweep.go` (`o.timeout.String()` as the `--timeout` argument of `tools/bench`); and `internal/sim/replay.go`, where `spec.Duration` is formatted with `%v` inside the key that `fnv64` hashes to seed the replay pick. `tools/bench/main.go` formats the hang limit with `%s` in an error. A typed scan of every ported package for a `time.Duration` argument to a variadic `...any` function or a `.String()` call on one found exactly these and the `Round(time.Millisecond)` prints above; a Duration inside a struct printed with `%v` would not show in it.
- `shortDuration`, `lengthWords` and `minutes` in `internal/watch` print whole seconds or minutes by integer division and `%`, never `Duration.String`.

**Parsing durations.**

- `time.ParseDuration` is reached through the `flag` package: `flags.Duration("after", ...)` in `tools/replay/main.go` and `flags.DurationVar(&o.timeout, "timeout", ...)` in `tools/bench/main.go` and `tools/audit/main.go`. `flag` maps every parse error to its own message (`errParse`), so only whether Go accepts a string and the nanoseconds matter, not the error text. The grep found no other Duration parser, including direct `ParseDuration` calls, `TextVar`, or `UnmarshalText` implementations, outside the vector generator; it covers the same non-test files as above.
- `parse_duration` ports `ParseDuration` with `leadingInt`, `leadingFraction` and `unitMap`, including both micro signs (U+00B5 and U+03BC). Each fraction goes through float64 (`uint64(float64(f) * (float64(unit) / scale))`), so `0.5ns0.5ns` is 0, and the int64 boundaries are checked as Go checks them. It returns `None` where Go returns an error. A string that is not UTF-8 cannot be a `&str`; Go rejects every such string, since no digit, sign or unit contains an invalid byte, and the test expects `error` for those vectors.

**Integer division and `%` with negative operands.** Go truncates toward zero, as Rust does, but `MIN / -1` is `MIN` and `MIN % -1` is 0 in Go while Rust panics. The `%` sites are `internal/machine/workloads.go` (`index%len(ws)`), `internal/trial/plan.go`, `internal/trial/run.go`, `internal/tuner/{checking_partial,deepening,search,dashboard_state,hunt}.go`, `internal/watch/{panels,render,story}.go`, `internal/smu/driver.go`, `internal/simrun/simrun.go`, the duration tests against `time.Minute` and the `tools` that take medians or sample. The `/` sites are too many to list (`core / 8`, medians, the Duration conversions above), and the port uses `wrapping_div` and `wrapping_rem` wherever an operand can be negative or `MIN`. The vectors show those two equal Go's for negative operands, `-1` and `MIN`; whether a given site can see such operands was not audited. Shift counts of 64 or more give 0 in Go and panic in Rust; `shl_i64` follows Go, and no site is known to reach it.
- `int(*value/1000)` and `int(*value / 1000)` in `internal/trial/samples.go` (lines 47 and 109) are not float-to-int: `*value` is an `int64` from `strconv.ParseInt`, so `/` is integer division, equal to Rust's for a non-negative or negative operand (truncation toward zero).

**Float to int.**

- `int(math.Round(x))` (`internal/requests/requests.go`, `internal/sim/shared_voltage.go`), `int(math.Ceil(...))` (`internal/config/config.go`, `internal/requests/requests.go`, `tools/forecast/summary.go`), `int(math.Floor(...))` (`internal/tuner/r7.go`), `int(x*float64(len(banks)))` in `internal/sim/model.go`, `int(float64(cells) * ...)` in `internal/watch/render.go`, `int(e.result.Ran.Seconds())` in `internal/session/trial.go`.
- Go's amd64 conversion (`CVTTSD2SQ`) returns `i64::MIN` for NaN and for any value outside the int64 range, where Rust's `as` saturates and turns NaN into 0. Go on arm64 lowers the conversion to `FCVTZSD` (`ARM64.rules`), which is Rust's `as`: NaN is 0 and an overflow saturates at `i64::MAX` or `i64::MIN`. `f64_to_i64` dispatches on `target_arch` as `math` does; private `f64_to_i64_amd64` and `f64_to_i64_arm64` implementations are each tested against their own file on every host. `internal/sim/model.go` `scriptedFailure` with `AtS=1e10` is a case where the two differ.
- `math.Round` on amd64 is Go's pure-Go bit algorithm (not intrinsified), which returns a signalling NaN unchanged where Rust's `f64::round` quiets it (`7ff0000000000001` in, `7ff8000000000001` out). `convert::round` is a port of Go's algorithm on x86_64; on aarch64 Go intrinsifies `Round` to `FRINTAD`, which `f64::round` lowers to. `Floor`, `Ceil` and `Trunc` use `ROUNDSD` on amd64 when the CPU has SSE4.1 and `FRINTM`, `FRINTP` and `FRINTZ` on arm64; both quiet a signalling NaN and Rust's x86_64 `floor`, `ceil` and `trunc` do not, so `floor`, `ceil` and `trunc` here quiet it. The vectors assume a CPU with SSE4.1: without it Go runs assembly that returns a signalling NaN unchanged, and the generating host had it.

**Vectors.** Three files. `convert.txt` holds only rows that are the same on every architecture: `dur-string`, `dur-float`, `dur-int`, `dur-round`, `dur-mul`, `dur-parse`, `divmod`, `shl`, `shl-int`, and the `f32`, `f32-ops` and `math` rows without a NaN. `convert-amd64.txt` and `convert-arm64.txt` hold what depends on the architecture: every `i64`, `dur-secs` and `dur-scaled` row, and every `f32`, `f32-ops` and `math` row with a NaN input or result. The generator modes `convert-amd64` (refuses to run on another architecture, and on a `GOAMD64` other than v1) and `convert-arm64` (runs natively on arm64, otherwise cross-builds the generator and runs it under `qemu-aarch64`) write them. Every generated input is architecture-independent: a product that is added or subtracted is converted to float64 first (the Go spec's rule against fusing it), because the arm64 compiler fused `r.Float64()*2e4-1e4` and changed the input itself. `convert.txt` generated by the arm64 build under `qemu-aarch64` was compared with `cmp` and is byte-identical to the amd64 one. The `gocompat-vectors-convert` flake check regenerates all three files on x86_64-linux (the arm64 build runs under qemu-user, and its `convert.txt` must equal the committed one) and `convert.txt` and `convert-arm64.txt` natively on aarch64-darwin, where the darwin `rust-nextest` depends on it as it does on `gocompat-vectors-math`. The Rust tests compare raw bits everywhere: no NaN is equal to another. The float-to-int rows of both files run against both software conversions on every host, and the file of the build's own architecture runs against `f64_to_i64`. The files are about 4.0 MB (`convert.txt`), 1.4 MB (`convert-amd64.txt`) and 1.4 MB (`convert-arm64.txt`). The float-to-int inputs are the boundaries of int64 and int32, three ulps either side of each power of two at the exponents 31, 32, 52, 53, 62, 63, 64, 65, 100 and 1023 (positive and negative), NaN with several payloads, infinities, half-way cases, the model's own values (volts, MHz, request counts), and seeded random values. The `dur-parse` inputs are Go's own `parseDurationTests` and `parseDurationErrorTests`, the int64 boundaries, long fractions, `0.5ns0.5ns`, malformed strings, and 6,000 seeded strings built from the grammar, with the input hex-encoded and the result either nanoseconds or `error`. Each Rust test passed in debug and release on one x86_64 host. The `gocompat-vectors` check compares exactly its three float files with `cmp` rather than the whole `testdata` directory, so every float vector is still compared byte for byte while other modes add files.

**Not measured.** Whether any Go site reaches an out-of-range float or a negative divisor. The vectors come from one x86_64 host with `GOAMD64=v1` and SSE4.1, and the arm64 vectors from Go's arm64 build under `qemu-aarch64`, not on arm64 hardware. The aarch64 Rust build was type-checked and linted for `aarch64-apple-darwin` but its tests were not run here; they run on the macOS job. The `nix build` of the flake check was run on x86_64-linux only.
