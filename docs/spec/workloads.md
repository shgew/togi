# Workloads

Normative rules for what a trial runs, how it is contained, and how its outcome is judged. The research behind the regime choice is summarised in `../prior-art.md`.

## Evidence compatibility

The evidence epoch (`togi_tuner::EVIDENCE_EPOCH`) versions workload content, effective backend configuration, duration and pass/failure detection contracts. Incompatible observations remain raw history but earn no current passing exposure or qualification. Content identity includes executable bytes/build and effective generated configuration, never the Nix store path alone; a path-only relocation preserves compatibility, changed content does not. Firmware context separately scopes validity. [The tuner](tuner.md#evidence) owns ledger keys and [the journal](journal.md#transitions) owns the fresh transition.

## Backends

| Backend | nixpkgs attribute | Result check |
|---|---|---|
| mprime | `mprime` (unfree) | Torture test residue and rounding checks, reported in `results.txt` |
| y-cruncher | `y-cruncher` (unfree) | Built-in verification in stress mode, reported on stdout |

Every workload must check its own results: silent computation errors are a known failure mode ([ADR 0008](../adr/0008-self-checking-workloads.md)).

A backend integration:
- generates its configuration files, which togi creates exclusively in the trial's work directory, with the thread count, and with the exact logical CPUs where the program takes them: y-cruncher sets its own affinity from its config and would otherwise start workers on every CPU, while mprime names no CPUs (`EnableSetAffinity=0`) and the trial's scope confines it;
- produces the argument vector to launch;
- parses output as it arrives into progress, computation error and fatal setup error;
- reports setup problems as inconclusive, never as failures.

Togi creates a root-owned `trials/<trial>/` container. Each backend instance has its own writable directory: `work/` for a single instance, `cNN/` for each core of an R6, R7 or R8 trial, or `cpuNN/` for each logical CPU of an R9 trial. Before launching, togi gives the configured backend account ownership of that directory and every generated input file, so mprime can update `prime.txt` and `local.txt`, create `results.txt`, and y-cruncher can access `stress.cfg`. The surrounding trial and state directories, retention markers, journal and control files remain root-owned and nonwritable by that account. Backend binaries remain read-only in the Nix store; no package file changes ownership. This is a privilege drop, not a filesystem sandbox: ordinary system permissions still apply outside togi's state.

The runner recreates a reused trial container before preparing inputs, without following old instance or file symlinks. It exclusively creates and retains both log descriptors before transferring instance ownership, so another workload sharing the backend UID cannot redirect privileged log opens. Ownership moves by descriptor, each generated input in turn and then the instance directory; the first transfer that fails ends preparation naming that file or directory, and nothing after it changes owner or launches. Relative trial-directory paths are resolved lexically against the working directory, which is exact because no component may be a symlink, and the absolute result is passed unchanged to both the launcher and the scope's working-directory option.

File preparation (recreating the trial container, then creating each instance's directory, logs and inputs and handing them over) runs on a dedicated thread, one preparation at a time, because storage can block it while the runtime keeps handling cancellation and deadlines. One absolute budget of 10 s covers all of a start's preparation. A preparation that misses it ends the start with a typed preparation error naming the step; a preparation asked for while an abandoned one still runs is refused as busy, and a thread that cannot be created or ends without reporting is a preparation error too. Cancellation ends the wait at once. Instances already launched when a later instance's preparation fails are rolled back by the shared teardown. An abandoned preparation thread is never replaced and never joined: it keeps the next preparation refused until it returns.

Before changing anything below it, the runner opens the trials root by descriptor from `/`, one component at a time with `O_NOFOLLOW`, so no component may be a symlink, and judges each directory by its place before going below it. `/` is trusted whoever owns it. Every other directory must belong to root or the runner's user. A directory above the state directory may be writable by group or others only with the sticky bit, which stops them replacing entries they do not own, and each directory below it must pass in turn. The state directory belongs to root or the runner's user and the trials root to the runner's user alone, and neither may be writable by anybody else, sticky or not. Missing components are created with mode `0755`. Conditions samples are read back and trials compressed only through descriptors held from that validated root, opening regular files with `O_NOFOLLOW | O_NONBLOCK`, so a planted symlink or FIFO is never read and no validated pathname is resolved again. The state directory, trials root and trial containers have mode `0711` independent of the process umask; instance directories have mode `0755` before ownership transfer. Other ancestors are never chmodded: before launching, the runner checks, over the directories its walk recorded from `/` down to the trial container, that the backend UID and primary GID may search each one, and refuses an inaccessible path by naming the deepest such directory. Each directory grants search through exactly one permission class: its owner bits when it belongs to the backend UID, else its group bits when its group is the backend's primary GID, else its other bits. A directory that only an ACL makes traversable must also grant the applicable mode-bit search permission. Watched outputs are opened without following symlinks and without blocking on special files, and only a regular file with one link, owned by the account the workload runs as, is read; a rejection makes the trial inconclusive unless stronger failure or containment evidence survives.

Known quirks the integrations handle:
- **mprime:** needs `NumCPUs`, `CoresPerTest`, the `CpuSupports*` switches for the instruction set and the FFT range in `local.txt`/`prime.txt`. `TortureTime=1` keeps each FFT size to one minute, so a trial covers several sizes. Errors land in `results.txt`, which the runner tails once per second, and mprime can keep running after one.
- **y-cruncher:** command-line thread options do not confine it; only a config file names the CPUs. It prints `Failed to set core affinity` when confinement and config disagree, which counts as a containment violation. Its startup is slow and needs the stall grace period.
A recognized affinity CPU number outside `0..=65535` is a typed backend-observation error and leaves the trial inconclusive unless stronger evidence decides it; it is never replaced by the instance's first CPU.

Backend output lines on stdout, stderr and watched files may contain at most 64 KiB before a newline or carriage return; an unterminated line has the same byte limit. Exactly 64 KiB is permitted. A longer line is a runner error and uses the shared bounded teardown: the trial is inconclusive unless a containment violation or backend failure signal collected before or during teardown takes precedence. Other output I/O errors and unconfirmed cleanup remain runner errors regardless of captured backend evidence. Reading and retaining output is bounded even for an unfinished line or a large watched-file append. The runner keeps the first 64 KiB of the offending line for diagnosis (in the stream log or watched-file buffer), stops reading that stream or file, and never classifies its truncated prefix as a complete line. It does not silently truncate output and continue the trial.

Watched-file opens, `fstat` calls and reads never run on the runtime thread: each watched file has one blocking owner, at most one read per file is in flight, and a read still running is never replaced. The runtime waits for it only until an absolute bound, the polling budget below during a trial and the drain or teardown deadline during teardown; a read not finished by then stays in flight and leaves the file undrained. A supervision tick waits for an in-flight read at most until the next sample, load step or trial deadline, so a stuck read delays cancellation and `Stop` by at most one sample interval. Each watched-file polling read processes at most 64 KiB, including short complete lines, in chunks of at most 4096 bytes. Unread bytes and partial lines remain at their exact incremental offsets for later batches; exhausting a batch is not EOF or successful draining. Polling checks cancellation and deadlines before each chunk and after every classified line, and a stop at any line boundary, including one on the last byte of a chunk, ends the poll with the offset just after the consumed line. During a trial, a polling round yields by the next scheduled load step or sample interval, or the trial deadline, whichever comes first; this scheduling budget expiring leaves output pending, not an I/O error. The next round resumes with the next watched file and instance so a flooded file cannot monopolize polling. Only output classification yields to the polling budget: each sample tick still checks containment and CPU progress for every ready instance until an outcome or trial cancellation ends supervision. Supervision returns to process events and load-step scheduling between polling rounds.

## Regimes

"One thread" means the core's first logical CPU. Its SMT sibling stays idle, except in R5 and R9, which load both threads of a core by their own rules.

| Regime | Purpose | Content |
|---|---|---|
| R1 light | Highest single-core boost with light instructions | 1 thread. mprime SSE FFT 4K-21K; y-cruncher BKT + SFTv4; y-cruncher SNT + SVT, using the lowest-ISA binary the package ships |
| R2 vector heavy | Vector units, higher current | 1 thread. mprime AVX2 FFT 36K-248K; mprime AVX-512 FFT 36K-248K; y-cruncher FFTv4 + N63 + VT3, using the Zen 5 binary |
| R3 load steps | Current transients between busy and idle | An R1 or R2 workload suspended and resumed with `SIGSTOP`/`SIGCONT`. On and off periods are drawn from {10 ms, 50 ms, 200 ms, 1 s, 5 s} with a recorded seed |
| R4 medium load | Partial duty cycles | An R1 workload at 25%, 50% or 75% duty with a 100 ms period, cycling per trial |
| R5 SMT pair | Both threads of one core | R1 and R2 workloads with 2 threads on both logical CPUs of the core |
| R6 idle | Normal power management with the profile applied | One confined 1-thread R1 instance per core, each stopped with SIGSTOP as soon as it enters its scope, before the next instance launches. Trial timing begins only after all instances are stopped. First half: no load at all. Second half: short bursts (SIGCONT, then SIGSTOP 100 ms later, every 2 s) on one core at a time in scheduling order |
| R7 full and partial | Package power, thermals and shared-rail/CCD interaction | One confined 1-thread R2 instance per loaded physical core; full CCD, honest partial subsets and all-CCD full load are distinct classes |
| R8 neighbours | Light-core boost beside heavy neighbours on one CCD | One light role on one core's first logical CPU, an R1 workload sustained or an R3 workload with load steps, beside an R2 workload sustained on the first logical CPU of every other core of that CCD, one instance per core. The light core is an explicit argument. Light and heavy roles may use different backends |
| R9 all threads | Every logical CPU loaded, SMT and whole-CCD interaction | An R1 workload, 1 thread, on every logical CPU of every core, one instance per logical CPU. 10 s phases alternate all threads loaded and only the serial logical CPU loaded, all threads first. The serial logical CPU is an explicit argument and never stops |

Ruleset 13 schedules R1–R9 under the [coverage matrix](#coverage-matrix). Workloads, subsets, roles, light/serial positions and intended durations remain distinct classes. A failure never selects a culprit by request rank: requests generate informative partials only. R6 uses every physical core; the profile includes idle cores even when a trial loads only a subset. Every set-load intent names its actual loaded cores.

Every loaded logical CPU has a role: its core, logical CPU, instance, workload and schedule (`trial.start.roles`, `journal.md`). Roles that name the same instance share one process, as both threads of an R5 core do; separate instances may run different backends side by side, so an R8 light y-cruncher instance can run beside mprime neighbours, and each instance's output is classified by its own backend. R1–R7 derive their roles exactly as before. Instance directories and scopes keep their names (`work` and `togi-trial-<id>` for one instance, `cNN` and `togi-trial-<id>-cNN` per core in R6, R7 and R8) and an R9 instance, one per logical CPU, is `cpuNN` and `togi-trial-<id>-cpuNN` named by its logical CPU, so the SMT siblings of one core never share a name. Whichever instance a backend signal comes from, it names that role's core.

Ruleset 13 uses the existing honest partial-load derivation (`HonestChain`), not the removed checking-chain policy. With finite measured requests for every loaded core, idle successive highest-request groups, ties within 1 mV together, retaining at least two physical cores. With any absent/nonfinite request, ignore offsets and all partial telemetry and use explicit subsets, removing highest core ID first, one per link. Record the measured source or missing-request fallback, the frozen subsets and any changed derivation. Fewer than three cores, or a tied group leaving fewer than two, produces a typed uncovered reason, never an empty chain counted as partial coverage. To qualify when a measured tied chain has no partial, explicitly run the subset fallback; topology that admits no two-core partial is reported structurally unavailable rather than passed.

### Load-step schedules

An R3 or R4 workload starts running, then alternates on and off periods; each on period ends with SIGSTOP and each off period with SIGCONT. R3 draws each period independently and uniformly from {10 ms, 50 ms, 200 ms, 1 s, 5 s} with `rand`'s `StdRng` seeded by the recorded seed, so the seed reproduces the schedule with the same build. R4 runs for its duty share of every 100 ms period. The trial end records how many of each signal were sent.

### Role schedules

R8 suspends only its light role: an R1 light role runs sustained and an R3 light role follows the seeded load steps above, while the R2 neighbours on the other cores of its CCD run sustained and are never signalled after launch. The light core is an explicit argument, so a caller rotates it by building one trial per light core.

R9 alternates 10 s phases, all threads first. Every instance runs through an all-thread phase; at its end, SIGSTOP stops every instance but the serial logical CPU's, and SIGCONT at the end of the following one-thread phase resumes them: stops at 10 s, 30 s, and so on, continues at 20 s, 40 s. A boundary at or after the trial's end sends nothing. The serial logical CPU is an explicit argument and its instance is never stopped.

## Durations and checking schedule

The old search/checking/hunt duration allocation is retired. The bounded matrix is sized against the registered gate's simulated operator calendar, not a real-night deadline. Qualification receives the [scheduler's soft elapsed-time share](tuner.md#night-order-and-reserved-budgets) while queues compete. On hardware, launch/cleanup overhead and required repeats consume task time too; incomplete qualification spans operator-ended nights rather than dropping cells. The calendar gate instead idealizes zero trial setup/teardown and applies no controller-placement exclusion or required repeat, so its scores omit that overhead.

### Warm-up boundary

After all instances and confinement are ready and profile readback is verified, trial timing starts. Exposure excludes the first 5 s for R1–R7 or 30 s for R8/R9, **inside** the intended duration, not added to it. These retain the runner's existing boundaries without crediting setup or making many small cells cost an extra warm-up. Schedules run from timing start and are not restarted at the boundary. Failures are active throughout and always retained, including during warm-up. A sustained block is one uninterrupted launch, not summed short starts; its eligible seconds are duration minus warm-up. Request/clock summaries still require 20 valid post-warm-up samples.

### Coverage matrix

The exact-profile qualification certificate is a **composite matrix**. R1–R5 per-core cells on the changed CCD run at its proposed offset; unchanged CCD cells may reuse an earlier completed qualification only at that CCD's identical offset, class, placement contract, content, epoch and firmware, with no intervening applicable failure. This is reuse of a per-CCD observation, not a pass from a deeper offset. All package/interaction cells below run freshly at the **complete proposed profile**. On first qualification, stock controls or firmware invalidation, no unchanged-CCD credit is assumed. Monthly re-qualification runs all CCDs' cells fresh. The certificate explicitly lists reused witnesses and the fresh whole-profile cells; it cannot be described as every class having run freshly at that vector.

One full own-duration launch per listed breadth position plus each stated sustained block is required. A conclusive failure invalidates the certificate: [failed next-step qualification](tuner.md#failed-next-step-qualification) owns the durable disposition of a proposed profile, and [daily-event escalation](tuner.md#whole-profile-veto-and-escalation) owns a current-D re-qualification failure. Only incomplete, nonfailed certificates retain outstanding cells across nights. Every position means every physical core for per-core/R8 rows, and each explicit physical-core position group for R9; only the actually tested logical position gains ledger exposure.

| Regime | Breadth cells, ordered by catalog then core ID | Intended duration | Additional sustained cells |
|---|---|---:|---|
| R1 | All 3 light catalog entries on every core of the changed CCD | 90 s | None |
| R2 | All 3 heavy catalog entries on every core of the changed CCD | 90 s | None |
| R3 | First 3 light load-step entries, every core of the changed CCD | 120 s | None |
| R4 | The 3 light entries paired in order with 25%, 50%, 75% duty, every core of the changed CCD | 120 s | None |
| R5 | One rotating R1/R2 catalog entry on both SMT CPUs of every changed-CCD core | 120 s | None |
| R6 | One rotating R1 entry, all cores, full idle-then-burst schedule at the exact profile | 900 s | None: its own duration already exceeds a short probe |
| R7 | One rotating R2 entry, each CCD full then every honest partial, finally all CCDs full | 120 s | One 600 s all-CCD full block |
| R8 | One rotating light/heavy catalog pair and light schedule, every light-core position on **both** CCDs | 120 s | One 600 s block at the rotating light-core position |
| R9 | One rotating R1 entry, one serial logical CPU per physical-core position group, all threads otherwise following its phase schedule | 120 s | One 600 s block at the rotating serial position |

Use the durable qualification ordinal, starting at zero, modulo catalog/position count for rotating selections. R5 enumerates R1 then R2; R8 enumerates index-matched light/heavy pairs, sustained light then bursty light for each pair. R9 selects the serial SMT sibling by ordinal modulo sibling count; consecutive qualifications cover the other logical positions. Sustained R8/R9 position is ordinal modulo physical-core count, using the same selected workload/schedule. The declared classes are frozen when qualification starts. R7 full/all-CCD are one cell on a single-CCD machine; honest partials do not duplicate the full set.

The numerical choices preserve existing 90 s search, 120 s short and 900 s idle durations and add ten-minute package blocks to expose sustained load without an exhaustive cost explosion. For two eight-core CCDs with at most twelve partials, a normal one-CCD step schedules 19,380 s (about 5.38 h) before launch/cleanup and required repeats. Fresh firmware qualification, single-CCD exclusion repeats and monthly nonzero-profile work may take longer and span nights. Qualification does not shorten or omit a cell when the operator ends a night; an interrupted cell remains unmet. No trial runs an all-zero profile, including at first qualification or after firmware changes; [Ruleset 14](tuner-ruleset14.md#operator-attested-stock-stability) owns operator-attested stock stability.

The [registered calendar](../../tools/bench/day-night.json)'s simulated operator ends each night after eight hours, leaving an arithmetic 2 h 37 min for all other work and overhead after those 155 launches. This is a diagnostic comparison, **not a policy limit**: there is no predicted-night allocation or cell-fit check. The simulator keeps its scenario's fixed operator-end length for comparable gate scores, interrupting a running trial at that instant under the normal operator-end rules. Its gate reports convergence under the zero-setup/teardown assumption, without controller-placement exclusions or required repeats; actual overhead must come from hardware runs, not matrix arithmetic or calendar scores.

**Coverage limits:** this bounded matrix does not test every workload/duty Cartesian product, both R8 schedules and all pairs at each step, every R9 serial SMT sibling at each step, or sustained blocks at every position/partial. Untested classes remain uncovered, never inferred safe. Later qualifications rotate the sampled classes and positions. This deliberately trades exhaustive exposure for timely day steps within the registered calendar; neither a certificate nor its cap is a rare-event or hidden-daily-load guarantee.

For **mapping**, run one breadth launch per R1/R2 catalog/core position, the selected rotating R8 pair/schedule at every light position, selected R7 full/partials and selected R9 serial position group at each tested CCD offset, other CCDs zero. Use the same duration and selection rules, frozen by the mapping-step ordinal instead of the qualification ordinal. Diagnostic cap coverage uses that same ordinal until the step finishes, including across interrupted attempts. Mapping never qualifies a day profile; the [cap spec](tuner.md#cap-s-margin-from-measured-slope) owns which observations enter its rate projection. Order is R1, R2, R8, R7, R9; full qualification order is R1 through R9. Reproduction follows the qualification order but stops under its [bounded task](tuner.md#night-order-and-reserved-budgets).

Freeze the complete mapping matrix, including R7 partial subsets, at the ordinal's first `trial.intent`; later telemetry shapes only later steps, never reopens finished steps. Subtract compatible adequate isolated witnesses at the same class and complete profile, whichever task produced them.

All trials use managed placement under the ordered [controller placement](#controller-placement) rules. Mapping's quieter contract cannot qualify an exact-profile cell; these conditions are separate classes.

On a single-CCD machine the [controller placement](#controller-placement) keeps a capped host outside the loaded set when possible. Where every physical core is loaded, exclude the rotating host from passing credit: each required position must run with that position **not** the host, repeating rotations until its quota is met. For multi-position CCD rate accounting use the minimum eligible seconds across required positions, never summed simultaneous core-hours, retaining every failure once. This conservative minimum neither pretends the host was tested nor multiplies wall-hours by cores. A placement that cannot cover a required position remains uncovered and cannot qualify.



## Controller placement

The controller is togi's session, journal, supervisors, Tokio runtime, sampler and in-process dashboard. Every Ruleset 13 trial uses managed placement ([ADR 0078](../adr/0078-controller-clock-and-rotation.md)); no legacy-placement evidence qualifies it. The trial's purpose distinguishes isolated mapping from exact-profile qualification.

Placement is computed before any backend launches, from the loaded physical cores, their logical CPUs and the applied, read-back offsets. A suspended role remains loaded for this purpose. A missing offset is not CO 0. The rules, in order:

| Shape | Controller placement | Clock and credit |
|---|---|---|
| Single CCD with an unloaded physical core | Rotate across unloaded physical cores, in core-ID order, regardless of their offsets | Capped; the host core earns no exposure credit, while every loaded position remains eligible |
| Single CCD with every physical core loaded | Rotate across tested physical cores, in core-ID order | Capped; exclude the host and repeat rotations under the matrix's position-credit rule |
| Isolated mapping, other than R6: every loaded core is on one CCD and another entire CCD is unloaded at CO 0 | Every logical CPU of the lowest-ID eligible idle CCD | Capped; the loaded CCD retains its credit |
| Exact-profile trial or R6 with an eligible unloaded CO-0 core | The lowest-ID unloaded CO-0 core | Uncapped; controller work is outside the tested set |
| Every core loaded, including both-CCD R7 and R9, or any remaining shape with no unloaded CO-0 core | Rotate across the loaded physical cores, in core-ID order | Uncapped; controller work counts as load on the host core |

Rotation uses the caller's persistent trial ordinal modulo the eligible core count, not a workload index, pass quota or random draw. Each rotating placement records its host core and applied offset. Outside the single-CCD unloaded-host rule, it never chooses a nonzero unloaded core merely because its offset is shallower. The single-CCD unloaded-host selection changes with the implementation layer; the predecessor runner's tested-core-only rotation cannot fulfill this contract for one-core loads.

The cap uses the lowest permitted cpufreq limit, respecting the policy's current minimum. The runner discovers shared policies rather than assuming one policy per logical CPU. It must not cap a policy containing another tested core: on a single CCD only the excluded host's SMT CPUs may share the capped policy. Policy discovery, saved limits, requested limits and readbacks are recorded; restoration and same-boot recovery follow [runtime.md](runtime.md#trial-confinement).

An unavailable placement, incomplete thread-affinity change, failed cap or mismatching cap readback withholds passing exposure for the whole trial and records why. It never erases stronger failure evidence. Single-CCD exclusions and their coverage accounting follow [the matrix](#coverage-matrix); raw outcomes/telemetry remain visible and a host fault remains failure evidence.

## Containment

Each backend instance runs as a child of togi inside a transient scope confined to its logical CPUs:

```
systemd-run --scope --quiet --collect --uid=<uid> --gid=<gid> --working-directory=<instance-dir> -p AllowedCPUs=<cpus> -p DefaultDependencies=no -- <argv>
```

`DefaultDependencies=no` keeps a system shutdown from stopping the scope on its own. Otherwise systemd stops the scope and the unit running togi at the same moment, the backend can exit before togi sees its signal, and the trial would end as an unexpected exit on the target instead of interrupted. Without the default dependencies, togi's teardown ends the scope after the signal reaches it.

The root launcher clears all supplementary groups before starting `systemd-run`, retaining UID 0 for system-bus access and scope creation. The scope launch then drops to the configured backend UID and primary GID. Its working directory is explicit: with `--uid` alone, `systemd-run --scope` defaults to the account's home instead of the prepared instance directory. Between fork and exec the launcher makes only direct system calls (clearing the groups as root, its CPU affinity, a parent-death SIGKILL and a check that its parent still lives), never a C library wrapper that can take a lock another thread held at the fork.

If togi dies before teardown, the scope can outlive it and keep its descendants running. The next fresh start or resume sweeps concrete `togi-trial-*.scope` units after nonwriting preflight and before any SMU profile write, whether in a tuning boot or an in-session run. The sweep sends SIGCONT and SIGTERM through bounded `systemctl kill --kill-whom=all` calls on each exact scope during the shared grace period, then uses normal teardown's bounded scope-kill slot to send SIGKILL and stop the scopes. A recovered PID and its start time are used only to verify exit, never to signal a PID or process group that may now belong to somebody else. Cleanup verifies that no matching unit or process remains and that every captured process exited, including one that moved out of its scope. A moved process that survives scope signaling is a containment dead end, not a reason to signal its recovered PID. Recovered processes are observed only; the runner holds no handle that could signal them. Discovery and verification consume the same absolute 15 s budget as teardown, not a fresh budget per scope. Cancelling a sweep before any scope is known returns cancelled at once; once a scope is known, cancellation, including during the process scan, never drops the cleanup: the signals, kill, stop and verification of the listed scopes still finish inside that budget, and the result is cancelled joined with the containment failures if cleanup did not confirm.

The safe real-process integration test kills a helper owner and sweeps its detached descendant, with systemd unit discovery and operations replaced by a deterministic seam. It proves real process cleanup without touching host scopes; deterministic fake-time tests prove unit filtering and deadlines. This does not prove systemd transient-scope collection on a real tuning boot; that requires the VM trial infrastructure.

Processes that disappear while `/proc` is scanned are no longer leftover workloads; missing-process errors do not fail the sweep, but permission and other read failures still do. A process the kernel is tearing down, whose stat shows state `X` and a process group of -1, counts as gone, not as a failed observation.

The kernel enforces the cpuset whatever the backend does. togi also samples the processor field of every backend thread in `/proc/<pid>/task/*/stat` once per second, from the moment the process is inside its scope. A thread seen outside its allowed logical CPUs is a dead end. Stopping a trial terminates the whole scope.

Every running workload exposes `Started`, `Wait` and `Stop`. `Stop` consumes the trial: it ends supervision if it still runs, returns once teardown has finished and returns the teardown's outcome, which the single supervisor task owning the trial caches, so a `Stop` racing a `Wait` mutates nothing. A trial dropped without `Stop` is torn down by its supervisor, which reports that and whether the teardown confirmed on standard error and decides nothing; a handle dropped after the supervisor last looked for that, so that the outcome cannot be delivered, is reported the same way. Shutting the runner down cancels every start and sweep in progress and at once asks every live trial's supervisor to tear down; a trial that a pending start delivers afterwards is torn down as soon as it exists. Rollbacks, sweep cleanup and teardowns all run at the same time within one shared slot measured from the start of shutdown (the 15 s teardown, the 5 s writer join and a 5 s margin) before its runtime ends; a start, sweep or trial still not finished at the end of that slot is reported on standard error, never silently abandoned. A start nobody waits for that ends without confirmed cleanup, and a sweep nobody waits for that fails, are reported there too. Every such report, like the one for a dropped trial, names each joined error and each cleanup failure with every cause behind it, each cause once. The run owner calls it before any cleanup profile write and preserves containment errors. Trial timing, meaning the duration deadline, the sampling ticks and the load-step schedule, is anchored when `Start` returns, after R6's initial stops, not when `Wait` is called: supervision and output draining run between the two calls, readers keep draining, and `Wait` delivers the queued reports and the outcome whenever it is called. Reporter callbacks run only on the thread blocked in `Wait`.

Teardown order is an explicit sequence of steps in one owner function (the numbered steps below), never an arrangement of `Drop` impls: fields drop in declaration order, locals in reverse, and a moved value drops where it ends up, so `Drop` is only the backstop that reports.

`Start` waits for the runtime at most the 10 s preparation budget, plus each instance's scope-readiness wait of at most 30 s, plus the 15 s rollback teardown and a 5 s margin. A start that has not answered by then returns a containment error with no stop proof, and the runtime rolls that start back instead of finishing a trial nobody holds.

Normal trial ends and partial-start rollbacks use the same teardown, with one absolute deadline shared across all instances:
1. Send SIGCONT, then SIGTERM to each process group owned by the current run, and allow up to 3 s of grace shared by all groups. The runner owns each launcher through a pidfd and observes its exit with `waitid(P_PIDFD, WNOWAIT)`, so an exited launcher stays an unreaped zombie holding its PID and process group until teardown reaps it; no group signal can reach a reused PID, and the supervisor alone signals and reaps, so no start-time check is needed for owned groups.
2. Send SIGKILL to every known scope with `systemctl kill --kill-whom=all`, including scopes whose launcher has exited and scopes attempted before a launch failed. The calls share a slot of at most 2 s and each gets only the remaining time.
3. Send SIGKILL to every owned process group, then reap each launcher; a launcher that has not exited by the deadline is an unconfirmed cleanup. A group that no longer exists receives no signal and its scope remains the cleanup target.
4. Drain output for up to 10 s, without passing the absolute deadline. Every watched file on every instance shares this deadline, so the collective drain of any number of files and instances is bound by the one teardown budget and unread backlog at the deadline withholds the proof: drain them in bounded polling rounds that check the remaining time between files, reads and lines, even after the launchers exit. Both pipe readers of an instance must reach end of input; at the deadline the readers are aborted, which closes the pipe descriptors even when a detached descendant holds the pipes open but leaves the drain unconfirmed. Aborting a reader does not close a log file: both log files of every instance belong to the output log writer, which is waited for separately after teardown (below). A watched read still in flight at the deadline stays in flight and leaves the drain unconfirmed.
5. Verify, by scanning `/proc` every 100 ms within the same absolute deadline and off the runtime thread, that no process remains in any known scope. A successful `systemctl kill` only acknowledges delivery, so a descendant that outlives it is caught here; a member still present at the deadline, or a scan that fails or finishes late, is a containment dead end. A scan is abandoned at its absolute deadline or when its caller is cancelled, and while an abandoned scan is still blocked every new scan fails at once as a lost observation instead of occupying another thread.
6. For each instance whose writers are confirmed stopped (its group SIGKILL delivered and, when scoped, its scope kill confirmed and its scope seen empty), read every watched file to its end once more, within what remains of the absolute deadline and whatever an earlier poll saw, then classify its final unterminated line exactly once. A surviving writer's last append made while step 5 waited is read here. A file that cannot be read to its end by the deadline is unconfirmed draining even when an earlier poll had drained it, so the proof is withheld. No watched-file read follows the deadline.

Teardown takes at most 15 s regardless of instance count. Cleanup succeeds only when every launched process has exited, output has drained, every scope kill succeeded or confirmed that its scope no longer exists, and no process remains in any known scope. A failed or timed-out scope kill, an unconfirmed process-group kill, or an undrained backend is a containment dead end: no next trial or tuning profile write follows. When a partial-start rollback cannot confirm cleanup, its containment error lists the launch error that caused the rollback first, then the cleanup failures. Offset restoration belongs to run-level cleanup, not partial-start rollback or trial outcome adjudication, and runs only after confirmed workload teardown; unconfirmed cleanup prevents restoration and a clean `shutdown` even if the journal also fails. Final output from the pipes and watched files is classified before the outcome, including unterminated computation errors printed during teardown.

After the teardown, the output log writer and the samples writer are waited for together, each for at most the 5 s writer join (Conditions sampling). A log write stuck past that bound abandons the writer thread with the files it holds; that, or a log writer thread that ends without reporting, is an output runner error, never containment.

A panic in the backend's classifier, during supervision, teardown or a partial-start rollback (including the final watched-line classification), is caught at the classifier: the line counts as unclassified output, the teardown still runs within its bounds and still proves or withholds the stop, and the trial ends with a supervision-panic runner error and an inconclusive result unless higher-precedence evidence decides it, never a pass. When supervision itself panics and the classifier panicked too, both are kept as supervision-panic runner errors, the supervision panic first. A failed start keeps its launch error first and joins the panic after it. The panic hook of `togi run` does not end the process for such a panic, which happens on the trial runtime's thread and not the run owner's: it reports the panic on stderr and lets it unwind to this catch, so the run goes on (`runtime.md`, Exit codes).

A watched file is tracked by device and inode as well as offset: an accepted but unread backlog is lost when the file vanishes, shrinks, is replaced by another inode (even of the same size) or becomes a symlink or nonregular file, and a half-read line counts as backlog. Its descriptor must also be a regular file owned by the account the workload runs as (the backend account, or the runner's user when unscoped) with exactly one link; a hard-linked file or a file of another owner is refused before any byte is read. Each poll commits the size it accepted before framing any byte, so a read that fails while accepted bytes remain unread is lost output, including bytes first accepted by that same poll; end of file before the accepted size keeps the backlog pending and the file undrained. An unread watched-file backlog at the cleanup deadline is unconfirmed output draining, not a successful EOF, and prevents a pass, another trial or a tuning profile write. Final unterminated watched-file lines are classified exactly once only after their bytes have been fully read; a batch boundary is not a line boundary. Backend errors beyond the first read batch remain evidence when drained within the shared deadline. The explicit oversized-line rejection above still retains its diagnostic prefix without classifying it as a complete line and keeps the same evidence precedence; the retained prefix is not unread backlog, so the cap alone is not containment.

Rejecting a watched symlink, nonregular file, hard-linked file or file of another owner without a known unread regular-file backlog intentionally stops that reader and does not by itself make draining unconfirmed; confirmed process and scope teardown leaves the trial inconclusive and retryable. If a previously accepted regular file still had unread bytes, replacing it with a symlink or nonregular file, or adding a link to it, loses accepted output evidence and remains unconfirmed draining and a containment dead end.

A non-EOF backend-pipe read failure cannot confirm output draining and is a containment failure, even if the process exit and scope kill otherwise succeed.

Every systemd CLI invocation has a context deadline. The preflight `systemd-run` probe and `systemctl reboot` are bounded by 30 s; a trial's `systemd-run` process is bounded by its trial duration plus the startup and teardown allowances. Teardown `systemctl` calls share the bounded slot within the absolute 15 s cleanup deadline, so each kill has only the remaining time. A timed-out kill is failed cleanup even if its output says the scope is missing. The `journalctl` commands of one kernel-log read share a single 30 s budget, the whole read rather than each command, and stdout is capped at 64 MiB. At the deadline the command's whole process group is killed and its pipes are closed, so a descendant holding them cannot extend the wait. A timeout, an output over the cap and an entry that cannot be decoded are read failures, not an empty log, and follow the existing inconclusive handling; a failed cursor read keeps the machine checks read before the failure and returns no cursor. Every journal row is decoded only from a JSON object, and each kind of read decodes only the fields it requests. Each row of a kernel-log MCE read carries `MESSAGE`, an in-range microsecond `__REALTIME_TIMESTAMP` and a non-negative microsecond `__MONOTONIC_TIMESTAMP`, all three present and the timestamps decimal strings; a cursor read also requires a non-empty `__CURSOR` and the read boot's `_BOOT_ID` on every row, else the cursor is unresumable. The first row of a resumed cursor read is the anchor already read: it must carry the resume cursor and is otherwise not decoded. A reset-reason row needs only `MESSAGE`. A boundary row's `__SEQNUM`, when present, must be a decimal number; a missing or zero `__SEQNUM`, an empty or missing `__SEQNUM_ID` or another boot's `_BOOT_ID` only leaves the boundary unproven. The CPU and bank of a machine-check status line must be decimal numbers in range. A value these rules reject is a read failure, not a silent zero. A `Linux version` line counts for reset-reason support only when it starts with decimal major and minor numbers; any other such line is ignored and a boot with no such line reads as unsupported, and only a recognized number too large to represent is a read failure.

## Trial outcome

A trial passes when all of these hold:
- it ran for its full duration;
- the backend reported no computation error;
- the backend kept making progress;
- no failure signal named a core;
- every sampled thread was on an allowed logical CPU.
- for a managed trial, controller placement and any required cap were established and read back.

Both successful waits and runner errors use the same evidence precedence, including recovery after a crash:

| Evidence (first applicable row wins) | Result |
|---|---|
| Containment escape | Dead end |
| Backend computation error, stall or early exit | Failure, even with cleanup errors, cancellation or a crash |
| Relevant managed controller, dashboard or worker process fault inside the trial window | Failure; kernel-reported executing CPU locates it when available |
| MCE inside the trial's window | Failure |
| Reset reason | Applies only without higher-precedence evidence |
| Required sampling, current-boot kernel log or setup observation missing | Inconclusive |
| Full duration, every required observation valid and no failure | Pass |

Runner errors remain diagnostics in the trial's reason; they never replace a classified failure. A failed kernel-log boundary read or an unresumable cursor leaves its interval unobserved, making an intersecting trial inconclusive unless higher-precedence evidence survives. Later successful reads do not erase that trial's lost observation. MCEs returned with a read error remain evidence.

An explicit `No journal boot entry found` result from `journalctl` is a missing observation, not zero MCEs: the current-boot read returns a missing-boot error and the trial is inconclusive unless higher-precedence evidence decides it. Exit status 1 with empty stdout and stderr is a valid no-match result and remains clean. During crash recovery, a missing older boot still supplies no MCEs without a retry; missing current-boot recovery observations keep the existing retry policy.

The kernel log is read from a cursor at each trial's intent boundary and at teardown, also on process startup and clean shutdown. Consecutive reads cover profile writes, backend retry waits and the time between trials without a streaming follower. Each trial's evidence window starts once its profile has been applied and read back and ends at the teardown read, including the target's reset to 0. Both boundaries are inclusive. An MCE is a trial cause only when its boot-local timestamp falls inside that window; MCEs before profile readiness, after teardown or beyond the current read's monotonic time are recorded and shown by `status`, `events` and `watch`, but do not feed trial decisions.

The opaque cursor is persisted on existing boundary events, scoped to their boot ID. Same-boot resume validates and continues the last recorded cursor; crash recovery reads the previous boot's persistent log, including its unread tail, while the new boot starts its own cursor. No cursor crosses boots. An unavailable cursor is recorded as observation loss before re-anchoring on the retained log; re-anchoring permits future covered trials, not a retroactive pass for a trial with a lost observation. A journal from before cursor recording is read from the beginning of the boot, with existing MCE records deduplicated.

Required samples are the thread processor fields used to check containment and the process CPU-time fields used to check progress. A failed task-directory read, an unreadable thread or process stat, or malformed required data, including a processor field above the largest CPU number the journal records (65535), is a lost observation. Even a single lost sample makes the trial inconclusive unless higher-precedence evidence decides it; successful samples later in the trial do not repair the loss. Readable threads still provide containment evidence when another thread cannot be read. A process or thread disappearing before its stat can be read is normal, not sampling loss: an exited thread is skipped, and the process-exit observation decides whether a backend exited early. Temperature is optional and does not affect sampling validity.
CPU-time milliseconds and sample elapsed milliseconds must fit their recorded signed fields. An overflowing required CPU-time observation is sampling loss, and an overflowing sample elapsed time is a runner error; neither is capped to an invented measurement.

A scoped instance that never entered its scope by the trial deadline is a setup error and makes the trial inconclusive unless higher-precedence evidence was found. A process exit queued before teardown begins is an unexpected exit; exits caused by teardown are not.

Failure signals:

| Signal | Detection | Reported location |
|---|---|---|
| Computation error | Backend output | The instance's core |
| Unexpected exit | Process exits before the trial ends, without a setup error | The instance's core |
| Stall | Over a 10 s window of unsuspended time, backend CPU time advances less than half of thread count times that window, after a 30 s startup grace | The instance's core |
| Managed process fault (SIGSEGV, SIGBUS, SIGILL, general-protection fault, SIGABRT) | Kernel trap reports or the system journal's coredump signal metadata, at the trial boundaries and recovery | The executing logical CPU's physical core when reported; a CPU outside the tested set is journaled only, never charged to tested offsets |
| Corrected MCE | Kernel log, read from a cursor at every trial boundary | The core of the reporting logical CPU if the bank is core-local, else unattributed |
| Uncorrected MCE | Kernel log of the next boot, or of the crashed boot in the persistent system journal | Same rule |
| Crash | Boot ID differs from the last journal boot with no clean shutdown; reset reason narrows its classification | Unlocated unless associated backend or core-local MCE evidence supplies a location |

These locations describe the observed signal, not a culprit selected for a
per-core offset change. No regime, including multi-core R7, infers blame from
voltage-request rank or a worker's stalled CCD.
[Isolated mapping](tuner.md#night-edge-u) owns charging the tested CCD,
including a failure located on a CO-0 core during a nonzero mapping trial.
There is no all-zero stock-confirmation rerun. Whole-profile qualification
and reproduction failures remain failures of their exact tested profiles.

Managed process-fault observations match the recorded controller PID or known thread IDs, a saved backend instance PID or exact trial scope, and the dashboard's known process identity. An executable name alone does not prove membership. Faults without a reported CPU remain unattributed failure observations; they never inherit a made-up executing core. Recovered observations use the fault's boot-local time and the same trial window as live observations, including the unread tail of an interrupted same-boot trial. They are deduplicated on recovery. A controller fault can therefore close its interrupted trial as a failure instead of disappearing as an inconclusive interruption.

Crash detection and evidence: every tuning boot in the journal other than the current one, whose last tuning event is not `shutdown` and that no `crash.detected` names, has crashed. A tuning boot has at least one event only a tuning run appends, so run startup that precedes `config.loaded` (`state.rebuilt`, a startup `mce`) admits it. The run's notes, `session.warning` and `boot.leave_reason`, are the exception: they neither admit a boot nor replace its last tuning event. The events the day observer shares with a run alone, `night.plan`, `night.qualification`, `night.reproduction` and the SMU intent, write, readback and error events, do not admit it, nor do the journal's `journal.torn` marker or `command.reset` and `session.archived`. Daily-only boots remain excluded, as [runtime's daily-evidence boundary](runtime.md#ruleset-13-policy-boundary) requires, even when the day observer writes those shared events. Its evidence is the MCEs in its own kernel log that are not between trials, plus the uncorrected MCEs logged by the boot after it (the next boot in the journal, or the current boot), each recorded once as an `mce` event with `from_boot`. Recovery also records the previous boot's between-trial MCEs with `between_trials: true`, without using them as crash evidence or decision causes. An MCE that an earlier `crash.detected` already cites is evidence of that crash only: a boot's own log starts with the MCEs its predecessor's crash left in the banks. Recovery is idempotent: detection, closing the crashed trial and its failure are each redone by the next `run` if a further crash or kill interrupts them, so a crash during recovery is detected on its own, normally as stray, without losing the first.

Recovery compares an old boot's MCE `monotonic_ns` with the profile-applied boundary of the open trial in that same boot. A crashed trial has no teardown timestamp: its unread kernel-log tail remains eligible after the start boundary, rather than being cut off at the last progress event. Uncorrected MCA evidence retained into the following boot is eligible for the preceding crash without comparing its new-boot clock to the old trial's clock. Corrected next-boot MCEs are not retained crash evidence. Events lacking `monotonic_ns` preserve the earlier replay behavior; an explicit zero is a timestamp, not a missing field.

Recovery journals MCEs decoded before a read error and retries the unread remainder at 1, 5 and 30 minutes; after those retries, relevant backend or MCE evidence still decides the crash, while no evidence leaves the existing `no_evidence` dead end.

Kernel reset reasons are read from the immediate system boot after the crashed boot, even when togi did not run in that boot. `journalctl --list-boots` supplies a candidate, not proof of succession: recovery requires the crashed boot's last journal entry and the candidate's first entry to have the same `__SEQNUM_ID` and consecutive `__SEQNUM` values. These boundaries read all journal entries, not only kernel messages, because journald assigns sequence numbers across its split files. A gap, a changed sequence identity, missing boundary entries or missing sequence metadata (including systemd before 254) leaves the reason unknown. If the crashed boot or its successor cannot be identified, or the successor's log has been vacuumed, recovery records no reason and keeps ordinary crash handling; it never substitutes a later boot's reason. Watchdog expiry, sync flood and CPU shutdown are crash failures. Power-button reset during a trial is a crash failure; outside a trial it is inconclusive. Thermal trip is a dead end unless earlier backend or MCE evidence established a failure. No reason line on a kernel supporting this log (6.16+) is treated as power loss, and is inconclusive only after reason reporting has been confirmed in another tuning boot. Day-only boots do not supply that confirmation. A boot whose kernel log holds neither its `Linux version` line nor a reason line, because its start was rotated out, reads as unsupported. A boot the system journal no longer holds confirms nothing and is skipped without a retry; other kernel-log read errors keep the recovery retry policy. Unknown or unsupported reasons keep ordinary crash handling. A recorded backend signal or relevant MCE always takes precedence over reset reason.

Crash recovery also looks for the previous boot's saved kernel messages under `/var/lib/systemd/pstore/`, after `systemd-pstore.service` has archived `/sys/fs/pstore/`. The supported EFI layout is `<Unix timestamp>/<three-digit dump count suffix>/dmesg.txt`, reconstructed by systemd from `dmesg-efi-` or `dmesg-efi_pstore-` chunks. The dump timestamp must fall at or after that boot's first system-journal entry and before the next listed system boot's first entry, including boots where togi did not run. Missing or non-increasing boot timestamps leave the diagnostic absent. Among matching records, the greatest full boot-local dump count wins, then the lowest chunk part from each record's first kernel dump header: the directory count suffix wraps after 999, and EFI timestamps each chunk separately, so a dump crossing a second boundary can be split across archive directories. The group containing the lowest part retains the newest kernel messages. Malformed or incomplete headers warn and leave the diagnostic absent. Other layouts are not guessed from filesystem modification times, which date archival rather than the dump. This is a best-effort wall-clock match, not a boot ID embedded in pstore; clock changes or vacuumed intervening boots can make the interval unavailable or ambiguous. Unlike reset reasons, this optional diagnostic does not require consecutive journal sequence numbers: it can survive the loss of the crashed boot's journal tail. A matching record adds the optional bounded `crash.detected.pstore` diagnostic (`journal.md`); missing records, including hard freezes that never dumped messages, leave it absent. Read errors warn and do not retry or stop recovery, since this is optional diagnostic text, not stability evidence. Recovery neither removes nor modifies the archive. It opens every path below the archive directory relative to a directory descriptor without following symlinks; a directory that is writable by its group or others, or an entry owned by neither root nor the user running togi, a `dmesg.txt` that is not a regular file or has more than one hard link, is a read error. The dump header and the kept tail come from the same opened file.

The opened `dmesg.txt` must not be writable by its group or others; otherwise it is a read error.

A trial still open when `run` starts, in a boot that did not crash (the same boot, or one that ended in `shutdown`), ends as `interrupted`: a failure (`corrected_mce`, or `uncorrected_mce` when none is corrected) when `mce` events were already recorded for it, else inconclusive. Interrupted trials do not count toward the inconclusive dead end.

A trial closed this way, after a crash or an interruption, records as its `duration_s` the time from its `trial.start` to its last `trial.progress`, `trial.signal` or `trial.sample` in the journal, or 0 without a `trial.start`. The separate conditions samples do not change this lower bound or supply stability evidence. After a crash, recovery also records the last complete conditions sample's elapsed seconds, Tctl and available loaded-core frequency range in optional `trial.end` fields (`journal.md`).

For failed trials with at least two loaded cores, persisted worker CPU-time samples may name the worker that stopped advancing first. R6, R8 and R9 omit this evidence because their workers are suspended by design: unchanged CPU time can be scheduled suspension, including a worker that has not yet carried load. A stall is a terminal run of unchanged cumulative CPU time, dated at its first unchanged sample; a later advance cancels that stall. The earliest terminal stall must be unique. No samples, fewer than two samples, any missing loaded-worker reading, decreasing counters or non-increasing sample timestamps, and tied earliest stalls leave the evidence absent. A worker that advanced through the final sample has no observed stall. `stalled_core` is diagnostic only in every regime: it neither attributes a failure nor restricts a requester group or tested CCD. Crash recovery derives it from completed persisted samples on the next boot; an ordinary failure derives it after the samples writer finishes.

The `trial.end` message for a trial closed on resume says `last evidence Ns after start` instead of presenting `duration_s` as elapsed time. A trial that ends while togi watches it, including an orderly stop by signal, reports its measured duration with `after Ns`.

### MCE locality

- Locality uses the SMCA bank type decoded by the kernel (`edac_mce_amd`), never a hard-coded bank number.
- A decoded bank continuation is assigned only when exactly one MCE could own it. If multiple status records arrive before their bank lines, those records keep an unknown bank type and are unattributed; journal message order alone cannot identify the owner.
- A new error-description boundary closes orphaned continuation state, so a truncated record does not prevent attribution of the next independent record. A surplus bank continuation establishes interleaving and clears tentative attribution back to the earliest unresolved status; this can also clear independent records whose ownership the log cannot distinguish.
- Core-local bank types are load-store, instruction fetch, L2, decode, execution and floating point. Their reporting logical CPU identifies a physical core when the topology can map it.
- Shared bank types, including L3, memory controller and data fabric, are not core-local even when a reporting CPU or core is known. An unknown bank type is not inferred local from that location. Preserve reported CPU/core and bank information as diagnostics without confusing reporting location with bank locality.
- Offset adjudication follows [isolated mapping](tuner.md#night-edge-u) and [whole-profile qualification](tuner-ruleset14.md#3-what-exactly-qualifies-the-next-profile), with no all-zero rerun or R7 requester-group exception.

MCA bank contents survive a warm reset and the kernel logs them early in the next boot. The tuning boot keeps the system journal persistent, so the crashed boot's last kernel messages stay readable.

## Conditions sampling

At each sampling tick (once per second by default), the runner hands one conditions sample to a writer without waiting for storage. The writer creates the root-owned `trials/<trial>/samples.jsonl` and syncs its containing directories, then appends each accepted sample in order as one JSON line and fsyncs it before writing the next. One sample may wait while file setup or a write is in progress; if that slot is full, the new sample is dropped instead of delaying load-step transitions or the trial deadline. File setup also does not delay scheduled load steps, cancellation or teardown. A crash can lose the unfinished write and queued sample; completed writes remain durable. Trial teardown does not wait for storage, but afterwards the runner waits at most 5 s for the writer thread to drain accepted samples and close the file, unless setup or persistence failed; the 5 s is one absolute bound that counts any wait for a worker thread, never a join that could outlast it; a writer still stuck after 5 s is abandoned, not joined, and reported as a storage runner error, never as containment, and the trial's result is not delayed further. A writer that ends without reporting is reported the same way, and an append failure is kept ahead of a later close timeout in the reported errors. Writes are complete (`write_all`) before each fsync, so a short write is a failure. Samples use milliseconds since trial timing began, including idle and suspended periods; they are diagnostic, not observations that decide an outcome. Missing or unreadable sensors are omitted, never fatal. A failure to create, write, sync or close the samples file is a runner error, with the existing teardown and outcome precedence. The close error is the one the kernel's `close(2)` returns for the real descriptor, observed after the final `fsync`; when both the sync and the close fail, one close error carries both. Compression of the closed samples and logs is separate maintenance (`journal.md`, Files), never stability evidence.

Tctl and Tccd temperatures come from the first hwmon whose `name` is `k10temp` or `zenpower`, using the `temp*_input` with labels `Tctl` or `Tccd1`, `Tccd2`, and so on. Temperatures are whole degrees Celsius. The maximum Tctl still goes into normally ended trials' end events.
An absent, unreadable or unrecognized optional numeric sensor remains absent. A recognized integer outside the signed sensor range is a typed observation error, including initial energy baselines and energy-counter wrap ranges; it is not silently omitted. Baseline errors use normal partial-start rollback, and sample-time sensor errors omit that sample and remain runner diagnostics.

For every physical core in the host topology (all 16 on a two-CCD part), idle cores included, the runner reads its first logical CPU's `cpufreq/scaling_cur_freq` under `/sys/devices/system/cpu`, converts kHz to whole MHz, and records it by core ID in `core_mhz`. Missing, unreadable, negative or invalid readings are omitted. Consumers summarizing loaded-core frequencies, including last-sample minimum/maximum and per-CCD medians, filter by the trial's loaded set, including temporarily suspended workers. Older samples containing only loaded-core clocks remain readable.

The same tick records cumulative backend worker CPU time in whole milliseconds by loaded core ID (`worker_cpu_ms`), reusing the confined instance's process CPU-time reading used for progress checks, which converts the `/proc` tick counts at the system's clock rate (`sysconf(_SC_CLK_TCK)`) with checked arithmetic. It includes user and system CPU time and does not advance while suspended. A reading that was not obtained (including an instance not yet ready or a tick stopped early by stronger evidence) is absent, never fabricated as zero. Non-Linux runners retain the existing unsupported process-observation fallback; this telemetry adds no new required observation or failure rule.

On Linux, the same tick takes the latest completed reading of the driver's read-only `/sys/kernel/ryzen_smu_drv/pm_table_version` and `pm_table` without waiting, then requests a background refresh if no read is in flight. Only version `0x620205`, exactly 2452 bytes (613 little-endian float32 values), and core IDs exactly 0–15 in CCD/slot order (0–7 on CCD0, 8–15 on CCD1) decode per-core lanes, for all cores including those outside the loaded set; lane i identifies core i. Zero-based float indices 301–316 are power in W, 317–332 voltage requests in V, 333–348 temperature in °C, and 381–396, 397–412 and 413–428 are C0, CC1 and CC6 residency in percent. Indices 349–380 remain undecoded because their meaning is not established. Granite Ridge feeds both CCDs from one VDDCR rail where the highest request wins: voltage lanes are requests, not separate core rails. Non-finite decoded values, any other version, size or topology, missing files, or a failed read omit `pm_table`; no zero-filled lanes replace missing data. Non-Linux hardware runners report no lanes. These readings never stop a trial or decide its outcome; request summaries inform [honest partial-load derivation](#regimes), not blame or backoff.

Development simulator: a machine with `shared_voltage` emits synthetic voltage-request lanes for all 16 cores and clocks for loaded cores on every sample, retaining lazy generation and seeded determinism. Only multi-core R7 uses its shared-rail hazard; its highest loaded request across both CCDs sets the voltage and each loaded core's smooth hazard depends on the voltage minus its workload threshold. Such failures are crashes without fabricated MCEs unless the failing core's signal mix selects a computation error. R1–R6 and single-core failure rules are unchanged. Machines without the table retain their previous samples and journals. The parameter contract and steady-state package/thermal clock model are in [Simulating](../simulating.md#shared-voltage-r7-model).

For every R1–R9 trial, `trial.end` summarizes requested voltage over complete persisted samples: take the maximum voltage request among the loaded cores in each sample with decoded lanes, then take the median and minimum of those maxima (`journal.md`). Loaded cores include any temporarily suspended workers; idle cores outside the loaded set never count. An even sample count uses the mean of the two middle maxima. The watched end and resume after a crash or interruption use the same computation from the trial's samples (`samples.jsonl` or `samples.jsonl.gz`), skipping samples without lanes and a torn tail. If no sample has lanes, both fields are absent. This optional telemetry supplies no stability evidence.

A missing conditions file is absent telemetry, and bytes after the final newline are a torn tail, even if they parse as JSON. Any other open or read failure, gzip failure, or complete line that cannot decode invalidates the trial's entire sample summary: the watched end and recovery omit every sample-derived `trial.end` field, including maximum Tctl, request telemetry, worker stalls and last-sample measurements. They append `session.warning` naming the trial and the error; the trial's outcome still follows its other evidence. Missing sensor lanes remain absent lanes, not file errors.

Sample-summary temperatures and clocks destined for `trial.end` must fit its signed 32-bit temperature or unsigned 32-bit MHz fields. An unrepresentable summary value invalidates the summary with a typed observation error and the same warning, rather than disappearing individually. An unrepresentable live maximum temperature is a typed trial-recording error.

The same persisted samples also supply each loaded core's median voltage request, each loaded CCD's top requesters (ties within 1 mV) and median clock in `trial.end`. This summary uses samples at or after the [warm-up boundary](#warm-up-boundary) and needs at least 20 samples with decoded lanes; otherwise the fields are omitted. Each CCD's clock is the median over qualifying samples of that sample's median available loaded-core clock, rounded to whole MHz, and needs at least 20 sample medians for that CCD. Single-core trials use the same summary. These fields do not affect trial outcomes or the whole-trial voltage summary above (`journal.md`). Requests may order [R7 partial loads](#regimes); they never attribute a failure or size a voltage-targeted backoff.

A file read triggers the driver's SMU table transfer (RSMU `0x03`, about 0.3 ms measured). The reader starts one initial read and refreshes at sampling ticks, not in a separate polling loop. At most one read is in flight for the shared run reader, including the informational preflight check. A read has a 100 ms budget: while a read is overdue its lanes are omitted, and a late completion is discarded. A completed reading may be reused only within two seconds of its read's start; an older reading is omitted. A stuck driver read cannot be cancelled, so it occupies that reader instead of spawning replacement goroutines. Sampling, deadlines, cancellation, backend events and load steps never wait for it. The informational check waits only for the remaining part of the same 100 ms budget and reports pending/overdue, unsupported topology or other unavailability without failing preflight.

The driver's `pm_table_version` is a binary little-endian uint32, not hexadecimal text; a version read of any length other than four bytes is invalid. The decoder checks the actual `pm_table` payload length rather than relying on a separately advertised size.

On Linux, the same sampling tick reads `/sys/class/powercap/intel-rapl:0/energy_uj` for `package_power_w` in watts, with a baseline taken when trial timing begins and the package's `max_energy_range_uj`. Successive microjoule readings produce watts as the delta divided by elapsed seconds and one million, without another sleep. A counter decrease wraps only when the package's readable range exceeds the previous reading and yields a nonnegative delta; otherwise power is omitted. Missing, unreadable, negative or invalid readings omit package power and reset its baseline, so the next valid reading also omits power. A missing domain is absent telemetry, never zero. The core subdomain is not read: on the measured Zen 5 target it tracked core 0's PM-table power alone, not all cores ([#1242](https://github.com/shgew/togi/issues/1242)). All-core power is the sum of the PM-table `power_w` lanes; package power minus that sum estimates SoC power. Samples have no independent format version; optional telemetry fields do not change the journal schema. The simulator retains its existing loaded-only clocks rather than inventing a new energy model. The hwmon, CPU and powercap roots, like the sampling, grace and teardown timings and the unscoped helper execution used by integration tests, are crate-private test construction, not runner options.
