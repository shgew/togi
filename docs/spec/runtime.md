# Runtime

Normative rules for how togi is invoked, configured and deployed.

## Day journal destination

Daily observation appends to the existing session's `events.jsonl`, using the same writer lock, strict decoding, compatibility check and durable append as tuning. It never creates a session or archives/transitions an incompatible one. Without a live session journal, `togi day` exits 1 with an instruction to start a session with `togi run`; this refusal creates no state directory or journal. Incompatible builds or unknown event data are refused before appending (exit 16). Compatibility is checked again under the writer lock, and an already archived session is not reopened for observation.

## Day observation

`togi day` requires Linux and root. It owns no SMU-writing capability and never starts a workload. At each invocation it records `day.boot_start` with the envelope's boot ID, current BIOS context, build, every online core's SMU readback and whether PID 1's hardware watchdog is armed ([Day watchdog](#day-watchdog)). A restart in the same boot reopens observation without inventing an unclean boot; its cumulative time resumes at the last durable checkpoint and excludes the unobserved downtime.

Every ten minutes of active monotonic time (`CLOCK_MONOTONIC`, not boot-time or wall time), it re-reads every offset and records `day.checkpoint` with cumulative whole active seconds for this boot. Suspend-to-idle, suspend-to-RAM and hibernation do not add exposure while the monotonic clock is stopped. A changed readback first records `day.offsets_changed`. The change time within that interval is unknown: the whole interval remains in the boot's cumulative active time but is excluded from both profiles' applied hours. No crash tail or time after the last checkpoint is extrapolated.

SIGTERM, SIGINT and SIGHUP wake the wait and finish with a final readback/checkpoint, then `day.clean_stop`, in that durable order. Systemd's orderly shutdown/reboot stop includes a power-button shutdown it handles normally. A failed read, clock or append exits 1 and never fabricates a clean stop. The observer never zeroes or restores offsets, even on error.

The next invocation records each previously observed other boot with no final clean-stop marker once as `day.unclean_end`, naming its boot ID, last checkpoint (or absence), last read-back offsets, reset reason and the evidence below. An unclean end is an observation, not a tuning crash. The tuner ignores all day events; session recovery admits only tuning activity as a tuning boot. Applying offsets is outside this command.

### Live faults

At start, every thirty seconds of active time and once more before the final readback, the service reads the running boot's kernel log through `togi-detect` and records each fault it holds as `day.fault`: every machine check, corrected or not, with its CPU, core, bank and bank type; every kernel oops, RCU stall and soft lockup; and every process killed by an illegal instruction, bus error or general-protection fault (a segmentation fault or abort is not recorded, as software defects cause them far more often than unstable silicon). Each record names its boot in the envelope and carries the offsets last read back (the profile the fault belongs to) and the log lines. The first read takes the whole boot, so a fault logged before the service started is recorded with the profile read at start; later reads resume after the log cursor, and a cursor the log no longer holds means reading the boot again from its start within the same poll, once, so the stop-time read never leaves the final checkpoint behind a lost cursor.

A fault is recorded once per boot however often it is read or the service restarts: the service rebuilds the set it has recorded from the journal's `day.fault` events of the current boot. A machine check or kernel error is identified by its content and monotonic time. A trap is identified by its kind, process name and pid, and is the same fault as an earlier one only when logged within 60 seconds of it, because the kernel line and the core dump record of one killed process carry different times and CPU evidence (writing a large dump takes tens of seconds), while a later crash of the same executable that reuses the pid is a new fault. A read that fails after returning some faults records those first, then ends the service with exit 1; it never fabricates a clean stop.

### Load mix

Every five seconds of active time the service reads each CPU's cumulative busy and total time (`/proc/stat`: user, nice, system, irq, softirq and steal count as busy; idle and iowait do not) and credits the interval since the last reading to exactly one shape. A core's share of the interval is its busiest hardware thread's busy share, so a core with one busy thread counts as busy. A core whose counters did not advance is left out of the interval, and an interval with no such core credits nothing. Cores are grouped by the session journal's recorded topology; a journal with none is an error. The interval's length is the monotonic clock's, so suspended time is never credited. An interval longer than three samples (the process was stopped or the machine held) is credited to no shape, and the next interval starts afresh, so the shapes sum to the sampled time, not to the active time.

A core is *busy* at or above 600 per thousand, *light* at or above 50 per thousand and otherwise *idle*. In this order, the first rule that holds names the shape:

1. *Idle transition*: some core was busy and the interval before had none, or none was busy and the interval before had some.
2. *Quiet*: no core busy.
3. *All threads* (the R9 shape): every core busy.
4. *Light beside busy* (the R8 shape): at least 500 per thousand of the cores busy and at least one light.
5. *Single thread*: at most 250 per thousand of the cores busy.
6. *Other*: everything else.

Each threshold is a constant of `crates/togi/src/day/load_mix.rs`, and each has one reason:

- `SAMPLE` (5 s): long enough for a share of time to mean something and short enough that a build's serial and parallel phases fall in separate intervals.
- `MAX_GAP` (15 s): three sample periods tolerates a late wake-up but not a missed stretch, which one average would misdescribe.
- `BUSY_PERMILLE` (600): far above what desktop wake-ups and background services use and well below a core's share under sustained load, so a working core counts even when scheduling noise takes a third of its interval.
- `LIGHT_PERMILLE` (50): timer ticks and housekeeping keep an idle core above zero, and 5 % is above them but below any work a person or a service would call light.
- `SINGLE_THREAD_PERMILLE` (250): boost clocks hold near their limit only while a quarter of the cores or fewer are active.
- `NEIGHBOURS_PERMILLE` (500): half is the least that makes the neighbours' heat and power draw the main condition of a lightly loaded core.

The cumulative milliseconds per shape are part of each `day.checkpoint` and resume across a restart within the boot like the hours. They describe how daily time resembles the regimes; they validate no offset. Hours exclude suspend and the downtime between invocations; the mix excludes suspend and every interval longer than three samples. A process stopped for less than that is still credited to the shape its readings show. How the service may be paused is a separate decision.

Evidence has three parts. The reset reason comes from `togi-detect`'s proven immediate-successor lookup. The kernel logs of the crashed boot and of its immediate successor give machine-check counts (corrected and uncorrected, per boot) and the crashed boot's log tail: graphics ring timeouts and resets (amdgpu, i915, xe), NVIDIA `Xid` reports, machine checks, oopses and hung tasks, and whether the log held entries after the last error. The tail also gives the sleep the log ends in: `asleep` is `suspend` or `hibernate` when the last `PM: suspend entry` or `PM: hibernation: hibernation entry` line has no `PM: suspend exit` or `PM: hibernation: hibernation exit` after it, and is absent otherwise, as in records written before the field existed. Only `togi-detect`'s kernel reader parses log text; everything after it carries typed values. A missing or unreadable boot, successor or tail is recorded as unknown, never as zero and never as CPU evidence. Until someone answers, togi classifies the end from this evidence alone, in this order: thermal trip; CPU fault (an uncorrected machine check, sync flood or CPU shutdown, logged or reported); sleep (a watchdog reset whose crashed boot ended asleep: the machine was going to sleep, which is not a CPU hang, whatever the tail logged earlier); then by the last recognized fault in the tail: a graphics error with more logging after it, a graphics error that ended the log, or another kernel error; then by reset reason: watchdog reset, power button, power loss; otherwise unknown, which covers a CF9 or software reset. Any other reset reason with a boot that ended asleep is classified as if it had not. The classification is shown, not acted on: no answer changes a profile, a decision or an offset.

**Questions and answers.**

Each `day.unclean_end` opens one question about its crashed boot: what happened. The four answers are `frozen` (it froze), `graphics` (graphics died but sound went on), `power-off` (I turned it off while it was working normally) and `unsure` (not sure). An answer is journaled as `day.answer` with the boot, the offsets that boot last recorded (its profile), the answer and the answering user's uid. A later answer for the same boot replaces the earlier one, so an answer can be changed at any time; an unclean end already recorded can be answered whether or not it was ever pending. The question is pending until its first answer. `togi status` and `togi watch` show every pending question with what togi saw, the four choices and the `togi day answer` command, and show an answered question's current answer.

`togi day answer <boot> <frozen|graphics|power-off|unsure>` needs no root shell. It connects to the day service's Unix socket `/run/togi/day.sock` and runs before the root, platform and journal checks of `togi day` itself; the service appends the answer. The socket lives in a root-owned directory that is not group or world writable. The service accepts root and users it identifies through `SO_PEERCRED`: peers whose primary group is the socket's group, and explicit members of that group, re-read from the account files on each connection of such a peer, so a user added to or removed from the group is accepted or refused from the next connection without restarting the service. Each request is one JSON line, `"questions"` or `{"answer":{"boot":"<boot>","answer":"<kind>"}}`, and each reply one JSON line: `{"questions":{"pending":[...]}}`, `"answered"` or `{"refused":{"reason":"..."}}`. The service serves one client per second, reads at most 4 KiB and times a client out after 250 ms. Without the day service running there is no socket and no answer; the client never writes the journal.

In a request, `answer` is the journal's wire name (`frozen`, `graphics`, `power_off`, `unsure`); the command line spells the third `power-off`.

`togi day notify` is the desktop notifier. It polls the socket every ten seconds and sends one notification per pending boot per process lifetime. It invokes the installed `notify-send` (libnotify), adding no notification library; a dismissed or expired notification answers nothing. When `XDG_CURRENT_DESKTOP` (colon-separated) contains `KDE`, it passes `--wait` with four `--action` flags and a 120-second expiry, and the chosen action is the answer. Other desktops get a plain notification naming the command; togi does not query the notification server's capabilities. The question stays in `status` and `watch` until answered.

The Day section of `status` appears when observations exist. It reports distinct boots observed, boots with clean and unclean ends, whether PID 1's hardware watchdog was armed at the newest observer check (`not recorded` when the newest start predates checking), checkpointed hours per exact read-back profile, and the last unclean end with its reset reason. Hours are a lower bound, truncated to three decimal places for display, and make no stability claim. A Day questions section follows when unclean ends exist: a pending question lists what togi saw, its reading, and the four choices with their commands; an answered one gives its current answer and the command that changes it. `watch` narrates the oldest pending question when no trial is in flight, and its footer counts pending questions on every view.

Day observation takes the nonblocking host lock, then the session writer lock, and holds both throughout its lifetime. Its read-only hardware capability borrows the host lock. This intentionally excludes `run`, `reset`, another day observer and other hardware-lock users, even in the same normal boot: stop the day service before tuning or resetting. Contention exits 3 before hardware access. `status`, `events` and `watch` continue reading without either lock.

`services.togi.day.enable` defaults to false. Enabled, `togi-day.service` runs `togi day --state-dir /var/lib/togi` as root in normal boots after local filesystems and kernel modules are ready, restarting after a failure with a 60-second delay. The tuning specialisation explicitly disables the option and has no day service. Normal-boot journald defaults to `Storage=persistent` and `SyncIntervalSec=5s` when day observation is enabled; the tuning boot retains its existing one-second sync policy. Shutdown uses the ordinary systemd stop ordering, so the service can append its final records before its state filesystem is unmounted.

`services.togi.day.users` (default none) names users, of any account type the configuration declares, who may answer without root: each joins the `togi` group, which owns `/run/togi` (mode 0750, created by tmpfiles so it outlives a service restart), and each gets the systemd user service `togi-day-notify` (`wantedBy`, `partOf` and `bindsTo` `graphical-session.target`, ordered after `graphical-session-pre.target` because ordering after `graphical-session.target` itself would form a cycle), running `togi day notify` with `libnotify` on its `PATH`, only for users on the list (an exact-list `ExecCondition`), and retrying every ten seconds (`Restart=on-failure`, `RestartSec=10`, no start limit) while the day service's socket is down. Group membership starts at the user's next login.

### Day watchdog

`services.togi.day.watchdog` defaults to false and takes effect only with day observation enabled in a normal boot. Opting in loads `sp5100_tco` in the initrd and sets PID 1's `RuntimeWatchdogSec=60s`; it adds no lockup-panic kernel parameters or sysctls. It neither changes the tuning boot's existing 30-second watchdog nor promises that a watchdog device is available on every platform. Daily observation does not apply offsets and does not itself require an armed watchdog; the day service that applies offsets applies them only with PID 1's watchdog armed.

**Armed.** PID 1's hardware watchdog is armed when PID 1 holds open at least one `/sys/class/watchdog/watchdog*` device that passes the preflight identity check and reports state `active`. When the driver exposes `timeleft`, it and `timeout` must be readable numeric values with `timeleft <= timeout`. An all-ones MMIO read or any reading greater than the timeout is **open but not counting**, not armed; a present but unreadable or malformed counter is also not armed. A driver without `timeleft` keeps the state-only answer; missing support is not a failed read of a present counter. A single plausible reading rules out the lost-decode failure, not every possible timer failure. PID 1 must hold `/dev/watchdogN` for `watchdogN` or the legacy `/dev/watchdog` node, which the kernel registers for `watchdog0` only, so systemd is what feeds it. Every such device is a candidate, not only the first. An inactive device is not armed, nor is an active hardware device while PID 1 feeds only a different one, such as the software watchdog. The day service records its initial check in `day.boot_start.watchdog` and checks again at every load-sampling tick (including the first scheduled tick after resume), at checkpoints and on stop. A changed result immediately triggers a checkpoint; every new checkpoint includes the latest `watchdog`, with the same `{"state":"armed"|"unarmed","detail":...}` shape. Older records may omit it; an older checkpoint preserves the preceding check. `togi_hardware::day::Observer::watchdog` is the live reading the applying service gates on; an unreadable `/proc/1/fd` is unarmed, with the cause in `detail`.

**Sleep.** The kernel and systemd do not stop a watchdog that userspace opened across sleep. The `sp5100_tco` driver has no suspend or resume callbacks and does not set `WDOG_NO_PING_ON_SUSPEND`, the only flag that makes the watchdog core register its power-management notifier, which pings once and stops the core's feeding worker. The core's worker does not feed a device userspace holds open, and PID 1 is frozen during every sleep, so nothing feeds the timer. systemd's sleep handling does not touch the watchdog. What the timer does while asleep is a chipset property that neither the driver nor systemd states:

- **s2idle** (suspend-to-idle, `freeze`): the platform stays in S0 and the chipset stays powered, so the timer is expected to keep counting and reset the machine 60 seconds after the last feed. This is inferred from the power state, not read from a kernel or vendor statement.
- **Suspend-to-RAM** (`deep`, `mem`): on SP5100 TCO with the `efch_mmio` layout, measured deep sleeps longer than 90 seconds caused no reset, with or without the pause unit. After waking, `state` remained `active` but `timeleft` was the all-ones value `4294967295`: timer MMIO no longer decoded. Reloading `sp5100_tco` restored counting. The driver has no resume callback to restore decoding; the resume unit therefore reloads it before re-arming. This measurement does not establish s2idle behavior.
- **Hibernation** (`disk`): userspace is frozen while the image is created and written, which can take longer than 60 seconds with the timer running; once the machine is off the timer cannot run. The boot that restores the image sets up PID 1's watchdog as in any normal boot.

With the option on, `togi-day-watchdog-sleep.service` (`WantedBy` and `Before` `sleep.target`, `StopWhenUnneeded`, `Type=oneshot`, `RemainAfterExit`) sets the manager's `RuntimeWatchdogUSec` to 0 over D-Bus (`busctl set-property`), which makes PID 1 disarm and close the device, before any suspend, hybrid sleep or hibernation that systemd starts. The pause stays for s2idle and the other modes whose timer behavior is unmeasured. When `sleep.target` stops after resume, the unit's `ExecStopPost` unloads and reloads `sp5100_tco`, then sets the property to `infinity`, dropping the override and re-arming the configured `RuntimeWatchdogSec`. systemd logs either module command's failure and continues to the re-arm command even when unloading or loading fails; a failed reload does not leave the manager's override at 0. The restore is `ExecStopPost`, which also runs after a failed start: PID 1 may have applied the 0 before `busctl` failed, and restoring the configured value is still required. Limits: a sleep written straight to `/sys/power/state` bypasses `sleep.target`; disarming and unloading can fail with `CONFIG_WATCHDOG_NOWAYOUT` or `nowayout=1`; a failed reload may leave a noncounting watchdog, and a failed D-Bus restore is reported by systemd; between resume and restoration the machine is unprotected. The unit exists only with the option, so never in the tuning boot.

Each module command runs under `timeout --verbose --kill-after=2s 5s`: a stalled command receives TERM after five seconds and KILL two seconds later. Both commands therefore finish within fourteen seconds in total, leaving time to restore PID 1's watchdog before the unit's explicit thirty-second `TimeoutStopSec`. Ignoring a module command's exit status alone would not suffice: systemd skips subsequent stop commands when the unit's own stop timeout expires.

The modes a machine offers are in `/sys/power/state` and `/sys/power/mem_sleep` (the bracketed entry is what `mem` uses), and `/sys/power/disk` reads `[disabled]` when hibernation is unavailable. Hardware acceptance must check both that a sleep longer than 90 seconds resumes without a reset and that `timeleft` counts down again afterward. Deep SP5100 recovery and untested s2idle acceptance remain tracked in [#1223](https://github.com/shgew/togi/issues/1223).

**Classification.** A watchdog reset whose crashed boot ended at a suspend or hibernation entry is classified as sleep-related ([Day observation](#day-observation)), not as a CPU hang. With the unit working it should not occur, so it points at a sleep that bypassed the unit or at a timer that was armed again too early.

Needs no root, state directory or configuration. The scripts are generated from the clap definition, so they offer every command with its summary where the shell shows summaries, each command's own flags (`--name`, plus `-h` and `-V` where they exist), directories for `--state-dir`, files for `--config` and `--tuning-boot`, and the shell names for `completion`; `--config` only for `doctor`, `run` and `reset`. Once `events` exists ([#826](https://github.com/shgew/togi/issues/826)), `events --kind` completes the comma-separated kinds and groups (the item after the last comma, in bash, zsh and fish; only the bash script is run by a test, zsh and fish are pinned by assertions on the script); clap's static generators complete one whole value and cannot split on the comma, so #826 adds that completion itself; nushell's completers take no arguments, so there `--kind` completes one kind or group and not the items after a comma. Bash completes a flag's value only after a space (`--state-dir <TAB>`); after `=` (`--state-dir=<TAB>`) it offers flags, as clap's generated bash script does. `events`' other value flags (`--core`, `--trial`, `--since`, `--until`) offer nothing, not file names; other values get no completion. The nushell script was loaded with nushell 0.115.1. The Nix package installs all four scripts (end of [NixOS module](#nixos-module)). |

`doctor` also validates the online cores with the same tuner topology constructor as `Session::open`, with or without root. A topology the tuner cannot work on, including more than three CCDs, adds a failed `topology` check saying it is not supported and exits 15 instead of reporting ready.

### Dashboard

The dashboard has one page, plus help (`?`) and journal (`l`) views; `Esc` returns to the dashboard.

The Wide size class requires at least 200 columns and 60 rows; Medium requires at least 150 columns and 40 rows; smaller screens use Compact. At 240x67 the two CCD tables and lower panels sit side by side, with a two-row trial bar and large remaining-time digits. The supported 160x45 Medium dashboard keeps the tables side by side and the countdown inline; Compact shortens narration and lower panels while retaining core offsets. Panels remain within their measured rectangles; excess context ends with `+N more`. A line that does not fit never cuts inside a value or a word: it first shortens or leaves out whole clauses, lowest priority first, and keeps what it names (a core, an offset, a count, the loaded or next core), in a short form such as a bare offset when its label does not fit; text that must still be cut keeps the words that fit and ends with `...`, the ASCII form of an ellipsis, or shows nothing when not even one word fits. All dashboard text fitting uses this same rule; only gauges and rule dashes are clipped by cell, so a help example's gauge shortens first and its failure point, state word or offset are left out whole, never cut, only when even an empty gauge leaves no room. Labels and values keep at least one cell gap. Footer hints shorten labels before leaving out keys, retaining all four keys at 20 columns and wider on the main, help and journal views; below that, `q`, labelled `exit dashboard` and shortened to `exit`, is the last key left out and is shown whole whenever one footer cell fits. With `--tuning-boot` there is no `q` hint at all: the footer keeps the other three keys by the same rule, and the help's top-line section has no `q` row. Active and current-view styling stays the same in the shortened forms. Help uses three columns on wide screens and one scrolling column otherwise; it explains the screen's glyphs, colours and terms and links [the tuner specification](tuner.md) for the rules the tuner decides by. The journal view follows the end until scrolled.

The fitting rule uses a one-cell `…` cut mark in the rich profile and the three-cell ASCII `...` otherwise. Widths count display cells, including Unicode wide characters; fitting never splits a value or word to make room for the mark.

Live trial states never move a panel: while a trial runs, ends, waits for the tuner's next intent and is prepared, every panel keeps its rectangle on every screen size. Between trials the trial bar's slot holds the between-trials band, which shows the last result and the next trial and no countdown, and the outcome lines keep the outcomes of the trial that just ended until the next trial's intent is recorded. Stopped, dead-end and recovery layouts may differ: their bands take the rows they need and the outcome lines give theirs up.

The journal view lists the newest 400 journal events, oldest first, without `smu.intent`, `smu.write`, `smu.readback` and `preflight.check` events; its rule says how many events the journal holds that it lists, and `togi events` lists them all. A view scrolled back stays on the entries it shows: events that arrive meanwhile do not enter the list, so no row moves, and the hint line counts them. Scrolling to the end shows the newest events again; leaving the view and reopening it does too. Removing, replacing or truncating the journal, or a journal read failure, discards the held list; once a readable journal is available, the view shows its entries rather than retaining the previous journal's rows. WHAT HAPPENED keeps the newest 200 of the lines the journal folds into it. When lines are left out, whether they do not fit the panel or are older than those 200, its last row reads `+N more` with N the number left out, and its rule says `l: last 400 events`.

At Medium, WHAT HAPPENED reserves the failure result and its decisive attribution (`no core named` or the named core after `wrong result`) before fitting trial position, temperature or other context. HUNT's cause and evidence rows likewise reserve attribution and its uncertainty (`not enough to attribute`) before trial placement and sample timing. TURNS descriptions and explanatory HUNT prose use shorter wording rather than wider panels. WHAT HAPPENED summarizes `checking.chain` with its cycle, step, CCD and partial loaded cores, or the end of that CCD's partial chain; the full recorded request groups, provenance and profile remain in the journal view and `togi events`. Intentional clause short forms, the omitted Medium workload column and `+N more` remain density choices, not a font workaround.

The stage line names the phase: `SOLO LIMITS`, `PHASE 1`, `PHASE 2` (its round, or `confirmation cycle`, with the most rounds left if none fails) and `CLEAN CYCLES`. A `BIOS PROFILE` panel lists the profile to enter, one row per CCD in slot order, with `*` on each unconfirmed offset and a rule that reads `confirmed by the cycle ending #N` or `UNCONFIRMED since #N · cores …`, where `#N` is the number of the journal event; before phase 1's first passed cycle it says that no profile is confirmed yet. During phase 2 the context opens with `N rounds left if none fails, then one full cycle` and lists each candidate with its offset, solo limit and remaining gap. A core's solo limit is the offset it passed alone, not the margin one count shallower that phase 1 checks from.

Help shows a scrollbar whenever its contents need scrolling, in both its one-column and three-column layouts. Section spacing separates content; scrolling to the end reaches the last text row, not trailing blank content rows.

The help explains the screen's terms: what each stage shows, the glyphs and colours, the state words and the load kinds. It decides nothing and states no threshold, count, order or condition the tuner works by; it links the tuner specification ([`tuner.md`](tuner.md)) for those, as the plain-text URL `https://github.com/shgew/togi/blob/main/docs/spec/tuner.md`.

Narration never contradicts the journal. Before the first trial (preflight, readback, or a session seeded from carried evidence) the between-trials band shows no last result and says that no trial has run yet. A search turn whose light and heavy confirmation passes are complete says it records the solo limit, not another confirmation trial. After the session stopped, the stage line marks no stage as running (`○` for a stage still open, `■` for a finished one) and drops `repeats until stopped`. A session whose journal ends on an unfinished trial is narrated by what the journal shows after it. When a later event carries a different boot id than the trial's own, that boot ended for every regime, R6 included: the NOW band, the stage line (no running marker, no countdown) and the narration say the trial crashed and that `togi run` records it, even when only its intent was recorded. An earlier trial's recovery or a clean shutdown on the later boot does not hide that unfinished trial's crash. Recovery remains visible while a next trial is prepared on the same boot, until that trial starts. For a started non-R6 trial with no later-boot event and no recorded end, once its planned end has passed the countdown shows how long it is past its end (`0:42 past its end`). The narration says no trial end is recorded, not that nothing has been recorded since: same-boot progress can arrive during teardown. It claims no crash, because the trial's deadline or the watchdog may still be running, and the clock keeps ticking in live `watch`. A journal that exists but cannot be read, whether damaged or of another schema, is a state of its own: the header says `can't read journal` and the narration `can't read journal: <reason>`; live `watch` adds that it retries when the journal changes, and one-frame `watch` leaves that promise out. `no session yet` is for a journal that does not exist.

The dashboard's stopped state begins at `shutdown` and ends only at the next `config.loaded`: no other event reopens it, including a `command.reset` queued after the shutdown and a trailing `session.warning`. A reset queued after the stop stays queued for the next run, and no panel claims the session is running. A stopped cycle checklist draws `○` for its open current step, never `►`, and names no trial in progress.

The `can't read journal` state does not cover a journal whose first line is not a complete header of this build (another build's journal, or a header of this build torn before its first newline): `watch` refuses it before drawing, live or one-frame, as [Reset and compatibility](#reset-and-compatibility) says.

The live dashboard redraws when the journal changes, when a key is pressed, when the terminal is resized, and once a second for the clock outside idle trials. During a started R6 (idle) trial, live `watch`, one-frame `watch` and replay all show the same frozen planned-end frame instead of a clock, countdown or elapsed-past-end updates. Advancing time alone never changes that frame, even past the planned end while the trial has no recorded end. Live `watch` holds still until the journal changes, a key is pressed or the terminal is resized; on Linux the live loop arms no ticker, timer or journal polling for it, so duration updates do not wake idle cores during the measured workload. Later-boot evidence removes the quiet hold; an unfinished R6 trial then follows the same crash and recovery rules as every other regime. Linux detects journal changes with filesystem notifications; platforms without journal notifications check the journal once a second. Between trials the band shows the last result and the tuner's next trial, or `deciding` when a hardware read is needed. Recovery, stopped and dead-end bands explain their respective states; a recovery band places the crashed trial in the step it ran in, even after a backoff moved the cycle on. After offsets are restored, core rows explicitly show the saved profile rather than claiming it is applied now.

Checking's clean-cycle goal requires every step and every R7 part, partials included, to pass. Multi-core R7 failures are not tolerated: they follow a [located hunt](tuner.md#hunt) when required, then [voltage-targeted backoff](tuner.md#r7-voltage-targeted-backoff) if the failure stays with the loaded cores. Narration, context and history explain the backoff and the next partial's loaded cores and request-order provenance. Until each CCD's partial chain has a recorded ending, the cycle checklist counts an R7 step's parts as `N+` and ends its part list with `partials may follow`. Deepening's alone R1 and R2 checks are narrated and labelled as phase 2 checks of their round, not as solo-limit search.

The NOW band's `N/M` counts credited passes in the current part: each short or long quota contributes at most its required count. Surplus short passes never substitute for a long pass; three short passes against a three-short, one-long part show `3/4` until the long trial passes. `togi status`'s PASS EVIDENCE column retains the surplus evidence.

`watch` reads the journal without taking the lock; while `events.jsonl` does not exist yet, Linux watches the state directory for it, and checks once a second only when neither that directory nor the journal can be watched. On a terminal it clears the screen once and never scrolls it: it writes neither the last row nor the last column, and a resize or a view change clears and repaints the whole screen. It hides the cursor and restores it on SIGINT, SIGTERM or SIGHUP, and redraws on SIGWINCH. With `TERM=linux`, unless colour is off (`NO_COLOR` or journald), it redefines the console's 16 colours for the dashboard and restores them on exit. Every console-profile glyph is in IBM437, the character set of the kernel's built-in console fonts; unsupported text is transliterated or visibly escaped. Other terminals advertising `COLORTERM=truecolor` or `COLORTERM=24bit` use the rich profile: the exact same console-palette RGB values are emitted as truecolour foregrounds and backgrounds, without redefining any terminal palette. Rich rendering preserves Unicode text while still visibly escaping control characters. Neither profile uses bold. `TERM=linux` always takes precedence over the truecolour advertisement; `NO_COLOR` and journald keep unstyled, console-compatible rendering. Without a terminal it prints one frame of `--width` by `--height` (default 240 by 67, each 1 to 1000; a value beyond is a usage error, exit 2) without styling and exits. Other terminals without the truecolour advertisement keep the named-slot, console-compatible rendering. No journal shows "no session yet".

Console core gauges draw applied depth and the solo failure segment with the same lower-half `▄` block, the latter red; failed hunt-group offsets use a distinct red `▀`. Rich core gauges use lower-three-quarter `▆` blocks for applied depth and the red solo failure segment, and red `┆` for failed hunt-group offsets. Applied depth is white when judged and grey otherwise. Both profiles retain grey `·` cells for recorded proven depth not applied now and magenta `░` for combination-held depth. Wide and supported 160x45 Medium use 50 gauge cells, one count per cell, so odd and even failure depths have exact positions. Medium starts its gauge at column 20 of the CCD table, uses a four-column right-aligned failure value at column 71, moves the brief loaded/idle role beside the CCD name, and omits per-core right notes; the R7 top-requester lists still name those cores. Compact uses this same dense geometry when its CCD table is at least 75 cells wide, otherwise its existing 25-cell geometry with the active profile's glyph shapes. Help shows the active profile's glyphs and their meanings.

Trial bars use `█` cells for elapsed time and `░` for the remaining track: one full-height row on Compact and Medium, exactly two full-height rows on Wide. The row below the Wide bar remains blank across the bar's width, without moving the countdown or other panels. The filled and unfilled parts have the same height, with no half-height underline in either profile. A frame without colour (`NO_COLOR`, or one frame of `watch`) still shows elapsed time by shape; the quiet R6 bar is all `░`. Rich trial bars use eighth-block leading edges for sub-cell precision. These are spatial rendering changes only: no gradients, animation or faster redraw timers.

Loaded and judged are independent: parked-trial group members remain judged even when idle or equal to parked offsets. R7 partial checking parts are ordinary decision evidence. Failure counters count `failure` decisions, including skips of already-failed trials; the last observed failure excludes those skips. Crash counters count boots that ended without a clean shutdown.

An offset with no hardware readback is unknown: its core row shows `?` and no applied-depth fill, never the tuning profile or an invented zero. After a stopped run restores the hardware, the rows instead show its saved tuning profile as labelled.

The header's two durations answer different questions. The session age is the time since `session.start`. The tuning time is the time togi ran in the session, folded one event at a time, never from a rescan of the history. A run starts at a `config.loaded` and spans its crash reboots until a `shutdown` or a dead end, the grouping `just stats` shows in its Runs table, so the time a crash reboot takes counts and the time between a clean shutdown and the next run does not. A `config.loaded` in the boot of the run's latest one restarts the run without a shutdown: the silence before it belongs to no run, including the silence before the `mce` and `boot.leave_reason` events a starting session records ahead of its `config.loaded`; the journal cannot tell those from the `mce` a stopping session records before its `shutdown`, so a run killed after that `mce` and restarted in the same boot also loses the time up to it. On a later boot those events and the first `config.loaded` belong to the crash recovery and count at most 30 minutes together. A `command.reset` is recorded outside any run, so it neither ends a run, nor moves its last event, nor renews the recovery limit. A gap inside one boot counts whole, since an idle trial or a retry wait is silent for as long as it lasts. A gap between two boots of one run, a crash reboot, counts at most 30 minutes, the longest wait a live run schedules on its own (a backend's third retry); the crash reboots in the long target-machine session this limit was chosen from took 52 to 157 seconds. The limit keeps a run left crashed and resumed days later from crediting all the days between, and it also caps what a run with no recorded end adds beyond its last event, because an open run may be a crashed machine waiting for its recovery. Both durations stop at a dead end and at a stop, and a frozen R6 (idle) frame shows both as of the trial's start, so neither clock moves on a frame that holds still.

On a narrow header neither duration is ever left out. The idle trial's pause notice beside the clock leaves before the long labels `tuning` and `session` shorten to `tune` and `age`, and those shorten before the words after the failure and crash counts do.

A hunt's part numbers describe its current split, not a fixed total for the hunt: later splits depend on the preceding evidence. When the hunt cuts another split, its stage line and running-trial heading explicitly say `re-cut N`, counting re-cuts from one. Parts and their complements at the same candidate set, granularity and trial length belong to the same split.

Search forecasts distinguish the core's next search turn from the session's next trial: `if it passes: core 08 searches -5 on its next turn; next trial: R1 light, core 01 alone at 0`. A forecast's search offset is not the offset or target of that next trial.

The hunt panel states each core's offset as the hunt's recorded profiles set it, never as one parked-at-zero claim over every other core. A core is parked at 0 when its parked offset is 0; a core whose parked offset equals its nonzero failing offset is held at its failing offset (it is not a candidate, as the loaded cores of a located hunt) or kept at it (it is a candidate); any other nonzero parked offset is shown with its offset. The parts table's parked column lists only cores parked at 0 or at a nonzero shallower offset and reads `parked at 0` only when every listed core is at 0; held and kept cores, and cores parked at a nonzero offset, appear in an `others` row (`held at failing offsets`, `kept at failing offsets`, `parked at N`). Narration says the rest are `parked at 0` only under the same condition, and before the hunt's profiles are recorded it says only `parked`.

Forecasts preserve uncertainty: a ranking read without a recorded ranking, or hunt history the replay cannot complete, may prevent the tuner from naming the next trial. A running multi-core R7 trial's conclusive forecasts assume its end supplies no new request or clock telemetry; they use the tuner's fallback to earlier recorded measurements or offset order. New telemetry can change top requesters, backoff targets and partial derivations, so those folded outcomes are conditional, not guaranteed: outcome lines end their backoff or derived partial `per earlier requests`, or `per offset order` when no measurement of the running load or its CCD's full part covers a loaded core, or the partial was derived from offsets, and compact screens say so once after the outcomes. A multi-core R7 trial's named-failure outcomes say what the named core is: a core away from 0, a core at 0 that is no top requester (naming its CCD when cores at 0 on different CCDs move different groups), or a top requester at 0; when the band has too few rows, the cores at 0 become exceptions on the line of the cores away from 0. The dashboard never estimates an overall completion time. The clean-cycle count is credit still valid for the current profile; a schedule change alone does not erase it. Raw journal formatting is bounded to the newest 400 eligible events.

The tuner exposes owned dashboard projections and read-only queries from its incrementally folded state; queries do not replay an event list or advance tuning. Forecasts are empty until every core has a phase, and after `shutdown` or `deadend`, including when a trailing `session.warning` records a stop-time error. A new `config.loaded` reopens the session's forecast. A crashed flight is forecast as between trials. An all-pass forecast reports the number of hypothetical passes actually folded within the running trial's stored requirement; if uncertainty stops it early, it does not claim the remaining passes occurred. A next trial from a different requirement omits that all-pass premise.

The dashboard model owns batched folding and outcome retention. A batch keeps only its last trial end's pre-end outcome context; a batch with no trial end keeps the previous context until the next trial intent, a stop or a new session makes it inapplicable. Folding a batch and folding its events individually leave the same visible frame.

When stdin and stderr are both terminals (the same check) and `--no-tui` is not given, `run` draws the `watch` dashboard on stderr from the moment the session starts until it stops, including the restore after a signal. Event lines are not printed while the dashboard is up; `events.jsonl` still records every event. Output before the session starts, such as a refused configuration, prints as usual. While the dashboard shows, `run` turns off the terminal's echo and line buffering but not its signal keys, so typed keys neither print over the frame nor scroll it and Ctrl-C still stops `run`; `run`'s dashboard takes no keys, and the previous settings return when the dashboard stops, however it stops. A defect prompt clears the dashboard, asks, then redraws it. When the session stops, `run` clears the screen and prints the outcome: after a clean stop, the closing `profile.restored` line, when the run restored offsets, and the `shutdown` line; otherwise what it prints without the dashboard, the dead end and its evidence, or the error. If the dashboard cannot draw, `run` prints why and falls back to event lines. Without terminals, as under systemd, it prints event lines.

`run` keeps its own SIGINT, SIGTERM and SIGHUP listener from before the host lock until the process exits, because the dashboard's signal registrations last for the rest of the process and never restore a disposition: Ctrl-C reaches that listener whether the dashboard is showing, closed or failed, and stops the session as on any SIGINT. `run` opens the journal before showing the dashboard. Until the journal records an event after the last one present at startup, the dashboard says `STARTING`, not the earlier run's stopped frame or an empty-journal invitation to start a run. Its deferred dashboard owner cancels and joins the dashboard on every exit, including a session panic, so the cursor, Linux-console palette and input settings are restored before the original panic propagates.

The clean-stop summary prints exactly the closing events the dashboard kept off the screen, each once and in journal order: the `profile.restored` and the `shutdown` of this stop. A `profile.restored` is the stop's own only if nothing but the closing sequence's own events follows it (`session.warning` events, the `mce` events the shutdown's kernel-log read records, then the `shutdown`): the restoration of a same-boot resume at its startup, which work follows, is not repeated, and no closing line of an earlier run ever is. A closing line already printed live, because the dashboard had given way to event lines, is not printed again, so when it gave way between the two, the summary's `profile.restored` line follows the live `shutdown` line.

### Status

`status` shows each core's current `OFFSET`, not its checked solo limit, and the profile to enter in BIOS in the `BIOS` column: the last confirmed profile with every later step-back applied and every valid held failure shown stepped back ([BIOS profile](tuner.md#bios-profile)). A `*` marks an unconfirmed offset, a note under the table names the cores and the passed full cycle that last confirmed the profile, and the column and note read `-` and `none confirmed yet` until phase 1's first passed cycle. In phase 2 `status` lists the candidates (`CANDIDATE OFFSET SOLO GAP STATE`, `SOLO` the offset the core passed alone) and the worst case if no round fails: the most rounds left, then one full cycle ([Phase 2](tuner.md#phase-2)). It estimates nothing through future failures. `PHASE` shows the dashboard's state word for the core's phase: `SEARCH`, `HAS ROOM` or `AT LIMIT`. `CCD` comes from the recorded core topology and `SLOT` is the core number modulo 8; per-core access requires full CCDs (`Preflight`). Enter the `BIOS` column in the BIOS per-core Curve Optimizer controls, matching each row by CCD and slot. Board labels vary: confirm every row before saving and stop if the labels cannot be reconciled.

`status` and the dashboard name each core's self-sufficiency separately for every R7 workload: an observed passing trial as top requester at equal or deeper offsets since its latest reset, not a guarantee against future failures. They name the current top requester(s) for each CCD and workload using the current profile's request order, with ties included; absent measurements explicitly use offsets as a fallback. Unknown evidence says not yet demonstrated, never claims stability from another core supplying the voltage ([ADR 0038](../adr/0038-self-sufficient-cores.md)). `status` lists every core and workload under `R7 self-sufficiency`. Once checking has a cycle, the dashboard's context panel ends with an `R7` rule and one line per workload: its top requesters (`by offset` when offsets stand in, kept when the core list is cut, which cuts measured cores first) and its self-sufficient cores, or their count when the list does not fit, cut with `...`. Requester lists retain whole core IDs and ranges; a list with no fitting word is omitted rather than shown as a bare marker. Narrow rows leave out self-sufficiency first and shorten the workload column to retain `by offset` whenever that provenance fits. The rows above the `R7` rule end with `+N more` when they do not all fit, unless that row would push out the running part; the CCD tables mark the top requesters of the running or current R7 workload `top`.

### Reset and compatibility

`reset` reads the journal before it opens it: no journal or no session exits 1 without creating state files, except that `reset --all` completes an interrupted incompatible archive when the journal has already moved and its pending marker remains, and drops a pending carry. Every successful `--all` path establishes a permanent `archive/<session-id>-reset-all` boundary under the writer lock before changing its sources, including pending-carry drops, recovered moves and incompatible schemas. Later transitions cannot reuse facts, candidate solo limits or failure points from that boundary or an older source, even if the reset could not append `command.reset` to a journal. New session IDs sort after the boundary, including when the wall clock moves backwards. A core that is not in the session exits 2, and contention on the host or state-directory lock exits 3. `reset --core` records its event in the host's current boot and appends nothing else, no `shutdown`, so a crashed tuning boot stays visible to the next crash recovery (`journal.md`, Reset commands).

A session written by a newer ruleset, schema or evidence epoch is refused before another event is appended, even if another dimension is older. `run` checks the journal's build stamp before validating the configuration, so a newer journal still exits 16 when this build also rejects the config file. It reports the writing build's version and advice to install it or run `reset --all`; `reset` and `doctor` take that build from the journal's first line (`session.start`), not from the latest `config.loaded`, since any build that resumed the session had its schema, ruleset and evidence epoch. A session written by an older ruleset, schema or evidence epoch, and by no newer one, is not refused by `run`: after reading the configuration, `run` archives it and starts a new session seeded from it (`journal.md`, Transitions; `tuner.md`, Session start), in a tuning boot too. An epoch-only increase archives the live older-epoch journal under the same transition protocol: the new session keeps eligible same-BIOS failures and only passes whose original epoch equals its current epoch. The epoch is `session.start.build.evidence`, which every build stamp carries; no schema or ruleset increase is required. `reset --core` refuses any of these mismatches, and its message for an older journal names that transition. `status` and `events` (including `events --json`) warn to stderr before rendering a different ruleset with this build's rules, but refuse a different schema with a red bold line (journald priority 3). `watch` renders a different ruleset without a warning and shows a different schema's refusal on screen in place of the session. `reset --all` works for any of these mismatches; a schema mismatch archives without appending to the old journal. `reset --all` also drops a pending carry under the writer lock, exiting 3 while a `run` holds it, so the next session starts over with nothing carried; when the transition has archived the journal and no new one exists yet, it prints `carry from session <id> dropped; the next togi run starts a new session with nothing carried`.

Unknown event kinds and unknown event fields do not block `run` from transitioning an older-ruleset, older-schema or older-epoch journal: it archives without appending and derives carry from known events only. A current-ruleset, current-schema, current-epoch journal with unknown kinds or fields is refused with the kind (and the field's path, for a field) and both build stamps, exit 16. `reset --core` and same-schema `reset --all` refuse a journal holding unknown kinds or fields whatever its ruleset or epoch, exit 16, because they append `command.reset` (and, for `--all`, `session.archived`), and leave the journal and any pending carry untouched; a different-schema `reset --all` archives without appending. Read-only commands read such a journal leniently and say what they skipped ([journal.md](journal.md), decoding rules).

A journal whose first line is not a complete header of this build, in practice the Go build's, is refused by `run`, `status`, `events` and `watch` alike. The check reads the first line of `events.jsonl` and nothing else: a first line that is not a header of this build's journal, meaning anything nonempty that does not decode as a `session.start` envelope with `data.build` (Go's flat envelope, malformed JSON, another kind first, a missing build), makes the journal foreign, and so does one that is unterminated, such as truncated JSON at the end of the file with no newline. The refusal cannot tell another build's journal from a header torn by a crash before its first newline, so it does not claim the journal is Go's: the error names the `events.jsonl` file, says the first line is not a complete header of this build, that it is either another build's journal or a header torn by a crash, and points at [Go to Rust cutover](../howto.md#go-to-rust-cutover), which covers both cases. An unterminated non-header first line is never treated as a torn tail, repaired or truncated, and nothing repairs an incomplete first header automatically: the operator keeps the file aside by the procedure there. A first line that decodes as a complete header but has no newline is not foreign; it stays the torn first line of [journal.md](journal.md#rules). A header that does decode is judged by the build rules above, so a newer build's header with additive fields keeps its own refusal. Every command exits 1, the ordinary exit for an unreadable journal, not the 16 of a newer build. The refusal comes before anything is decoded past that line, before the state-directory writer lock and the host lock, before any GRUB write (a tuning-boot `run` leaves the saved entry and the leave reason alone) and before any state mutation: no file is created, moved, archived, rewritten or removed, including `state.json`, `archive/` and the journal itself, and `run` makes no `config.loaded` or other append. `run` still checks the platform first, as above. Live `watch` is not the dashboard exception here: it prints the error to stderr and exits 1 instead of drawing a `can't read journal` frame and waiting for the journal to change, with or without a terminal and in one frame or live, because the journal does not become readable by retrying. A missing or empty journal is unchanged. The operator moves the Go state directory aside before the first Rust boot; nothing in togi reads, archives or translates it ([Event format](journal.md#event-format)).

### Run recovery

At each hardware boot, `run` replays the complete journal before checking the verified full-state snapshot. A stale, changed, other-build or mismatching `state.json` is rebuilt and recorded as `state.rebuilt`; cached reducers never authorize hardware actions. Publication still follows every append. Read-only current-state consumers (`status`, watch and forecast premises, reset warnings, bench metrics and forecast tools) restore the same-build snapshot and fold its tail, falling back to full replay without modifying the cache. Historical scans, independent auditing and forecasts anchored before the snapshot still read their required journal history. See [State file](journal.md#state-file).

On resume, `run` checks historical decisions for known defects before queued resets and other tuning decisions are consumed. It records `defect.found` once per defect per session, naming affected cores and decision sequences. A too-cautious finding allows checking to continue; `status` shows each affected core's exact reset command until that core is reset. If stdin and stderr are both terminals (verified by a terminal ioctl, not merely character devices), `run` prints the finding and asks `Reset cores 3, 7? [y/N]`; only `y` or `yes`, case-insensitive after trimming a complete input line, records a durable yes `defect.answered` first, then queues ordinary `command.reset` events for those cores, each citing that answer, before tuning resumes. A later resume completes only the answer's missing per-core resets without prompting again. The prompt discards input typed before it appears, so only an answer typed after the question counts, and Ctrl-C at the prompt stops `run` as it does elsewhere, without waiting for Enter, recording no answer. EOF without a newline, read errors and other answers count as no: they record the answer and continue without resets. Either answer suppresses the prompt on later runs, but does not hide remaining reset guidance from `status`. Without a terminal there is no prompt: a too-cautious defect continues, whereas an unanswered too-aggressive defect stops as a journaled `defect` dead end (exit 17).

Recovery-time kernel-log read errors retry at waits of 60, 300 and 1800 seconds. A transient backend setup error makes its trial inconclusive and counts toward the backend's streak: after a backend has `dead_ends.inconclusive_in_a_row` consecutive inconclusive trials, setup errors included, the next three trials for that backend wait 60, 300 and 1800 seconds respectively. `backend.retry` records backend (or `kernel_log`), attempt, wait and cause. If all three are inconclusive too, `no_evidence` fires at `dead_ends.inconclusive_in_a_row + 3` consecutive inconclusive trials. Interruptions during the wait resume without treating the delay as trial evidence; a stop signal during either wait records `shutdown` and exits 0. A missing backend binary is not a transient setup error: it ends as `no_evidence` rather than waiting through retries. A computation error reported just before a crash remains failure evidence even if no `trial.end` was written.

`run` needs Linux. On any other platform it prints `togi run: hardware runs need Linux: unsupported operation` and exits 1 first, before it reads the journal, the configuration or the boot id, takes the journal or host lock, or makes any check. On Linux the order is then: what reading alone decides, with no lock held (the journal's compatibility, judged from its first line, so a newer schema, ruleset or evidence epoch, or an unknown event kind in a current journal, exits 16 before the configuration is read and appends nothing, taking the host lock first only in a tuning boot, where the refusal clears the boot entry; then the configuration, exit 2), the process's signal listener, the host lock (exit 3), the journal's lock (exit 3), in that order, as `reset` takes them, the journal's compatibility again under both locks, which is the verdict that counts if another writer changed the journal in between, the boot id, the hardware, the carry, a new session's topology (exit 15, see [Preflight](#preflight)) and the session. Every exit before the session returns before any offset is written.

Simulation is not part of `togi`: development programs live in `tools/` and are not installed ([ADR 0010](../adr/0010-development-programs-in-tools.md)). [Simulating](../simulating.md) describes `tools/sim`.

### Shared flags

`--state-dir <path>` (default `/var/lib/togi`) is shared by every command and accepted before or after the command name. `--config <path>` (default `/etc/togi/config.json`) is accepted before or after the command name only for `doctor`, `run` and `reset`. `status`, `events` and `watch` reject an explicit `--config`, before or after the command name, with the usage error `--config applies only to doctor, run and reset` (exit 2); so do `completion` and `restart-limit`, and so does `--config` without a command, even with `--help` or `--version`.

Top-level-only `togi --version` (or `-V`) prints `togi x.y.z+rev` to stdout and exits 0; `--version` after a command is an unexpected-argument usage error (exit 2). The version is read from root `version.txt` by the `togi-version` crate and the flake. The package's revision is the `TOGI_REV` environment variable at build time, which the flake's `packages.default` sets from the flake revision: the short commit, with `-dirty` for a dirty tree, or `dev`. Without `TOGI_REV`, or with it empty, the revision is `dev`, as in every local cargo build. Cargo records no commit, so a local build never reports one, dirty or not.

`togi` without a command prints the wordmark and the tagline `per-core Curve Optimizer` above clap's help, to stderr, and exits 2; so does `togi` with only `--state-dir` (`togi --state-dir /x`), whereas `--config` without a command is the scope error above. `--help` (`-h`) prints the help to stdout and exits 0. An unknown command or flag, a missing or invalid value and every other parse error print clap's error and a usage hint to stderr and exit 2, with nothing on stdout. The top-level help holds the description, the usage, the commands (with clap's `help`), the options (`--state-dir`, `--help`, `--version`) and examples.

`togi <command> --help` (or `togi help <command>`) prints the command's description, usage, arguments, options and examples to stdout and exits 0; `-h` prints the short form. The options are the command's own flags and the shared `--state-dir`, never `--version`. Only `doctor`, `run` and `reset` list `--config`. A parse error prints clap's message to stderr and exits 2. Flags show in their `--long` form, with the short form where one exists (`-h`, `-V`). Examples read as a table: every description starts in one column per block.

## Exit codes

| Code | Meaning |
|---|---|
| 0 | Stopped cleanly: by signal, after the requested clean cycles, or at the first result |
| 1 | Error |
| 2 | Usage or configuration error, including a start offset for a core that does not exist; also a panic, which prints a `panic:` line |
| 3 | The host lock or journal is held by another writer |
| 10 | Dead end `failure_at_zero` |
| 11 | Dead end `smu` |
| 12 | Dead end `no_evidence` |
| 13 | Dead end `boot_loop` |
| 14 | Dead end `containment` |
| 15 | Dead end `preflight`, or a topology the tuner cannot work on, refused before a session starts; for `doctor`, a check whose failure would make it |
| 16 | Dead end: journal schema, ruleset or evidence epoch newer than this build's, or, for `reset --core`, different from it; an event kind or field this build does not know in a current journal (current schema, ruleset and epoch) for `run` and `doctor`, or in any same-schema journal for `reset --core` and `reset --all` |
| 17 | Dead end `defect`: an unanswered too-aggressive defect without a terminal |
| 18 | Dead end `thermal_trip` |

Read-only commands (`status`, `events` and one-frame `watch`) exit 2 for usage errors and 1 for an unreadable or incompatible journal, with the error on stderr. A valid query with no results exits 0 with empty stdout. `watch` is the dashboard exception: without a terminal it still prints a problem frame on stdout before exiting 1, and a missing journal prints `no session yet` and exits 0 with empty stderr. Live `watch` keeps displaying journal problems in the dashboard without exiting. A journal written by another build is none of those problems: all four commands exit 1 with the error on stderr, live `watch` included, and `watch` prints no problem frame (see above). A readable journal with a different ruleset remains a warning for `status` and `events`, as described above.

`doctor` exits 0 when no check failed, with or without root, warnings included (an inactive watchdog or a changed BIOS context); 15 when a check failed; 16 for a refused journal, as `run`; 3 when another togi process holds the host lock; 2 for a configuration error; and 1 for an unreadable journal, a failure to read the BIOS context or a platform other than Linux.

`events --kind` accepts comma-separated known exact kinds and known undotted groups from the binary's kind registry. Each explicit occurrence must contain at least one name after trimming whitespace and ignoring empty entries. An unknown name or an explicitly empty list is a usage error (exit 2), with the error and valid names on stderr, before reading the journal. Omitted `--kind` applies no kind filter. A valid filter with no matches exits 0 with empty stdout.

`status`, `events` and `watch` read the journal leniently ([#877](https://github.com/shgew/togi/issues/877); decoding rules in [journal.md](journal.md#event-format)). An event of a kind this build does not know is skipped, whatever the `--kind` filter, so `events` never prints it; an unknown field at any depth is ignored; every other defect stays an error (exit 1 for the commands, a problem frame for `watch`), except that a first line that is not a complete header of this build is refused before any decoding, in lenient mode too, and `watch` prints no frame for it (see Reset and compatibility above). `status` and `events` print one line to stderr after their output, `togi <command>: ` followed by the journal crate's report (`skipped 1 event of a kind this build does not know (future.thing at line 3)`, and `ignored unknown fields: ...`), naming the lines, kinds and field paths, in yellow under the usual `NO_COLOR` and terminal rules; stdout (and `events --json`) carries nothing of it and the exit status stays 0. `watch` keeps the same report in the footer, after the key hints, for as long as the journal holds such content; on a screen too narrow for it the footer shortens it to `skipped journal content: togi events`, and one-frame `watch` shows it too. A skipped event's `seq` still counts, so a gap in the events printed is not a defect. `run`, `reset` and `doctor` stay strict, as above. The development tools that read journals (`togi-tool-audit`, `togi-tool-facts`, `togi-tool-stats`) read leniently and print the report to stderr, naming the journal.

One-frame `watch` strips application-owned ANSI styling from its frame and visibly escapes untrusted control characters in the frame and its journal-error diagnostic.

`run` records `shutdown` only for clean stops (exit 0) and journaled dead ends (10-15, 17-18), and only after required same-boot reconciliation succeeds. A compatibility refusal (16) and a refused topology (15) append nothing. Other exits may record restoration but no `shutdown`, so a later boot treats the gap as a crash, except the journal-write emergency below.

Once the host lock is held and hardware is set up, one deferred run owner handles every exit: ordinary error, signal, requested cycles, dead end and panic. It cancels the running workload and joins its teardown before restoring offsets, then closes the journal before releasing the host lock. If teardown cannot confirm that the workload stopped, ordinary restoration and `shutdown` are withheld; the cleanup error is reported and same-boot reconciliation remains necessary. Journal-write failures retain the emergency restoration below only when teardown confirms that the workload stopped; otherwise emergency restoration is also withheld. Cleanup errors are joined to the original error, not substituted for it. A panic on the thread that owns the run runs the same cleanup (the workload's teardown is joined even when the panic came while a trial was running), then the dashboard is stopped, the cleanup's own errors and any dead end it recorded (an offset restoration that failed, a teardown that could not be confirmed) are reported on stderr, the journal is closed and the host lock released, and only then the process exits with status 2 and a `panic:` line on stderr. A dead end that asked for a tuning-boot reboot does not reboot after a panic: this process no longer vouches for the run's state, so it says it did not reboot and exits 2 (the saved entry such a dead end cleared already hands the next boot to the normal system). No panic on any other thread or tokio task ends the process: the hook only reports it (`togi: panic on thread <name>: <message>`, held back while the dashboard owns the screen and printed when it lets go) and lets it unwind. A panic a thread contains itself (the trial runtime's classifier and supervision, a tokio task) leaves the run untouched, and one it does not contain ends that thread alone, never the owner's cleanup: whatever depended on the thread meets the failure its loss causes (a lost SMU worker is a refused mailbox command, a lost trial runtime a failed trial, a lost log or samples writer a reported storage failure) and the owner stops the workload, restores the offsets with readback or takes the emergency path, closes the journal, releases the host lock and exits with the status of that failure. The signal listener is the one thread whose loss nothing would notice, so its loss cancels every run in the process, which stops and cleans up as on a signal. A panic in the dashboard is contained: `run` prints `togi run: dashboard: <message>; printing events instead` at once, and the session goes on, from then on printing event lines. On a clean stop the closing `profile.restored` and `shutdown` lines each appear exactly once, as the clean-stop summary above says: one recorded while the dashboard still showed is printed when the run ends, one recorded after the fallback was printed as an event line then. SIGKILL, a kernel crash and power loss cannot run deferred cleanup; firmware resets offsets on reboot.

On a stop signal, after workload teardown joins and before restoration, the owner drains failure attribution, failure points and combinations and backoffs required by evidence already durable in the journal. The drain can close a completed hunt or a failed deepening round, but starts no trial, hunt, group, deepen or deepening move, reads no hardware ranking and waits for no new evidence. Its bound is the finite outstanding commitments of those recorded failures and completed groups; unresolved hunts remain for the next run. A failure at 0 retains its normal dead-end outcome.

A run that has written offsets, or read back offsets inherited from a same-boot run, restores each core to its baseline, or to its current offset where that is shallower, clamped to [-50, 0] and shallower than its recorded failure point. The restored profile reaches no combination. The writes follow the usual intent, write and readback, then `profile.restored` records the offsets. It skips writes when the cores already hold those offsets, when this run wrote nothing and inherited no offsets, and during cleanup at an `smu` dead end where writes are not trusted. A differing readback during a clean stop turns it into an `smu` dead end; another dead end retains its original outcome. In the tuning boot ordinary exit restoration follows the `boot.saved_entry` change; startup reconciliation precedes a pending dead end's completion.

A durable `trial.end` is authoritative. Trial directories are never pruned (`journal.md`, Files). Failure to compress the ended trial's samples or backend logs appends `session.warning` with `operation: "compress trial files"`, caused by that trial end, and does not change its outcome or stop tuning. A failure to append the warning still follows the journal-write emergency.

If appending an event fails after CPU family/model and driver codename validation has established that SMU commands are safe, after the stale trial-scope sweep of this run succeeded, and once the stop of every backend is confirmed, togi writes every core to 0 without an intent, reads each back, reports the original `journal write` error and emergency outcome on stderr/system journal, and stops without further journal events. Until all three hold (validation, a successful sweep, a confirmed stop) a journal failure remains fatal but performs no mailbox command or SMN access, and the report says which was missing: a leftover workload of an earlier run or of this one may still be running, and the offsets stay for the next run to reconcile. Before the validation boundary, this process cannot have written an offset. On the next run the SMU read reconciles hardware with the surviving journal. This narrow emergency is the exception to intent-before-write; failure to restore or read back must also be reported, and so is a refusal by a poisoned mailbox (see Preflight), whose zero write is never sent. Projection-write failures remain warnings; failure to append their warning follows the same boundary.

A simulated machine crash remains authoritative when a trial report also fails to append: cleanup performs no further hardware access, even if the workload's stop returns a proof that nothing runs.

After an abnormal service exit, `emergency-stop` is the other zero-only exception to intent before write. It acquires the host lock and establishes fresh hardware-validation and scope-sweep proofs, rather than trusting the dead process's state or journal. No offset write occurs until the exact leftover trial scopes have stopped and that stop is verified. Zeroing and every-core readback use the existing SMU emergency path; the report goes to stderr/the system journal, never to a session journal. The command cannot write a nonzero profile.

### Offset types and the write transaction

A write target is a `TargetOffset`, validated to [-50, 0] at construction. An observed offset—a readback or baseline, including one decoded from the journal—is an `ObservedOffset` holding the raw signed value, never clamped or refused: a firmware readback of +10 is recorded as +10, because clamping it would turn a failed zero restoration into a success. Journal fields that describe intended targets or profiles still use `TargetOffset`. Normal offset writes reach hardware only through the session's write transaction over the `Smu` seam. A constrained zero-only emergency, such as the journal-write emergency above, is the one separate path over `togi-smu`: it writes only 0, needs the validation and stopped-workload proofs (`SmuValidated`, `Stopped`) that the emergency rules above and in each emergency command require, and reads each core back.

The transaction is typed so that the compiler proves order and authority: a normal write needs the receipt of a durable `smu.intent` ([journal.md](journal.md#rules), rule 2), and a trial start needs the `Authorized` that only a `Verified` readback yields. The emergency path is never an arbitrary-offset bypass. Types prove order and authority, not that a readback or a teardown happens: safe Rust can drop or forget a value, so each transaction lives in one owner function that callers cannot split, and runtime fault tests cover every transition, including a failure straight after the write.

## Host lock

`run`, `reset`, `emergency-stop`, `doctor` as root and every `hardware`-tagged test take an exclusive, non-blocking `flock` on `/run/lock/togi.lock` on Linux. On Darwin, `reset` of a copied journal uses `/tmp/togi.lock`; hardware tuning remains Linux-only. The lock is shared across all state directories. `run` takes it before constructing hardware, reading the BIOS context or preparing a carry, and holds it until workloads are stopped, offsets restored and the journal closed. `reset` takes it before changing the session and holds it until its journal is closed. `emergency-stop` takes it after its platform and root checks, before constructing hardware, and holds it through the verified scope sweep, zeroing and readbacks. `doctor` takes it after its platform check and before opening the driver, and holds it until its checks end. Hardware tests hold it through workload teardown and any offset restoration; `just hardware` runs packages sequentially so the tests do not contend with one another.

Hardware access borrows the caller-owned host lock for its entire lifetime, including any seam taken out of the machine. The machine does not own the lock: the caller closes the journal after hardware cleanup and before releasing exclusion. The privileged diagnosis interface likewise requires a borrowed host lock, never a boolean assertion of authorization.

Contention exits non-restarting (`run`, `reset`, `doctor` and `emergency-stop`: 3), naming the lock path, before any SMU or SMN access and without writing an event, preparing a carry or changing GRUB's saved entry. A tuning-boot compatibility or unknown-kind refusal also takes the host lock before persisting its leave reason and clearing the entry. Failure to open or acquire the lock prevents those changes. A process exit releases the `flock`; on Linux, `/run` is a tmpfs as well, so a crash cannot leave a stale lock. The lock inode is never unlinked or replaced by acquisition or release.

New locks have mode 0600. The Linux host lock must be root-owned; delegated hardware-test users may open an explicitly provisioned root-owned lock with mode 0660 and read-write access through a dedicated authorized group. A public-readable or group-read-only legacy lock is not authorization. Darwin's copied-journal reset may create a private lock owned by its operator; another operator needs explicit access to a root-owned provisioned lock, not a public read-only fallback.

Acquisition opens relative to validated directory descriptors, without following symlinks in the resolved path or the final lock component, truncating contents or blocking on a special file. The containing directory must be owned by root or the caller. The execution namespace's `/` is trusted independently of its owner's numeric UID mapping, but still requires authorized ownership when it is itself the containing directory. Other ancestors must be owned by root or the caller, regardless of their permission bits: a foreign owner can chmod even a mode-0555 directory and replace its children, splitting the lock domain. Every directory writable by group or other users must have the sticky bit; sticky permissions do not authorize a foreign-owned ancestor. A nonregular lock, a multiply linked file or foreign ownership is refused without chmod or replacement. An owner may tighten legacy permissions to 0600 through the opened descriptor, including a read-only legacy descriptor; mode 0660 is preserved. Tightening does not bypass an existing holder: acquisition still flocks that same inode and exits 3 if it is held. Permissions cannot revoke an already-open legacy descriptor, so full migration requires quiescing all old holders and openers or rebooting; never unlink a held lock to force access.

The NixOS module provisions the lock during boot before user logins, under NixOS's root-owned mode-0755 `/run/lock`. Its creation-only tmpfiles rule neither replaces an existing inode nor changes its ownership or mode; acquisition performs the legacy validation and tightening above. `services.togi.hardwareTestGroup`, default `null`, selects an explicitly authorized existing group and mode 0660 for a newly provisioned lock. Changing or revoking delegation takes effect on a fresh boot or through the quiescent descriptor-based provisioning procedure in [howto.md](../howto.md#host-lock-and-delegated-hardware-tests). Other Linux installations need a root-controlled, non-user-writable parent or early trusted provisioning in a sticky parent: refusing a foreign precreated lock is fail-closed, but cannot repair that denial of service by unlinking it.

The state-directory writer lock remains: it protects journal integrity, not the shared SMU mailbox. `run` takes it after the host lock and before carry preparation, holding it through the session and cleanup. `reset` uses the same order before any marker change or archive operation. The simulator takes the state-directory lock before carry without a host lock. `status`, `events` and `watch` take neither lock and never touch the SMU. `doctor` never takes the writer lock; without root it takes no lock either and sends no mailbox command or SMN access. The host lock coordinates togi processes only; other clients of `ryzen_smu` can bypass it.

Before a successful leftover-scope sweep, a journal write failure reports the error and leaves offsets unchanged: even emergency zeroing must not write a profile while an old workload may still be loading it. After the sweep succeeds, the usual journal-write emergency behavior applies, including a failure to record the successful sweep itself.

## Privileges

`run` requires root: it changes core voltage and the boot entry, and creates cgroup scopes. Linux `reset` normally runs as root; its host lock is accessible only to root and explicitly delegated users. Darwin `reset` of a copied journal can run as that private lock's owner without root. `doctor` makes every check only as root; without it, it makes the checks that need no root and reports the rest skipped. The read-only commands work for any user who can read the state directory.

The hardware diagnosis API requires both a held host lock and effective UID 0 before constructing a command-capable driver. Without both, the driver is identity-only and mailbox, SMN, PM table and scope probes stay skipped even if file permissions would allow them.

Togi stays root. Backend workloads run as the unprivileged account named by `backend_user`, using that account's UID and primary GID with no inherited supplementary groups. The NixOS module declares the `togi-trial` system user and group and writes its name into the configuration. A missing account setting, nonexistent account, invalid UID or GID, UID 0 or primary GID 0 refuses preflight; workloads never fall back to root.

### Trial confinement

Backend confinement follows [workloads.md](workloads.md#containment). The controller includes the session, supervisors, journal, hardware workers, Tokio runtime and blocking threads, and the in-process dashboard. Managed trials follow [controller placement](workloads.md#controller-placement): shape-dependent capped placement or host-core rotation is established before workloads launch. Current schedules retain legacy placement until the Ruleset 13 cutover: every unloaded CO-0 core, else the least-deep unloaded core, else the least-deep loaded core; ties choose the lowest core ID and an unknown offset ranks deeper than a known one. Legacy affinity diagnostics alone never refuse a trial or change its credit.

Placement acts on whole physical cores, including both SMT logical CPUs. It covers threads already present and threads spawned during the trial, follows each trial's loaded set (including temporarily suspended workers), and resets the saved affinity after a confirmed teardown, start rollback or stale-scope sweep. Workloads retain their own declared CPU confinement; they do not inherit the controller's narrower CPU set as their final affinity.

Affinity changes are reported with the trial's progress. A thread that could not be read or moved, or continued thread creation beyond the bounded affinity sweep, is reported as incomplete confinement rather than claiming that every thread is protected. An incomplete restoration retains the saved affinity for the next confirmed teardown or sweep to retry.

Managed clock limits pass through the machine's cpufreq seam, with an in-memory adapter for ordinary tests. The real adapter discovers policy membership from `related_cpus`, reads the policy's minimum and maximum, saves `scaling_max_freq`, writes the cap and reads it back. A policy that also controls a tested core other than the single-CCD excluded host is refused rather than silently capping the test load.

The cpufreq core applies a written limit from a work item after the write returns, so an immediate read can still show the previous limit. Each limit, cap or restore, is therefore read back repeatedly until it equals the written value; a limit that does not read back as written by the deadline is unconfirmed, with today's consequences: a cap leaves the trial inconclusive and recovery restores every saved policy, a restore keeps the pending transaction armed. Every policy of a cap or of a restore is written first, then all policies not yet confirmed are read in rounds against one deadline of 500 ms that starts after the last write, so a slow policy never uses up the window of a later one. The deadline is 500 ms because the cpufreq core normally applies a limit within milliseconds, so half a second tolerates a work queue delayed by load while a failure of all 16 policies still ends well inside the margins of the stop and sweep bounds. Policies not yet confirmed are read again every 10 ms, which notices an applied limit soon after the work item runs and reads a policy at most 51 times per deadline. The waits go through the runtime's timers with the caller's cancellation token: cancelling a cap ends its wait at once and leaves that policy unconfirmed, as the deadline would. Restorations after teardown, rollback and sweep are cleanup and pass a token nothing cancels.

Before the first write a durable `controller-frequency.pending.json` transaction in the trials root saves the boot identity, policy identities and original limits. It is created exclusively with mode 0600 whatever the umask, through a staging file that is never opened through a symlink (an existing staging entry is replaced), because the backend account can search the trials root; the file is decoded only as a JSON object. It remains armed until every original limit has been written back and verified. Confirmed trial teardown and partial-start rollback restore frequency limits as well as affinity. Restoration attempts every saved policy even when a read-back or the persistence of one policy's restored state fails, writes nothing to a policy that is missing or whose `related_cpus` changed, and reports one failure that counts the unrestored policies and keeps the first cause. The stale-scope sweep restores an outstanding same-boot transaction before another trial or profile write, even when the controller died before it could report its start. Every managed trial restores an outstanding transaction before it launches, whichever placement it takes, and its start is refused with no credit if that restoration fails. An old-boot transaction is discarded without writing stale limits into a new boot. A failed restoration retains the pending transaction for recovery and prevents another managed cap from overwriting it.

The main journal records the selected controller CPUs, rotating host and its offset, saved/requested/read-back policy limits, failure diagnostics and restoration. Recovery reports its restoration through the sweep record. The pending transaction supplies recovery intent across a crash between changing a limit and reporting trial progress; it is not a second event journal.

## Preflight

Hardware construction checks CPU family/model from `/proc/cpuinfo` and the driver codename from its sysfs metadata before reading any SMN register, including the slot-mapping fuses. An unsupported identity leaves the driver available for topology and preflight introspection but refuses every mailbox command and SMN access, and it neither opens a mailbox file nor reads the PM table. CLI startup repeats this non-command validation and skips BIOS context reads when validation fails, then lets session preflight record the refusal and take the normal dead-end path (exit 15, including the watchdog check and saved-entry clear in a tuning boot). Session preflight establishes its own validation boundary before command-bearing checks; failures while writing earlier startup events must not emergency-zero the hardware.

An identity or topology file that exceeds its read limit (64 KiB for sysfs metadata, 1 MiB for the first `/proc/cpuinfo` stanza) is refused with a size error, never validated from a truncated prefix.

Every mailbox command and SMN read runs on one worker thread with a 1 second deadline. A blocked sysfs transfer cannot be cancelled, so an overrun poisons the driver: it refuses every later command, including emergency zeroing, with an error naming the stuck request, and starts no new hardware transaction while that one may still be outstanding. The poison also gates the PM table: reading `pm_table` sends RSMU command 0x03, so once a mailbox command or SMN read has timed out no PM table reader can be created and every existing reader starts no further `pm_table_version`/`pm_table` read; its checks then report the lanes absent (the table is unreadable) and any lanes it already cached age out as usual. A PM read that is itself stuck is not a mailbox overrun: the reader keeps its one stuck read, reports it overdue and starts no replacement. A transaction still queued when its caller times out is abandoned and never reaches the hardware.

Completed session preflight is the startup boundary for stale-scope containment and subsequent same-boot reconciliation, before `startSession` and the first offset write. An interrupted same-boot dead-end completion passes this same boundary before reconciling hardware and completing its recorded action; it starts no tuning.

Before any of them, a `run` whose journal holds no session yet refuses a topology the tuner cannot work on: more than three CCDs ([workloads.md](workloads.md)). It prints `togi run: this machine's topology is not supported: 4 CCDs; at most 3 are supported` (with the CCD count) and exits 15 before the first append, so the journal stays empty, no dead end is recorded and no pending carry is consumed; no offset is written. In a tuning boot it leaves the tuning boot as a refused journal does ([Dead-end actions](#dead-end-actions)). The next run on the same machine is refused the same way rather than stopping on an event it cannot fold. A resumed session's topology was accepted when it started.

`run` checks, each recorded as a `preflight.check` event:
1. In a tuning boot (`--tuning-boot`), a hardware watchdog is armed: at least one `/sys/class/watchdog/watchdog*/state` is `active`, with a readable, nonempty `identity` other than `Software Watchdog`. Where the driver exposes `timeleft`, it must be readable, numeric and no greater than the readable numeric `timeout`; a present counter that fails to read or parse, or exceeds the timeout, fails. Drivers without `timeleft` retain the state-only check. The software watchdog cannot recover a hardware freeze. This check runs before the other checks: it checks immediately, then polls every 1 second for at most 30 seconds, recording one final `preflight.check` named `watchdog`, not one event per poll.
2. Running as root. Without root, `readback`, `pm_table`, `slot_mapping` and `systemd_run` are refused before any mailbox, SMN, PM table or systemd access: they fail with the detail `needs root`. A check that was not made, for lack of root or after a failed `cpu` or `ryzen_smu` check, is recorded as a failed `preflight.check` whose detail is that reason, never dropped.
3. The CPU is family `0x1A`, model `0x40`-`0x4F` (Granite Ridge desktop).
4. `ryzen_smu` is loaded and reports a matching codename.
5. Every core's offset reads back through the SMU.
6. The PM table version, recorded as the `pm_table` check. It is informational and never fails preflight: without a decodable table, including when its reader worker cannot start, trials record no voltage requests. Reading the PM table sends RSMU command 0x03, so it too waits for the CPU and driver validation.
7. Per-core access is supported only on full 8-core CCDs (`../prior-art.md`): each CCD fuse is read twice with distinct RSMU register reads interleaved, and the OS topology must contain eight cores per CCD. Every logical CPU of a core must report the same CCD key (the cache `index3` id, else the `die_id`) and all online CPUs must sit in one physical package (`topology/physical_package_id`); otherwise all per-core reads and writes are refused before any fuse read, naming the offending CPUs in the preflight detail, for every core whose siblings disagree. Raw kernel core IDs must lie in 0–15; a core ID outside that range stops `run` and `doctor` before preflight, with exit 1 and an error naming the CCD and the offending core ID, instead of a preflight record. The CCD index is the rank of the CCD key among the online CPUs, so it is validated against the hardware, never trusted: every core's raw core ID divided by 8 must equal its CCD index, and its slot is the core ID modulo 8. A wholly offline CCD0 (cores 8–15 would rank as CCD0) or swapped CCD key groups violate this, and refuse all per-core reads and writes before any fuse read or per-core command, naming every offending core with the CCD it was found on and the CCD its core ID implies in the preflight detail. Any fused-off slot fails this check with the CCD, its fuse mask and a message that harvested CCDs are not yet supported. Indistinguishable RSMU probes, inconsistent fuse reads, or a live-core count mismatch also refuse all per-core access.
8. Both backends are configured and present. mprime's `bin/mprime` and both selected y-cruncher binaries must be regular executable files; otherwise preflight fails naming the file. y-cruncher selects the lexically first name matching `<two-digit ISA index>-<alphanumeric ISA> ~ <name>` in `lib/y-cruncher/Binaries` for the lowest ISA and the first matching `24-ZN5 ~ <name>` for Zen 5, ignoring unrelated files.
9. `backend_user` resolves to a non-root UID and primary GID.
10. `systemd-run` can create a scope confined to CPU 0 with those credentials.
11. The BIOS context matches the session, when resuming and all required checks passed.

Any failed check is a dead end. An unarmed watchdog after the bounded wait is dead end `preflight` (exit 15), with the tuning boot's usual saved-entry clear deferred until any required same-boot reconciliation succeeds; no SMU offset write or trial can happen before the watchdog check succeeds. When no same-boot reconciliation is required, a stop signal during the wait records `shutdown` and exits 0, rather than recording a watchdog failure.

Normal/manual `run` without `--tuning-boot` uses the same hardware-watchdog readiness check once at startup, after `config.loaded` and before crash recovery or its first offset write. If none is active, it appends `session.warning` with `operation: "check hardware watchdog"` and an `error` that names the check's detail, says a freeze needs a manual reset and recommends starting sessions from the tuning boot, especially after a breaking update. It continues without requiring, waiting for or arming a watchdog. This advisory is not a failed mandatory preflight check or a dead end. Like every event, the warning reaches the run log on stderr when no dashboard shows, the terminal dashboard's history otherwise, and `togi events`. A run that only finishes a pending dead end records no `config.loaded` and so no warning. The tuning boot's watchdog preflight is unchanged and never records this warning.

## Same-boot resume

Before appending startup events, `run` compares the current boot ID with the boot IDs already recorded in the journal. A matching boot means an earlier process may have left offsets applied, even if its restoration was interrupted or its last event says the profile was restored. After successful preflight and stale-scope containment, and before finishing a pending dead end or continuing the session, it drains the journal's outstanding failure attribution, failure points and combinations and backoffs without starting new tuning work, reads every core's actual offset and records `smu.readback`. Those actual readbacks establish this process's ownership of the inherited offsets.

It then restores the journal's failure-aware safe target using the same intent, write, readback and `profile.restored` sequence as exit restoration. Cores already at their safe targets need no writes. Repeated interruptions of these reads or restoration resume by reading every core again; a pending dead end cannot record `shutdown` before reconciliation succeeds. A failed preflight performs no reconciliation and leaves that completion pending.

Required same-boot reconciliation is bounded cleanup even after a stop signal. Cancellation does not short-circuit its startup preflight: the tuning boot still requires watchdog readiness and retains the 30-second watchdog deadline. Long kernel-log retry waits remain cancelable; cancellation during recovery still passes through this bounded preflight and restoration before a signal shutdown. An unarmed watchdog leaves the inherited offsets untouched and records no clean shutdown. After successful preflight and restoration, the stop signal still prevents starting tuning work.

A failed same-boot preflight records its checks and returns the preflight failure without completing a saved-entry action or recording `shutdown`. An existing pending dead end retains its original event, action and evidence; the failed preflight does not replace it. With no pending dead end, the new preflight dead end is recorded but its action remains pending. Once preflight and reconciliation succeed, the next run completes the original pending action, including any reboot request.

A different boot ID retains the firmware-reset assumption: no special reconciliation reads or writes occur. An interrupted dead end on a different boot completes its recorded action without preflight or tuning.

A trial still open in the current boot may have lost its owner while its scope lives on, so `run` neither closes nor compresses it until preflight and the stale-scope sweep have succeeded. Compression then precedes the durable `trial.end`, and the closing still precedes same-boot reconciliation, a pending dead end's completion and tuning. A failed preflight or sweep leaves the trial open and its plain files untouched; the next run that passes both closes it. A trial left open by an earlier boot is closed during crash recovery, before preflight.

After every successful nonwriting preflight, on fresh start and resume in either run mode, `run` sweeps leftover `togi-trial-*.scope` units before the first SMU profile write, including any resume-time reconciliation writes. The sweep stops only concrete unit names with the exact `togi-trial-` prefix and `.scope` suffix; it never touches preflight scopes or names embedding that prefix. Recovered processes receive signals only through bounded `systemctl kill --kill-whom=all` calls on those exact scopes, never through a recovered PID or process-group number. Listing, bounded teardown and final unit/process verification share one 15 s deadline regardless of scope count. A `preflight.check` named `trial_scopes` records the result. If listing, teardown or verification fails, `containment` is a dead end; no profile write or trial follows.

## Configuration

JSON at the `--config` path (default `/etc/togi/config.json`), produced by the NixOS module from `services.togi.settings`. Keys remain snake_case; nested settings are JSON objects and core IDs are object keys written as decimal strings:

```json
{
  "backend_user": "togi-trial",
  "start_offsets": {"3": -10},
  "candidate_solo_limits": {"11": -20},
  "durations": {"short_trial_s": 120},
  "evidence": {"miss": 0.05, "rate": 0.5}
}
```

The example assumes the `togi-trial` account exists; [Privileges](#privileges) defines the backend account requirements. Omitted settings retain their defaults.

| Key | Default | Valid |
|---|---|---|
| `start_offsets.<core>` | none | Offset override per core id: a canonical decimal key (`"3"`, not `"03"`, `"+3"` or `" 3"`) within 0..=15, and an integer offset within [-50, 0]; never clamped, never `null` |
| `candidate_solo_limits.<core>` | none | Candidate solo limit in [-50, 0], starting search at that offset with a solo-limit check; not together with `start_offsets` for the same core. A carried failure point can clamp it |
| `durations.search_trial_s` | 90 | [1, 86400] |
| `durations.short_trial_s` | 120 | [1, 86400]; short R7 trials, hunt groups, deepening checks and reruns |
| `durations.checking_trial_s` | 120 | [1, 86400] |
| `durations.checking_idle_s` | 900 | [1, 86400]; R6 |
| `durations.checking_all_core_s` | 1200 | [4, 86400]; R7 long trials: a quarter per CCD, remainder all-core |
| `checking.cycle` | `["R7", "R7", "R7", "R2", "R2", "R2", "R6", "R5", "R1", "R1", "R1", "R3", "R3", "R3", "R4", "R4", "R4", "R6"]` | Non-empty regime list; a passed cycle is not necessarily full. The schedule is full when it has at least three each of R1, R2 and R7 and one each of R3, R4, R5 and R6 (`CheckingSchedule::is_full`); `run --cycles N` and `run --first-result` refuse a schedule that is not full, because phase 1 ends only at a passed full cycle, and the session and CLI do the refusal |
| `evidence.miss` | 0.05 | Probability of missing the failure rate used by the pass rule; finite number strictly between 0 and 1 ([Evidence](tuner.md#evidence)) |
| `evidence.rate` | 0.5 | Per-trial failure probability used by the pass rule; finite number strictly between 0 and 1; together with miss yields between 1 and 1000 trials ([Evidence](tuner.md#evidence)) |
| `dead_ends.inconclusive_in_a_row` | 3 | [1, 100] |
| `dead_ends.stray_crashes_in_a_row` | 3 | [1, 100] |
| `backends.mprime` | not configured | Absolute path of the package (`bin/mprime` inside it); leave out or `null` for none, an empty string is an error |
| `backends.ycruncher` | not configured | Absolute path of the package (`lib/y-cruncher/Binaries` inside it); leave out or `null` for none, an empty string is an error |
| `backend_user` | not configured; module sets `"togi-trial"` | Existing account with non-root UID and primary GID; checked by hardware preflight |

Unknown members, including members of nested objects, duplicate members, duplicate core keys and out-of-range values are errors. TOML, JSON with comments and YAML are not accepted ([ADR 0050](../adr/0050-json-for-first-party-data-files.md)). When `--config` is not given and no file exists at the default path, the defaults apply.

Evidence values outside (0, 1) are errors, as is an evidence pair whose trial count falls outside 1..=1000. `backend_user` is left out for none; an empty string is an error. A removed key is an unknown member like any other.

The number of trials for a full evidence step is `ceil(ln(evidence.miss) / log1p(-evidence.rate))`, five at defaults. Durations and workload identity are part of the trial class, so a change to either never turns passes of a different class into valid evidence.

The probability interpretation, independence assumption and heuristic choice of defaults are specified in [tuner.md, Evidence](tuner.md#evidence). These settings determine a replicated check's pass count; they are not a tolerated failure rate or a guarantee about future use.

The effective configuration is recorded in `config.loaded` at every start. The JSON file cutover leaves that snapshot's shape unchanged and does not change the journal schema. Configuration that changes the meaning of existing evidence, such as trial durations, is allowed mid-session and takes effect from the next trial. The journal shows when it changed.

The JSON configuration has no version field, and the configuration rejects unknown members (`deny_unknown_fields`), so a removed or renamed option fails the command until the file is edited. The NixOS module keeps no `mkRenamedOptionModule` or `mkRemovedOptionModule` shims: the change is noted in the changelog. Changed configurable defaults are not a ruleset break.

Configuration keys keep their names once released. A change of vocabulary in `GLOSSARY.md` renames prose, messages, help and docs, never a key, so a vocabulary change alone never makes an existing configuration file fail. Event kinds and fields follow the same rule (`journal.md`, Event format).

## In-session run

`sudo togi run` on a normal boot. If the machine crashes, it comes back to the normal desktop. The next `sudo togi run` detects the crash from the journal, attributes it to the in-flight action, and continues. Nothing restarts togi automatically outside a tuning boot.

## Tuning boot

`services.togi.tuning.enable` adds a GRUB specialisation named `togi` and makes GRUB remember the last booted entry (`boot.loader.grub.default = "saved"`). Picking "togi" once in the menu starts unattended tuning. Every crash reboot returns to it until a dead end, exhaustion of the restart-limit retry boots below, an orderly operator shutdown or reboot (unless `tuning.leaveOnShutdown` is off), the operator ending the night ([Night and day](#night-and-day)), or you select a normal entry. The module requires GRUB with exactly one `boot.loader.grub.mirroredBoots` entry: the tuning boot supports a single GRUB environment. Other bootloaders are [#18](https://github.com/shgew/togi/issues/18).

Inside the specialisation:
- `systemd.defaultUnit = "multi-user.target"`, so no graphical session starts;
- `togi.service` runs `togi run --tuning-boot <grubenv>` as root, with `Restart=on-failure`, `RestartSec=60`, a start limit of 3 per 30 minutes, and `RestartPreventExitStatus` listing contention exit 3 and dead-end exit codes 10-18;
- `togi.service` runs the selected package's `togi emergency-stop` in `ExecStopPost` after an abnormal exit, before the restart delay. The hook stops and verifies leftover trial scopes before zeroing offsets and reading every core back, so a dead controller does not leave workloads and offsets applied throughout the 60-second delay. A successful normal exit skips emergency zeroing and preserves normal restoration. Recovery failure is reported in the system journal; the restart policy and limits above are unchanged;
- `togi.service` is ordered after `systemd-pstore.service`, so saved kernel messages are archived before crash recovery reads them;
- `togi.service`, `togi-restart-limit.service` and `togi-leave-tuning-boot.service` require the mount holding `<grubenv>` with `RequiresMountsFor`, including when that mount has `noauto`;
- `togi.service` has `OnFailure=togi-restart-limit.service`. systemd starts that oneshot after every failure, since each automatic restart passes through the failed state; it does nothing unless `MONITOR_SERVICE_RESULT` is `start-limit-hit`, the result of a fourth start within 30 minutes. Then it invokes the selected package's `togi restart-limit --tuning-boot <grubenv>`, which implements the cross-boot retry policy below. If that command fails, the shell fallback removes `/run/togi-retry-tuning-boot`, best-effort writes the fixed fallback reason, and runs `grub-editenv <grubenv> unset saved_entry`; only if the clear exits successfully does it request plain `systemctl reboot`. Recovery applies whether or not `tuning.leaveOnShutdown` is on. Contention and dead ends are never automatically restarted, so they end with result `exit-code`. Contention alone never drives restart-limit GRUB clearing or reboot; dead ends keep their own boot action and dashboard;
- with `tuning.leaveOnShutdown` (the default), `togi-leave-tuning-boot.service`, a oneshot unit ordered before `togi.service`, so it stops after it. Its `ExecStop` skips the return while `/run/togi-retry-tuning-boot` exists; otherwise it runs `togi night-end`, which restores the day's selection exactly (with no remembered day, the plain unset of `saved_entry`), and falls back to `grub-editenv <grubenv> unset saved_entry` when that command fails. This is how the power button ends a night. An orderly operator shutdown or reboot therefore hands the next boot to the day's remembered selection (the boot loader's default, normally the newest normal generation, only when the night remembered none), while restart-limit retry reboots preserve the tuning entry. A panic, a watchdog reset or a power loss never runs the hook, so crash reboots stay in the tuning boot. The clear is logged to the system journal, not to togi's journal. The unit is not restarted when a configuration switch changes it;
- `togi-watch.service` runs `togi watch --tuning-boot` on tty1 with `TERM=linux`, its keyboard as input, `Restart=always` and `Nice=-10`, in place of the tty1 login prompt. The unit's `ExecStart` passes `--tuning-boot` explicitly: `q`, `Q`, Ctrl-C and Ctrl-D, which the terminal delivers as keys while the dashboard shows, do nothing on any page, so a keypress on the console cannot close the unattended dashboard, while `systemctl stop` (SIGTERM) still ends it. `togi.service` keeps the default niceness: its backends run as children of its scopes and would inherit it;
- `services.togi.tuning.display` defaults to `"console"`, preserving that Linux-console watcher. With `"kmscon"`, `togi-kmscon.service` instead owns tty1 and launches the same `togi watch --tuning-boot` inside kmscon with `COLORTERM=truecolor` and `TERM=xterm-256color`. kmscon requests GPU acceleration, uses the shipped DejaVu Sans Mono font, and keeps the watcher's root identity, restart-always policy, one-second restart delay and `Nice=-10`. Direct VT/DRM access requires root; the child gains no privilege beyond the existing console watcher. `tuning.kmscon.fontSize` defaults to 27 pixels (16x32 pixel cells, 160x45 at 2560x1440). kmscon clones connected outputs, using their smallest grid;
- kmscon has one session, no scrollback, mouse input, blinking, display blanking or keyboard grabs for session control, terminal creation, scrolling, zoom, rotation or reboot. Ctrl+Alt+F2 and Ctrl+Alt+F3 switch to the login and logs; Ctrl+Alt+F1 returns to tty1. `--switchvt` selects tty1 at startup, not a prohibition on switching away;
- `togi-kmscon.service` allows three starts per 180 seconds. Its failure hook ignores intermediate failures; on `start-limit-hit`, after kmscon and its children have stopped and released tty1/DRM, it starts the unchanged console `togi-watch.service` for the rest of this boot. There is no hang detection. `togi-kmscon.service` conflicts with and is ordered after `togi-watch.service`, so starting kmscon again stops the console watcher first and the two never share tty1. Neither display unit requires or binds to `togi.service`, and a display failure or fallback never stops, restarts or otherwise controls tuning;
- `togi-console.service` follows `togi.service`'s log on tty3, in place of the tty3 login prompt; tty2 keeps its login;
- nothing else writes to tty1. The kernel command line is the system's, without its `console=ttyN` entries, plus `console=tty3`; it replaces kernel parameters defined for the specialisation alone, since a module cannot remove entries from a list option otherwise, so `/dev/console` output (early boot, systemd status, the emergency shell, panic text) goes to tty3; serial consoles stay. `console=` only picks the terminal behind `/dev/console`: the kernel prints its messages on the foreground terminal unless redirected, so `togi-kernel-log.service`, a oneshot ordered before the dashboard, runs `setlogcons 3` to send them to tty3 as well. Alt+F3 shows the boot log and kernel messages;
- `printk.always_kmsg_dump=1` is added to the tuning boot's kernel parameters, so an available pstore backend saves the kernel's last messages on an orderly reboot or shutdown as well as a panic; hard freezes may leave no record. A later `run` attaches a matching archived record's bounded tail to `crash.detected` (`workloads.md`);
- `console.font` forced to `tuning.consoleFont`, by default `null`, the kernel's built-in font, so a system font without IBM437's block glyphs never reaches the dashboard;
- sysctls `kernel.panic=10`, `kernel.panic_on_oops=1`, `kernel.hardlockup_panic=1`, `kernel.softlockup_panic=1`;
- `boot.initrd.kernelModules = [ "sp5100_tco" ]`, loading the SP5100 TCO hardware watchdog driver in the initrd, before `togi.service` can start; this is tuning-only and does not change the normal boot's initrd module list;
- `systemd.settings.Manager.RuntimeWatchdogSec = "30s"`, so PID 1 arms and feeds the hardware watchdog to reset a frozen machine. The preflight gate waits for an active watchdog and validates its counter where supported rather than assuming that this setting or a loaded driver means it is already armed;
- journald `Storage=persistent` and `SyncIntervalSec=1s`;
- suspend and hibernate disabled.

### Restart-limit retry boots and leave reasons

`togi_restart_count` in GRUB's environment counts consecutive service restart-limit hits without a successful durable journal append, not failed starts within one boot and not tuning crashes. A missing count is 0. Each `restart-limit` invocation increments the count, capped at 3, and writes the count and a new leave-reason record together in one `grub-editenv set` operation:

- counts 1 and 2 retain `saved_entry` and record `service restart limit hit; rebooting back into the tuning boot`;
- count 3 clears `saved_entry` and records `service restart limit exhausted; returning to the normal system`. Further hits remain at 3 and cannot grant another retry boot.

Every `grub-editenv` command (`list`, `set`, `unset`) has a 10 second deadline, is killed as a process group when it passes it and may print at most 64 KiB on each of stdout and stderr; an overrun is a failed GRUB operation like any other error, so a hung or noisy `grub-editenv` cannot hold up cleanup or the release of the host lock. Clearing `saved_entry` reads it, unsets it and reads it again, and fails when it is still set. While a night that `togi night` began lasts and it remembered the day's entry, clearing instead selects that entry again, reads `saved_entry` back, fails unless it reads as that entry, and ends the night; every path that gives up the tuning selection, the restart limit's third hit and the dead ends included, returns to the day this way.

Invalid counts cannot grant retries: a rejected value makes the command fail and takes the shell fallback. The command creates `/run/togi-retry-tuning-boot` only after its GRUB operations succeed, and only for a retry reboot. It removes that marker if the reboot request fails; the fallback also removes it before attempting its normal-system recovery. The marker is boot-local because `/run` is volatile. Reboot requests never use `--force` or GRUB's `next_entry`.

The shell fallback best-effort writes `togi_leave_reason` as compact JSON with `id` equal to `fallback-<service invocation id>` (systemd's unique 32-hex-digit `$INVOCATION_ID`), `count` 0 because the count is unknown, and `reason` equal to `restart-limit command failed; returning to the normal system`. Its identity comes from the unit environment, so recording it does not require launching another reader binary. Failure to remove the marker or write this reason does not prevent the subsequent saved-entry clear. A failed clear stops recovery without requesting reboot.

`togi_leave_reason` is a single compact JSON record with fields `id`, `count` and `reason`, separate from the restart counter. togi-written records have a fresh random unique ID; the fallback's service invocation ID identifies its record. Records are bounded to 300 bytes of printable, single-line ASCII; IDs contain only letters, digits, `.`, `_` and `-` and are at most 64 bytes, counts are 0-3, and reasons are at most 160 bytes. Restart-limit recovery, dead ends, and incompatible or unknown-kind journal refusals persist a reason before clearing `saved_entry`, so the explanation survives a return to the normal system without appending to an incompatible journal.

Only `run --tuning-boot` reads the pending record; ordinary in-session runs and read-only commands leave it alone. Before its first append, a tuning-boot run reads the record. Its first successful durable journal append resets `togi_restart_count` to 0 once for that run, including when the append is a preflight refusal rather than successful tuning. It then appends `boot.leave_reason` with `reason_id`, `restart_limit_count` and `reason` unless the current or an archived journal already contains that record's ID, and clears the GRUB record only after the event is durable. A crash after the append but before clearing, or a failed clear, leaves the record for a later run; matching IDs prevent duplicate events even if a startup transition archived the acknowledgement. If the system has returned to the normal boot, the reason stays pending until the operator selects the tuning boot again. This event adds no journal schema bump.

Before an interrupted dead end replaces a pending leave reason, `run` acknowledges and clears the old record. An unacknowledged reason is appended first, establishing durable progress; an ID already present in the current or an archived journal needs no duplicate append. Failure of this handoff stops the run before replacing the record or clearing `saved_entry`. The new dead-end record then remains pending for the next tuning-boot run, even if appending `boot.saved_entry` is interrupted. Importing a reason after `shutdown` is informational and does not make that cleanly completed boot a crash.

Count-reset, acknowledgement-lookup and reason-clear errors retain the pending record and stop the run as ordinary errors with its usual journaled cleanup, not the unjournaled emergency restoration reserved for journal append failures. A dead-end reason-write failure still attempts the saved-entry clear, records a separate `boot.saved_entry.reason_error` with its diagnostic in the message, and does not turn a successful clear into a failed one or prevent an otherwise-required boot-loop reboot.

## Night and day

A night is the time the machine spends in the tuning boot at the operator's request. `togi night` starts one from the normal boot without the boot menu; a tuning boot picked from the menu is a night too, since GRUB's `savedefault` selects the picked entry as `saved_entry`. A night has no time limit. It ends when the operator ends it, by answering F10 on the tuning dashboard or shutting down with the power button or `reboot`, or when the tuner stops on its own at one of its dead ends or the restart limit; each returns to the day the same way. A failure never ends a night: however often the machine crashes and reboots, `saved_entry` still selects the tuning entry and the tuner starts. A boot loop in which the tuner applies nothing is the tuner's to detect, as the stray-crash dead end ([`dead_ends.stray_crashes_in_a_row`](tuner.md#dead-ends)). Nothing counts the boots of a night.

**State.** Three GRUB environment variables hold it, so that nothing depends on the tuner, its journal or the filesystem the journal lives on:

| Variable | Holds |
|---|---|
| `saved_entry` | The boot loader's selection, as for any saved default |
| `togi_day_entry` | The value `saved_entry` held when `togi night` began the night: the day's selection, written once. Absent when the day had none, which means the boot loader's own default. It outlasts the night, so ending a night twice restores the same entry |
| `togi_night` | `1` from `togi night` until the night ends. Without it, `togi_day_entry` belongs to a night already over |

`/etc/togi/night.json`, written by the module, tells the commands the GRUB environment file and the menu title of the tuning entry (`{"grubenv":...,"entry":...}`; unknown fields are refused). A machine without it has no night switch: `togi night` says so and the dashboard offers no key.

**Boot-loader seam.** The selection lives behind one narrow interface in `togi-tuningboot`: begin a night (select the tuning entry, remember the day, mark the night begun) and end it. GRUB's environment block is its only implementation today; another boot loader, such as systemd-boot ([#1220](https://github.com/shgew/togi/issues/1220)), adds a backend without changing the commands. Nothing selects a generation: the day's entry is whatever `saved_entry` held, restored exactly, and when it held nothing it is unset again.

**`togi night`.** As root it reads `/etc/togi/night.json`. It prints what the night will do as `togi status` plans it today (the header line of the status, or `no tuning session yet; the night starts one` when the journal has none) and that the night runs until it is ended. The uncertain crash range that Ruleset 13 adds joins this plan line when the planner offers it. It asks; on yes it selects the tuning entry, remembering the day's selection if the night is the first (a second `togi night` in a night keeps the first remembered day), prints the good-night message and requests `systemctl reboot`. If the request fails it restores the selection and exits 1.

**Ending a night.** Ending gives up the tuning selection. While `togi_night` marks a night `togi night` began, it selects `togi_day_entry` again exactly, or unsets `saved_entry` when the day had none, and unsets `togi_night`. Otherwise the tuning boot was picked from the menu: its day is the boot loader's default, so `saved_entry` is unset, and a `togi_day_entry` left by an earlier night is unset with it. Ending again after that finds the day's entry already selected and changes nothing. No early-boot step runs in the tuning boot; the tuner starts as it would from the menu.

**F10.** In the tuning boot's dashboard, `F10` asks `Reboot into the day cycle?`. Yes (`y`) stops the run with `systemctl stop togi.service`, which ends it cleanly like any stop, then restores the day's selection and reboots. Any other key withdraws the question and nothing happens. If the run does not stop within five minutes, or the stop fails, nothing changes. The dashboard's quit keys stay ignored; F10 is its one way out. A normal boot's dashboard run as root offers the other direction on `n` (and `F10`): it asks `Reboot into the night tuning?` (`Reboot into the night?` where the line is short), and yes ends the dashboard and runs `togi night` without its own question, so the plan and the good-night message follow the confirmation. A dashboard without root, or on a machine without `/etc/togi/night.json`, offers no switch and ignores both keys.

**The power button.** `togi-leave-tuning-boot.service` is the leave-on-shutdown hook: its stop runs `togi night-end`, so the power button, `poweroff` and `reboot` all return to the day, with the day's selection exactly. It is the same hook as before; only what it runs changed. With `tuning.leaveOnShutdown` off no hook runs, and the night lasts until F10, a dead end, the restart limit or a pick of another menu entry.

**Hours.** Time spent in a night is tuning time. A paused interval is excluded from hours; the forms of the pause are decided in [#1214](https://github.com/shgew/togi/issues/1214).

## Dead-end actions

| Run mode | `deadend` action | Effect |
|---|---|---|
| In-session | `exit` | Record `deadend`, print the condition and evidence, and exit with a dead-end exit code. |
| Tuning boot | `clear_saved_entry` | Record `deadend`, persist the leave reason in GRUB, then give up the tuning selection: restore the day's remembered entry, or, when no night remembered one, run `grub-editenv <grubenv> unset saved_entry` so the next boot selects the boot loader's default, the first menu entry. Record `boot.saved_entry` with the entry before and after, or the clear error; a reason-write failure is separately recorded as `reason_error` and still attempts the clear. Then record `shutdown` and exit with the dead-end code; the unit does not restart, and the dashboard on tty1 shows the dead end. |
| Tuning boot, journal with a newer ruleset, schema or evidence epoch, or refused unknown event kinds | `clear_saved_entry` | Print the refusal to stderr, persist the leave reason in GRUB and clear the saved entry without appending to the refused journal. A reason-write failure still attempts the clear; report both results, and exit 16 without rebooting. |
| Tuning boot, a topology refused before a session starts | `clear_saved_entry` | As for a refused journal, with no journal to append to: persist the leave reason `unsupported topology: <cause>` and clear the saved entry, report both results, and exit 15 without rebooting. |
| Tuning boot, boot-loop dead end | `clear_saved_entry_and_reboot` | Same as the journaled tuning-boot action above, then plain `systemctl reboot` into the normal system if the saved-entry clear succeeded, even if writing the reason failed. |

A failed clear never reboots: the next boot would land back in the tuning boot.

If a `run` starts after `deadend` but before `boot.saved_entry`, it completes the recorded action without starting a trial: after same-boot preflight and reconciliation, or immediately after a reboot, it clears GRUB's saved entry, appends `boot.saved_entry`, records `shutdown`, and exits with the same dead-end condition and evidence. A `clear_saved_entry_and_reboot` action still requests a reboot after a successful clear; a failed clear records the error and exits without rebooting. A `run` without `--tuning-boot` cannot clear the entry: it records `shutdown` and exits with the dead-end condition, leaving GRUB's saved entry as the operator last chose it. If `boot.saved_entry` exists but `shutdown` does not, the next `run` reconciles in the same boot, then records `shutdown` and exits without clearing again or tuning. An interrupted in-session `exit` action likewise reconciles in the same boot before recording `shutdown` and exiting. Once the dead end and shutdown are fully recorded, a later `run` starts normally and re-evaluates the conditions; a still-failing preflight stops before tuning.

The flake also exposes `packages.x86_64-linux.default`, the crane-built `togi` that the module installs by default, and a dev shell, and the same for `aarch64-darwin` for development, where the checks are `board-test` (the Nushell board's fixed-fixture assertions), `sql-test` (the `just sql` views over fixed state directories), `doc-links` (relative Markdown links and anchors), `fmt`, `changes`, `module` and the `clippy`, `nextest-<group>`, `doc`, `cargo-deps`, `deny`, `shear` and `package` checks other than the simulation suite, without `trial-scope-tests`, `vm-recovery-tests` and the VM tests. The package builds only the `togi` crate in the release profile and runs no tests (the `nextest-<group>` and `doc` checks do; the `package` check runs the built executable's `--version` and `completion`), so the installed package contains only the `togi` executable and its shell completions: `togi completion` writes them at build time to `share/bash-completion/completions/togi.bash`, `share/zsh/site-functions/_togi`, `share/fish/vendor_completions.d/togi.fish` and `share/nushell/vendor/autoload/togi.nu`. Bash completion loads the first from the system profile; zsh and fish load theirs where the profile's `share` directories are on their paths, as on NixOS when the shell is enabled; nushell autoloads its script when the package's `share` directory is on nushell's XDG data directories, as on NixOS with `programs.nushell.enable` and in nix-darwin profiles. Otherwise, save `togi completion nushell` to a file and add a `source` line for it to nushell's `config.nu`. Loaded with `use togi.nu *` instead, the script completes everything but the flags before the command name, since a nushell module cannot export a command named after itself. The release procedure and version bump rules are in [Releasing](../releasing.md).
