# Journal and state

Normative rules for what togi records. Goal: anyone, human or agent, reading only the journal can reconstruct everything togi did and why, without reading code.

## Files

All files live in the state directory, default `/var/lib/togi`:

| Path | Role |
|---|---|
| `events.jsonl` | The journal of the current session: one JSON event per line, append-only, source of truth |
| `state.json` | Verified full folded-state cache; never authoritative over the journal |
| `trials/<trial-id>/` | Per-trial work directory: backend config files, raw stdout/stderr (`stdout.log`, `stderr.log` in each instance directory), backend result files |
| `trials/<trial-id>/samples.jsonl` (`.gz` once the trial ended) | Fsynced per-second conditions: milliseconds since trial timing began (`elapsed_ms`), optional `tctl_c`, CCD temperatures by label (`tccd_c`), every physical core's frequency in whole MHz by core ID (`core_mhz`, idle cores included), cumulative worker CPU milliseconds by loaded core ID (`worker_cpu_ms`), package power in watts (`package_power_w`), and decoded per-core SMU lanes (`pm_table`). Missing or invalid package readings and unexplained decreases omit power, never zero ([Conditions sampling](workloads.md#conditions-sampling)). |
| `archive/<session-id>.jsonl` | Journals of sessions ended by `reset --all` or by a transition |
| `archive/<session-id>-trials/` | The `trials/` directory of an archived session |
| `archive/<session-id>-compat-pending` | Crash-recovery marker while a journal this build cannot read is archived without being appended to (`reset --all` or a transition of an unreadable journal); removed on completion |
| `archive/<session-id>-import-pending` | Raw-day import marker: the filename identifies the immutable source and its contents identify the destination session; removed after durable `session.imported` commitment under [Transitions](#transitions) |
| `archive/<session-id>-reset-all` | Permanent reset boundary: excludes this and older sources from raw tuning carry, not from campaign-ledger reconstruction |
| `lock` | Held, exclusive and non-blocking, with `std::fs::File::try_lock` by the one process allowed to write the journal; a second writer fails at once with a contention error and never waits |
| `.events.jsonl.tmp`, `.state.json.tmp` | Temporary files of a torn-tail repair and of a `state.json` publication; a leftover is overwritten, never read as truth |

Optional `pm_table` contains six 16-element arrays indexed by physical core ID (0–15): `power_w`, `voltage_request_v`, `temperature_c`, `c0_pct`, `cc1_pct`, and `cc6_pct`. Residency units are percent. Voltage requests do not describe separate rails: both CCDs share VDDCR and the highest request wins. Only table version `0x620205` with the exact supported size and core IDs 0–15 in CCD/slot order (0–7 on CCD0, 8–15 on CCD1) is decoded (`workloads.md`, Conditions sampling). The sampler never waits for the single-flight background reader: a completed reading can be reused within two seconds of its read's start. Unavailable, unsupported, failed or overdue reads omit the entire field, never insert zero lanes; a read taking 100 ms or longer is discarded and readings older than two seconds are omitted.

Once per run, `preflight.check` with `check: "pm_table"` records in `detail` and `msg` the table version seen and whether per-core lanes decode. If no version can be read it says the version is unavailable; the simulator without `shared_voltage` says it reports no lanes, while an enabled machine identifies its synthetic voltage requests and clocks. The check uses the same single-flight reader with at most the remaining 100 ms read budget and explains pending/overdue reads or an unsupported topology. This informational check always has `ok: true`: unsupported or failed diagnostic reads are not preflight failures.

Retention: every trial directory is kept, whatever the trial's outcome; nothing prunes them. After its writers have stopped and before appending `trial.end`, the session gzip-compresses `samples.jsonl` to `samples.jsonl.gz` and each instance's `stdout.log` and `stderr.log` to `stdout.log.gz` and `stderr.log.gz`. Each file is written whole under a temporary name, fsynced, renamed into place and its directory fsynced before the plain file is removed; the removal is then synced too. A reader always finds one complete form. A crash in between leaves readable plain and/or compressed files; resume reads the samples, retries compression and closes the interrupted trial. All readers open the plain file first and fall back to the compressed one. Files remain plain when containment failed and writers may still be alive. Compression errors retain the plain file until the compressed form is durable and produce a nonfatal `session.warning`, not stability evidence (`runtime.md`, Exit codes). Simulations generate samples only when asked; in-memory simulations create no files, while `just sim --samples` compresses them on trial end too.

## Rules

1. **Everything is an event.** These are all events:
   - every action with an effect outside togi's memory: SMU command, process start, signal or stop, scope creation, file written for a backend, sysctl, GRUB change;
   - every observation that feeds a decision;
   - every decision.

    Exceptions: `SIGSTOP`/`SIGCONT` cycles too frequent to record one by one. R3 and R4 cycles are recorded as the schedule and seed at trial start and as counts at trial end. R6 bursts are recorded as a `trial.progress` when they begin and as counts in a `trial.progress` at trial end. R7 runs separate trials on each loaded set of cores, not in-trial CCD phases. A refusal of a journal written by a newer schema, ruleset or evidence epoch, or of a journal holding an event this build cannot decode, writes no event into the refused journal: the build that wrote it must remain able to resume it. The reason goes to stderr, which is the system journal in a tuning boot; persisting the leave reason in GRUB and clearing its saved entry for that refusal also write no event there. A later tuning-boot run with a writable journal imports the pending record as `boot.leave_reason` below. Restart-limit recovery likewise persists its record outside the journal because the failing service may never have opened one. A transition archives an older journal without writing to it, for the same reason (Transitions, below).
2. **Intent before action.** An action that may crash the machine, such as an SMU write or a trial start, is appended and fsynced before it happens. On the next boot the last intent without a matching result is the in-flight action. Every event is written with a single `write` of its whole line and fsynced before `append` returns, and only then is it published to the in-memory journal, so a crash loses at most the line being written (rule 6); closing the journal fsyncs it. Before the write, the line is decoded again: an event that would not read back (a payload the schema refuses) is an error, nothing is written and no seq is consumed; an invalid cause (not earlier than the event), an encoding error or a first event that is not `session.start` is refused the same way and does not poison the writer. Locking a state directory creates it and every missing ancestor durably, and opening the journal syncs the state directory after it creates `events.jsonl`, so a new journal file survives a crash. An ancestor may be a symlink to a directory, as `/var` is on macOS: the directory below it is synced in the directory the link names, while the state directory itself is never a link. `run` appends `shutdown` when it stops on a signal, at a dead end, or at the [night's normal end](#shutdown-reasons); other exits may record restoration but never `shutdown`, so a later boot whose journal ends without `shutdown` is treated as a crash (`workloads.md`, Failure signals). Simulated storage fsyncs nothing, because a simulated crash cannot lose written data (Simulated storage, below).
   A short write is an append failure. After a write or fsync error the journal is poisoned: every later append returns the first failure without touching the disk, until the state directory is reopened, because a complete line may have survived the error and the in-memory sequence is no longer authoritative. Reopen replays surviving complete lines and repairs a partial tail before assigning another sequence, so an event whose append failed is either absent or present once. Closing a poisoned journal does no I/O and hands back the locked state directory. Poisoning never blocks the session's emergency zeroing, which needs no journal.
   A `deadend` without its `boot.saved_entry` (for a GRUB action) or without `shutdown` is an interrupted dead-end action, not permission to resume tuning: the next `run` completes the missing action and records `shutdown` before doing other work; a `run` without `--tuning-boot` cannot clear GRUB's saved entry and only records `shutdown`. A `boot.saved_entry` tied to that dead end is not cleared again. Once `shutdown` is present, the next `run` starts normally and re-evaluates dead-end conditions.
   `smu.intent` and `smu.write` are not appendable through the generic `append`; it refuses them. `append_smu_intent` writes the durable `smu.intent` and only then returns a receipt, a value that cannot be built, cloned or copied outside the journal crate and is bound to the journal that minted it. `append_smu_write` consumes the receipt, writes `smu.write` caused by that intent, and returns a token whose seq the readback cites. A receipt from another or a reopened journal is refused, and a receipt is spent whether or not its write succeeds. A failed or poisoned journal mints no receipt. On the simulator's unsynced journal (`lock_unsynced`, below), whose files are never fsynced, `append_smu_intent` writes the buffered events through to the file before returning the receipt, so the receipt proves the intent's order and that it survives the process exiting, not a power loss; that journal's writes reach only a simulated SMU.
   On a same-boot restart, the startup `smu.readback` for a core cites that core's `smu.intent` left open by the dead process, if any. This observation resolves the inherited intent even when the observed offset needs no restoration write: the fold closes an open SMU intent on a readback that cites it, and readers no longer report it in flight. The readback records the actual offset, not a completed write or proof that the intended offset was applied. Next-boot in-flight attribution is unchanged.
3. **Decisions name their cause.** A decision event carries `cause`: the `seq` numbers of the events it was derived from, plus a `reason` in plain words. A step-back that rests on two failures cites both, the later one first.
4. **The journal wins.** At every boot, `run` independently folds the whole journal and checks `state.json` against it. A missing, unreadable, tampered, other-build or mismatching snapshot is rewritten; after a successful rewrite `state.rebuilt` records the difference. Its `fields` names differing top-level `facts` keys (`last_seq`, `cores`, …), `tuner` for the projection, and, at an equal sequence, `incremental`, `recovery`, `defects` or `presentation` for the full reducers. `build` identifies another build, `snapshot` identifies a wrong prefix stamp, and `state.json` identifies an absent or rejected document. `last_seq` marks a snapshot behind the journal, as after a crash between writes; the audit reads it as stale, not wrong.
5. **One writer.** `run` takes the host lock, then the state-directory `lock`, then prepares any [fresh transition and raw-day import](#transitions), and holds both locks through the session and cleanup. The writer lock precedes every observation-source scan, archive or pending-marker change, including before the destination journal exists. `reset` follows the same lock order through boundary creation, marker changes and archive completion; it refuses while a run holds the lock. The simulator holds the state-directory lock during transition preparation and each simulated boot's session. Closing the journal returns the locked directory; dropping that directory releases the lock. `status`, `events` and `watch` only read, without the lock, and narrate recorded observations and [policy commitments](#ruleset-13-events), never inferred predecessor decisions.
   Archiving is one recoverable transaction. First make the kind's marker durable: the permanent reset boundary for `reset --all`, or the source/destination import marker under [Transitions](#transitions). A compatible reset appends `command.reset` and `session.archived`, fsynced, and spends its writer; a fresh transition leaves its source unchanged. Remove the state file, move `trials/` to `archive/<session-id>-trials/`, then move `events.jsonl` to `archive/<session-id>.jsonl`, syncing each step before the next and using no-replace renames. A conflicting archive journal or trial directory refuses the transaction before any append. Its own reset/import/compatibility markers instead authorize resuming the interrupted operation.
   Opening a journal that records its own `session.archived` finishes that move first, even if a torn tail follows it, then continues with an empty journal. An archive without a compatible writer first fsyncs `compat-pending`, makes the moves without appending to the source, syncs both directories, then removes that marker. A subsequent open/archive resumes such a move only with its marker; a collision without one is refused. When the archive exists and the live journal is gone, remove and sync the compatibility marker under the writer lock. The import marker remains governed by the separate [import commitment](#transitions), not by archive completion alone.
   If an unreadable journal already recorded its own `session.archived`, `reset --all` completes that recorded move without creating a compatibility-pending marker, including when `trials/` was moved before the interruption, but still makes the permanent reset boundary durable at that session before the move completes.
   Completing a compatibility archive under the locked state directory does not open a replacement writer or create an empty live journal. If an empty live journal is present, its removal and the state-directory sync precede recovery; a failed removal or sync leaves the compatibility marker available for retry.
6. **Torn tails are expected.** A crash can leave a partial last line: bytes after the last newline are a torn tail, never an event, even when they happen to parse as JSON. A complete line that does not decode, a gap in `seq`, a first event that is not `session.start` or a cause that does not precede its event is corruption, never repaired: opening fails and the file is not modified. Replay drops a torn tail and records a `journal.torn` event with the discarded bytes, hex-encoded, without ever losing them: opening the journal writes its complete lines followed by that event to `.events.jsonl.tmp` in the state directory, syncs it, renames it over `events.jsonl` and syncs the directory next to the rename, before appending anything else. Until the rename, `events.jsonl` still ends in the torn bytes, so a failure or crash at any step leaves either the torn bytes or their durable record, and the next open repeats an unfinished repair, recording the bytes exactly once. The open reports the repair record's seq. The first line is the exception: before any of this, the first-header check of `run`, `status`, `events` and `watch` reads it, terminated or not. A nonempty first line that does not decode as a header of this build's journal, truncated JSON with no newline included, is refused as another build's journal or a torn first header (the two cannot be told apart): it is never treated as a torn tail, never repaired or truncated, and the file is not modified. The operator keeps it aside by hand ([Go to Rust cutover](../howto.md#go-to-rust-cutover), [Reset and compatibility](runtime.md#reset-and-compatibility)). Only a first line that decodes as a complete header but has no newline is a torn first line. It leaves an empty journal: nothing happened before `session.start`, so nothing is recorded and the line is truncated in place and synced. A failed open leaves no writer and releases the lock.

Reading never needs the lock and never writes: `Recording::read` parses a whole journal (events, an O(1) lookup by seq, and the torn tail as a value) and `EventReader` streams complete lines, both checking the same promises (contiguous seq from 1, `session.start` first, causes before their events) and ending at the first error. Both decode strictly; their lenient forms (`Recording::read_lenient`, `StateDir::recordings_lenient`, `EventReader::lenient`) are what read-only consumers use (decoding rules below) and report what they skipped, as a `Skipped` value with one human line.

Simulated storage. Tests and simulations run in memory: `StateDir::simulated` takes a `MemFs`, a shareable in-memory filesystem whose handle a simulation keeps across simulated reboots and can dump to disk on request. It injects faults (fail the Nth write, sync or rename, short writes, fail the publication of `state.json`) for the crash-resume tests and counts every mutating operation. It keeps the ordered history of operations and reads only for a test that calls `MemFs::record_history` before the operations it inspects; ordinary simulations keep none. `just sim --state-dir` uses `StateDir::lock_unsynced`: a directory on disk whose files are never fsynced and whose journal buffers 64 KiB of events in memory, writing them when the journal is read back, archived or closed and whenever the buffer fills; a kill of the process loses the buffered tail. Both constructors and `MemFs::dump_to` are on clippy's `disallowed-methods` list and approved only for the simulator crates, `crates/togi-tool-sim` and the session's tests; `StateDir::lock` is the only constructor a real `run` uses. The fault matrices prove each failure path recovers, not that data survives power loss.

Simulations never sync files or directories, including sample compression with `--samples`; their disk output is an inspection artifact, not power-loss evidence. Tests replace durability operations with recording or fault-injecting adapters, including kernel filesystem tests, so no test flushes a real drive. Production journals, samples and compressed trial files retain the durability rules above.

Warm resume is the contract of `togi-simrun` and the session, not of the journal. A run that ends cleanly hands back a `ResumeCapsule` with its journal: every fold of the journal's events (the shared facts, the tuner state, the recovery fold and the defect state), bound to the journal's session and last event. A caller that runs the same journal again, as the simulator does after a simulated crash or restart, passes the capsule in, and the session adopts it instead of replaying the journal, only when the capsule's session and last event are the journal's and the defects it judged by are the run's; any other capsule is ignored and the journal is folded from its events. A run that ended with the machine crashed hands back its capsule, which holds what the crashed boot folded, while the state file stays as the last publication left it; a run whose journal latched hands back none. `ResumeCapsule::publish` writes, into the state directory, the state document a `Live` run would have left after the capsule's last event, for a caller whose `OnFinish` run crashed before publishing. A warm simulated reboot goes further and keeps the open journal: `Journal::reboot` writes its buffer through, sets the new boot and a new journal identity (receipts of the earlier boot are refused) and reads nothing from the file, and `togi_session::prepare_kept` makes `prepare`'s decisions from that journal's events. A run that adopts a capsule skips the saved-state check, since the run before it left `state.json` pending on purpose; every other startup step still runs on adopted state: compatibility, dead-end resume, crash recovery, the defect check, preflight, the sweep and same-boot resume. `ResumeCapsule::verify` replays the events into fresh folds and names the first part that differs (facts, tuner, recovery or defects), that the capsule's last event is not the events', or that the state document published from the capsule's folds does not survive a JSON round trip unchanged or differs from the cold fold's; the simulator verifies after every Nth crash with `--verify-every N` and when the invocation ends, and `--cold-boots` never passes a capsule, as `togi run` does not. A new invocation reads the journal from disk, and `togi run` replays at every boot and writes `state.json` after every append. The simulator's tests pin that warm and cold boots leave the same events and state.

## Event format

One JSON object per line:

| Field | Meaning |
|---|---|
| `seq` | Positive integer, +1 per event from 1 within a session |
| `time` | RFC 3339 UTC timestamp with as many fractional digits as it needs |
| `boot` | Kernel boot ID (`/proc/sys/kernel/random/boot_id`) |
| `mono_ms` | Boot-local CLOCK_MONOTONIC milliseconds, truncated; the event an append publishes is the one its line decodes to, so a live fold equals a replay. Absent when unknown (events `reset` appends are no trial evidence), and an explicit `0` is a real zero. Used to match evidence to trials despite wall-clock jumps |
| `cause` | Array of the `seq` this event follows from, each earlier than the event; omitted when empty |
| `kind` | Event kind from the catalog below |
| `msg` | Human-readable description generated by the journal from the payload when it appends, stored as evidence and never regenerated on read; producers never write it. Raw diagnostic text stays unsanitized; human output escapes controls |
| `data` | The kind's payload object |

Diagnostic error text names the failed operation, followed by its retained causes in order, separated by `: `. Error messages do not embed their source's message; `togi_machine::error_chain` (also exported by `togi-render`) renders the chain without suppressing equal or substring text. A transparent forwarding error adds no operation of its own. Multiple failures retain their order and render each member's chain. This changes diagnostic prose only, never event kinds or fields, and recorded messages remain unchanged on read.

Fields appear in the order above. Payload fields are snake_case and carry units in their names (`duration_s`, `period_ms`, `tctl_max_c`); values use the vocabulary in `GLOSSARY.md`. Cores are always `core` (the kernel `core_id`, 0–15); logical CPUs are always `cpu`. Values are typed and the schema refuses what does not fit: a core set (`cores`, `candidates`, `top_requesters`, a group) is a sorted array without repeats; a per-core value (`profile`, `offsets`, `voltage_requests_v`) is an object keyed by core ID; a workload (`workload`, `workloads`) is the id of a catalog workload and an id outside the catalog is a decode error (an idle class has no `workload`); an offset the session decided (a profile, a target, a failure point, a decision's offsets) is an integer within −50…0, while an offset only observed (the baseline, a readback) is any integer; ordinals (`cycle`, `step`, `hunt`, `group`, `round`, `combination`, `part`) and `seq` references are positive integers and are absent, never `0`, when they do not apply. Optional fields are omitted when absent and optional flags when false, so absence is never an empty string, `0` or an empty list standing for “none”. Four booleans are required instead and always written, `false` included: `config.loaded.file`, `preflight.check.ok`, `session.carried.failure_points` and `mce.corrected`; a payload without one is a decode error. Closed vocabularies (activity, decision, outcome, attribution, hunt stage and result, dead-end condition and action, shutdown reason, …) have no empty or unknown value. Nested exceptions are `session.start.cores` (per-core `core`, `ccd` and `cpus`), `session.carried.sources` and `session.carried.carried` (per-core carried limits and failure points, each with the `session` and `seq` it came from), `trial.start.instances` (per-core `core`, `cpus`, `pid` and `scope`), carried facts' `source` (original provenance) and `class` (trial-class identity), `hunt.group.probe` and `hunt.group.held` (core/offset members), the `members` of `hunt.end` and `combination`, and `checking.chain.groups` (top-requester tie groups).

Historical decoding: the tuner refuses a recorded hunt or deepening-round trial requirement outside `1..=65535` instead of truncating or saturating it. A recorded intended trial duration must be nonzero. An absent deepening-round count or duration uses the validated configuration; an explicit zero does not mean absent.

`config.loaded` carries `config`, a journal-owned snapshot of the effective configuration, next to its `build` stamp, `path` (where the configuration was looked for), `file` (whether one was found) and the optional kernel-log cursor boundary. The snapshot is a type of the journal crate, not of `togi-config`, and its wire shape is pinned by a golden test, so a change to the configuration never changes the journal format silently: a change to the snapshot is a journal format change and follows [ADR 0009](../adr/0009-compatibility-across-updates.md)'s additive rule (a new optional field, like a new event kind, needs no schema bump, because read-only consumers ignore a field they do not know and skip a kind they do not know, as decoding rules below say; a change that renames, removes, retypes or tightens a field, or makes an optional one required, does). `ConfigSnapshot` writes the effective settings that remain: `dead_ends` (`inconclusive_in_a_row`, `stray_crashes_in_a_row`), `backends` (`mprime` and `ycruncher` store paths) and `backend_user`; an unset backend path or backend user is `null`. The retired Ruleset 12 fields `start_offsets`, `candidate_solo_limits`, `durations`, `evidence` and `checking` decode from old journals but are never written. Decoding checks what the snapshot's own types check (core IDs, offsets, regimes, unsigned integers; an unknown field is refused by a writer and ignored by a read-only consumer, like any other) and records the values as written, without the configuration's policy ranges: a journal stays readable when the configuration later changes what it accepts. The consumers that rebuild a configuration from a recorded snapshot (`togi-config`'s `Config::from_snapshot`, used by the simulator's resume and the tuner's fold) validate it as a configuration file is validated and refuse one this build would refuse.

Every build stamp is a `build` object with `version`, `rev` (absent when unknown), `ruleset`, `schema`, `fixes` (absent means 0) and `evidence` (the evidence epoch). The first event is `session.start` with the build stamp, the session ID and the cores; `config.loaded` carries the build stamp at every start or resume. The first line of a journal, its `session.start` envelope with the build stamp, is the compatibility envelope: its shape never changes across schemas, so any build can read the stamp of any journal from that line alone (`StateDir::live_build`) and judge it before decoding the rest. The durable epoch, ruleset and schema of a session are those of `session.start`; a later `config.loaded` refreshes only `version`, `rev` and `fixes`. This build stamps its tuner ruleset, its tuner evidence epoch and `togi_journal::SCHEMA`. The Rust journal starts its own schema numbering at 1; the schema increases only when an existing kind or field is removed, renamed or retyped. Added kinds and fields do not bump it: an added field carries a serde default, so newer builds read older journals, and a journal of a newer schema is refused. Older journals follow [Transitions](#transitions).

`Build::verdict(recorded, operation)` compares the schema, ruleset and evidence epoch separately and answers `Use`, `Archive` (move the journal aside without appending to it) or `Refuse` naming the first dimension that settles it. Any newer dimension refuses a resume even when another is older.

| Operation | Use | Archive | Refuse |
|---|---|---|---|
| Resume (`run`, and `doctor`'s checks) | all three equal | an older dimension and no newer one | any newer dimension |
| Append (to a current session) | all three equal | never | any difference |
| ResetAll | same schema | a different schema | never |
| Inspect (`status`, `events`, `watch`) | same schema | never | a different schema |
| Replay (dashboard history, `tools/replay`) | schema not newer and same ruleset; the epoch is ignored | never | a newer schema or a different ruleset |
| History (archives, raw-day imports, facts, statistics) | a schema from 1 that is not newer | never | schema 0 or a newer schema |

Read-only dashboard replay accepts a recording whose schema is not newer than this build's and whose ruleset is the current one, and refuses any other ruleset before decoding its events, because the dashboard projection uses the current tuning rules. It ignores an incomplete final line without changing the journal. Every reader preserves the recorded `msg` unchanged, including diagnostic text and vocabulary from older builds; decoding a payload never regenerates its message.

There is no schema translation and no reading of journals written by the Go implementation: its journals, `state.json` and archives are not read, never archived and never carried from. Go and Rust cannot share a state directory. Before the first Rust boot the owner moves the Go directory aside (`/var/lib/togi` to `/var/lib/togi-go`) and the cutover starts a fresh session in a new `/var/lib/togi` ([Go to Rust cutover](../howto.md#go-to-rust-cutover)); there is no rollback to the Go build. A journal whose first line is not a complete header of this build, such as a Go one or a header torn by a crash, is refused by `run`, `status`, `events` and `watch` with exit 1 before any later line is decoded, any lock is taken or any file changes ([Reset and compatibility](runtime.md#reset-and-compatibility)). Carry, facts, defects, statistics and fitting read one vocabulary, that of `SCHEMA`.

Session IDs are `YYYYMMDDTHHMMSSZ`, a UTC second, optionally followed by `-N` with `N` ≥ 2, and are validated wherever they are parsed. While holding the state-directory writer lock, a collision with `archive/<id>.jsonl`, `archive/<id>-trials/` or any marker of that ID chooses the first free `-2`, `-3`, … suffix (checked arithmetic: running out of suffixes is an error). A new ID must also sort after the newest reset boundary: if its timestamp is at or before that boundary, allocation starts at the boundary and takes its next numeric suffix, including after a backwards wall-clock change or deletion of the discarded archives. IDs order by timestamp and then numerically by suffix: the unsuffixed ID first, then `-2` through `-10` and beyond. Archive and trial paths are derived from the ID; a path recorded in an event is never trusted, which is why `session.archived` carries only the session. `archives()` lists the regular `<id>.jsonl` files in that order, and markers are listed by session and kind.

Build compatibility diagnostics consistently identify the program as togi, regardless of the recorded version.

Decoding is strict for writers and lenient for read-only consumers; there are no opaque events. Both refuse what a type cannot hold: malformed JSON, a missing required field, a value outside its type (a seq of `0`, a core above 15, a decided offset outside −50…0), a word outside a closed vocabulary, a damaged envelope, a first event that is not `session.start`, a gap in `seq` and a cause that does not precede its event. Apart from the first-header refusal below, such an error names the line and, when the envelope names a kind this build knows, the kind.

Strict decoding serves `run`, `reset` and every path that appends, including the decode of a line before it is written (rule 2). A kind this build does not know, or an unknown field anywhere in an event (the envelope, the payload, a nested object, the members of an internally tagged enum such as `smu.intent` or the schedule of `trial.signal`), is a decode error that names the line, the kind and, for a field, its path (`data.cores[0].extra`; `extra` for an envelope field). A journal with such an event cannot be read by this build for writing: whether it is archived, refused or ignored is the `Build::verdict` of the operation (table above), and a current-ruleset, current-schema, current-epoch journal with an undecodable event is refused for `run` and `Append` with exit 16 even after a BIOS change. Older journals are archived without decoding their events; `reset --all` archives a journal of a different schema without appending; an undecodable same-schema journal is refused before it is modified. Refusals name the kind or field and, with the stamps read from `session.start`, the journal's and this build's build stamps.

Lenient decoding serves the read-only consumers that only display a journal: `status`, `events`, `watch` and the development tools that report on one (`audit`, `facts`, `stats`, `trialfacts`, `replay`, and `forecast` over an operator's state directory). They skip an event of a kind they do not know, ignore an unknown field at any depth, and say what they skipped in one line naming the lines, kinds and field paths involved. Everything else strict refuses is still an error, and a first line that is not a complete header of this build is refused before either mode decodes anything, so a lenient read never accepts another build's journal or a torn first header ([Reset and compatibility](runtime.md#reset-and-compatibility)); replay keeps its compatibility gates (another ruleset, a newer schema) before it decodes later events. A skipped event keeps its place in the journal: its envelope is read like any other, so its `seq` counts toward contiguity, later events may cite it as a cause, and looking it up by `seq` finds nothing. An unknown kind or field therefore never needs a `SCHEMA` bump ([ADR 0009](../adr/0009-compatibility-across-updates.md)): an older build still reads a newer journal for display, and never appends to one it cannot read whole.

The consumers that resume from, replay into or score the journals a simulator writes stay strict: the simulator (its resume, its history and its read of the simulated journal) and `bench` (its read of the journals its simulators wrote and the forecast scoring over them). They refuse an unknown kind or field as `run` does, because skipping an event they cannot read would let them act on a journal they do not understand, so a passive display never loosens the integrity of a journal something else will write. Tools that only measure or report on a journal, such as `stats`, stay lenient, and so does the `audit` the bench runs over a run's state directory after that strict read: it only reports, and what it skipped is a warning.

A historical `tier.change` event (removed by [ADR 0028](../adr/0028-remove-tiers.md)) is an unknown kind like any other, and this section is its rule. [ADR 0028](../adr/0028-remove-tiers.md) says read-only commands treat it as an opaque event; that describes the Go reader, which kept unknown kinds as opaque events, and the native decoder has none ([ADR 0092](../adr/0092-rust-native-implementation.md#decision): journals of the Go build are not read). A read-only consumer here skips it and reports it as skipped. Writers follow [reset and compatibility](runtime.md#reset-and-compatibility): `run` refuses a current-ruleset, current-schema, current-epoch journal that holds one and archives an older one with no newer dimension without appending; same-schema `reset --all` refuses it whatever the ruleset or epoch; different-schema `reset --all` archives without reading it.

Every newly started trial records `trial.start.roles`, one entry per loaded logical CPU. Each entry names its physical `core`, logical `cpu`, backend `instance` (the instance's first logical CPU), `workload` catalog ID and `schedule`. CPUs sharing an instance share its workload and schedule; separate instances may run different backends side by side. The schedule records sustained work, seeded load steps, idle/burst placement or synchronized parallel/serial phases, so R8's light-core position and R9's serial logical CPU are part of the recorded trial identity. `instances` records the corresponding live process placement; `roles` records the intended work even for a single instance. Older records without `roles` remain readable and supply no role-level evidence. A backend signal names its instance's physical core in `trial.progress.core` and `trial.end.core`; a core-local kernel report keeps the reporting CPU's physical core, including an SMT role.

Managed trials additionally record `trial.start.controller`: the controller process `pid`, its known `threads`, and the tested physical cores' logical `tested_cpus`. Its presence opts the trial into managed process-fault evidence. Without it, a kernel-reported fault of the trial's worker or the dashboard is still journaled as a diagnostic `trial.progress` with `fault` and `pid` but no `signal` or `core`, so it never changes the outcome. `trial.progress.fault`, when present, preserves a relevant fault's raw `pid` (possibly a thread ID), matched leader `process_pid`, `name`, `kind` (`segmentation`, `bus`, `illegal_instruction`, `general_protection` or `abort`), optional `scope`, boot-local `monotonic_ns`, optional kernel-reported `cpu` and resolved `core`, optional intended `worker_core`, and raw diagnostic `lines`. Executing and intended worker cores remain distinct. Located faults inside the tested set carry the progress event's failure `signal` and `core`; faults outside it are diagnostic observations only. A later unlocated coredump summary cannot erase an already-known executing location.

`trial.end.excluded` lists physical controller-host cores, omitted when empty. The Ruleset 13 fold preserves each as an exclusion with `kind: "host_core"` and its `core` in `exposure.observed.exclusions`; it does not erase the raw outcome, eligible duration or failures. Such an exclusion withholds adequate passing credit when it matches the class's tested position: its sole loaded physical core, R8's light core, or the physical core containing R9's serial logical CPU. An excluded different core does not invalidate that position, and a package-wide class with no selected position is not blanket-rejected merely because this list is nonempty. Containment errors, escaped processes or a missing backend separately produce `kind: "placement_withheld"`, preventing an adequate pass for the trial. There is no per-core R7 self-sufficiency or carried-fact exception. Placement and [matrix position-credit rules](workloads.md#coverage-matrix) still apply; managed placement and cpufreq transaction details are recorded in trial progress and recovery's sweep detail ([runtime](runtime.md#trial-confinement)).

The managed controller marker may also record `workers`, a map from known backend thread IDs to their saved instance leader PIDs. This preserves a worker trap's executing CPU without guessing membership from its executable name. A dynamically created thread not in the recorded identities requires exact scope or coredump evidence; an absent identity never invents a located core.

Managed backend failure progress also records optional `trial.progress.pid`, the exact instance launcher identity. Legacy events omit it. Matching a located process fault to an unexpected exit uses that identity, not merely the intended physical core: R9's distinct SMT instances can fail independently on the same core. An outside-tested fault suppresses only its own unexpected-exit charge; an independent computation error, stall or another process's exit remains evidence.

When a trial is closed on resume, its `trial.end` message names the last evidence rather than implying its `duration_s` measured the full run, and its `last_evidence` flag says so. After a crash, the last complete line of its samples (`samples.jsonl` or `samples.jsonl.gz`) adds optional `last_sample_s` (elapsed milliseconds rounded down to seconds), `last_sample_tctl_c`, `last_sample_min_mhz` and `last_sample_max_mhz` (minimum and maximum of the available loaded-core frequencies). A torn last line is skipped. Missing files or sensors leave their fields absent. For example, a crashed trial says `trial 0889 FAIL crash, last evidence 0 s after start, last sample 3 s: Tctl 71°C, 5420-5610 MHz`; without samples it retains `trial 0330 FAIL crash, last evidence 0 s after start`. An interrupted trial without a failure says `trial 0331 INCONCLUSIVE, last evidence 0 s after start: togi stopped during the trial`. A trial ended while togi watches it, including an orderly stop by signal, keeps its existing message and measured duration.

Failed trials with two or more loaded cores also carry optional `stalled_core` and `worker_stalled_ms` when persisted worker CPU times distinguish a unique first terminal stall (`workloads.md`, Trial outcome). The latter is milliseconds since trial timing began at the first observed unchanged reading. Both fields are absent for R6, R8 and R9, whose workers may be suspended by design, and for missing or ambiguous evidence, including ties and workers that advanced until the final sample. The message adds `, core NN worker CPU time stopped advancing at N ms after start (evidence only)` when both fields are present. This does not set the attribution field `core` or alter `duration_s`.

Every trial with loaded cores (R1–R9), whether watched through its end or closed on resume, carries optional `voltage_request_median_v` and `voltage_request_min_v`. For each complete persisted conditions sample with `pm_table` lanes, take the highest `voltage_request_v` among only that trial's loaded cores, then record the median and minimum over those maxima in volts. An even number of samples uses the mean of the two middle maxima as its median. Samples without lanes are skipped; no decoded samples leaves both fields absent, as on unsupported tables and on a simulator without its shared-voltage model; a shared-voltage simulator supplies the lanes and fills both. Both CCDs share VDDCR and the highest request wins: these fields describe the loaded cores' request, not an observed rail voltage, and exclude requests from idle cores outside the trial. The message adds ` | loaded voltage request median X.XXX V, min Y.YYY V` only when both fields are present. These measurements do not change trial outcomes or tuning decisions, and do not bump the journal schema.

The same trials also carry optional `voltage_requests_v` (loaded core ID → median request in volts), `top_requesters` (each loaded CCD's highest requesters, sorted by core ID, including cores within 1 mV of that CCD's highest median) and `ccd_mhz` (loaded CCD ID → median clock in whole MHz). Their window includes only complete samples with decoded `pm_table` lanes at or after the [warm-up boundary](workloads.md#warm-up-boundary). Fewer than 20 such samples omits all three fields. For each qualifying sample and CCD, take the median of the available loaded-core clocks; then take the median of those sample medians, rounded to the nearest whole MHz. A CCD with fewer than 20 available sample medians has no clock entry. Even medians use the mean of the two middle values. Session topology maps loaded core IDs to CCDs; unloaded cores never count. The message appends ` | top requester NN X.XXX V`, with several requesters comma-separated. These added fields bump neither the schema nor the ruleset, and the existing whole-trial voltage median and minimum remain unchanged. These fields are used only to order R7 partial loads.

A conditions-file open, read, gzip or complete-line decode failure, or a summary value that does not fit its recorded field, omits every sample-derived field above, together with `tctl_max_c`, and appends `session.warning` with `operation: "read conditions samples"`, the `trial` and the error, citing the durable `trial.end`. This warning does not change the trial's outcome. A missing file remains absent telemetry, and an unterminated final line remains a torn tail, not a decode failure (`workloads.md`, Conditions sampling).

Event kinds and event fields keep their names once released. A change of vocabulary in `GLOSSARY.md` renames prose, messages, help and docs, never the wire, and never bumps `SCHEMA` on its own. Configuration keys follow the same rule (`runtime.md`, Configuration).

`crash.detected.pstore`, when present, contains `path` (the absolute location of the archived dmesg record) and `lines` (its bounded tail). Recovery reads at most 128 prefix bytes per candidate to identify its full dump count and chunk part, then at most the final 3968 bytes of the selected record, keeping each record's raw reads within 4096 bytes and retaining at most 32 lines. It discards a partial first tail line when a newline follows it, otherwise keeps the bounded suffix of a long line without splitting a UTF-8 rune. Lines retain raw diagnostic text in JSON, escaped by JSON encoding like MCE lines; terminal renderers escape the message's path like other raw diagnostics. The message names the record but does not repeat its lines; `togi events --json --kind crash.detected` exposes them. This optional diagnostic never changes crash classification, attribution or replay decisions. No matching record leaves `pstore` absent. Archive or boot-span read failures append `session.warning` with `operation: "read saved pstore"` and the failed operation, then recovery continues without `pstore`; failure to append that warning remains fatal under the journal-write rules.

`boot.leave_reason` imports a pending tuning-boot recovery or refusal explanation from GRUB's `togi_leave_reason`, a compact JSON record with `id`, `count` and `reason`. Its journal fields are `reason_id` (the record's unique ID), `restart_limit_count` (0-3; 0 means unknown for the shell fallback), and `reason` (the bounded single-line explanation). It is informational evidence, not a tuning decision, and adds no journal schema bump. Importing it after `shutdown` does not turn a cleanly completed boot into a crash.

Before its first append, `run --tuning-boot` reads the pending record. Its first successful durable append resets GRUB's `togi_restart_count` once for that run. It imports the pending record as `boot.leave_reason` unless the current or an archived journal already contains the same `reason_id`, and clears the record only after that acknowledgement is durable. When resuming an interrupted dead end, it completes this handoff before replacing the pending record with the new dead-end reason; importing an unacknowledged record is itself the first durable append, while an already-acknowledged record can be cleared without another append. A durable preflight refusal resets the count just as any other durable append does; merely launching a process or opening the journal does not. Ordinary in-session runs and read-only commands neither reset the count nor import the record.

If a crash happens after `boot.leave_reason` is durable but before the GRUB record is cleared, or if clearing fails, the record remains pending. The next tuning-boot run finds its ID in the current or archived journal and clears it without appending a duplicate, including when a startup transition archived the original acknowledgement. One record is journaled once. A reason left by a return to the normal system remains in GRUB until the operator selects the tuning boot again. A count-reset, acknowledgement-lookup or reason-clear error retains the pending record and is an ordinary run error with journaled cleanup, not a journal-write emergency. When a dead-end reason cannot be written, `boot.saved_entry.reason_error` and its message preserve that diagnostic independently of the saved-entry clear result; the clear is still attempted.

Backend computation errors, early exits and stalls are recorded as `trial.progress` with their typed `signal`, affected `core` and signal-specific human detail as soon as they are classified, before `trial.end`. Recovery retains this durable evidence if the machine crashes before the trial ends; a recorded backend failure outranks the reset reason. `trial.signal` records load-step signalling, not backend failures.

Kernel-log cursor persistence uses additive `kernel_cursor` and `kernel_error` fields on the already-existing `config.loaded`, `trial.intent`, `trial.end` and `shutdown` boundary events; it adds no boundary events or kinds. Replay keeps the newest cursor separately for each event's `boot`. A failed read retains the prior cursor, and its diagnostic stays with the intersecting trial even if teardown or same-boot resume later succeeds. An unresumable cursor records the lost interval and may persist a fresh anchor, without clearing that trial's error. A torn or interrupted boundary resumes the previous durable cursor and deduplicates already-recorded MCEs.

`trial.start.window_start_ns` records the boot-local monotonic instant after profile readback, before workload startup, so the evidence window does not depend on wall time or backend setup duration. The whole profile is applied before `trial.intent`; if startup is interrupted before `trial.start`, recovery uses the intent timestamp as the evidence-window boundary.

Each `mce` records `monotonic_ns`, its boot-local kernel-log timestamp in nanoseconds, including zero. Its clock belongs to `from_boot` when present, otherwise the event's `boot`; it is not the time recovery appended the event. The field is additive under ADR 0009, with no schema or ruleset change. Events without it, including those written by 0.5.0, retain their previous attribution behavior.

The session refuses elapsed trial seconds that do not fit `duration_s` and monotonic nanoseconds that do not fit `window_start_ns` or `monotonic_ns`, preserving the conversion error. It validates the trial window start before launching the workload. It never clamps these observations or drops a known instant as though its time were unknown.
Kernel monotonic clock observations require nonnegative seconds and nanoseconds in `0..1_000_000_000`; malformed components are errors, never zero substitutes or normalized times. If the event clock cannot be read, no event is appended with an invented timestamp; the journal is latched unavailable and follows the journal-failure emergency path.
If refusing a time observation prevents recording a trial's escaped workers or unconfirmed cleanup, the session records a containment dead end before returning the conversion error; refusing a timestamp must not lose safety evidence. Sample elapsed milliseconds used as worker-stall evidence must be nonnegative, and last-sample elapsed milliseconds must be nonnegative with seconds that fit their journal field. Refused sample times follow the conditions-sample error policy below: omit sample-derived fields and record a warning without losing the trial's outcome or containment evidence.
When recovery has no usable monotonic interval, its recorded wall-clock interval must be nonnegative; an inverted interval is refused rather than credited as zero. Valid monotonic intervals remain independent of wall-clock corrections. Recorded workload-rotation counters must fit the platform's index type before workload selection; they are never saturated to another ordinal.

An MCE whose timestamp is inside the inclusive profile-applied through teardown window names its `trial` on a normal boundary read; an outside-window MCE has `between_trials: true`, no trial, and the message suffix `between trials (recorded only)`. These events are visible in `events`, in `status`'s between-trial evidence and in `watch`'s recent log, but supply no trial outcome or failure decision. Crash-recovery MCEs retain `from_boot`; replay checks previous-boot timestamps against that boot's open trial, while uncorrected MCA evidence retained into the next boot is associated with the preceding crash without comparing the two boot clocks.
Recovery records MCEs decoded before a kernel-log read error before its `backend.retry` wait, deduplicating them on retries and resumed recovery; their evidence eligibility is unchanged by the read error.
`trial.end.containment_error` records unconfirmed trial cleanup, including partial-start rollback. Such a trial is inconclusive as stability evidence and leads directly to the existing `containment` dead end, even if the trial was interrupted or produced a computation error. Replay retains this evidence if the process stops before recording the dead end; no next trial or tuning profile write follows.

When trial setup fails and its rollback reports further errors, such as output-cleanup diagnostics, `trial.end.reason` retains each error in occurrence order with its underlying causes, whether rollback confirms cleanup or cannot confirm it. If rollback cannot confirm cleanup, `trial.end.containment_error` retains the same errors and causes.

`task.start` uses `{"kind":"task.start","data":{"night":<seq>,"task":{"queue":"<queue>","ordinal":N}}}` within the ordinary envelope. Its generated `msg` is `night #<seq>: <queue> task <ordinal> started`; it renders plain under [Colors](#colors).

`trial.intent.cores` lists exactly the loaded physical cores for a set load; a single-core load uses `core` without `cores`. The complete applied `profile` includes idle cores. Validated decoding rejects empty loads and cores outside the recorded topology. `trial.start.roles` records each loaded logical CPU's core, CPU, instance, workload/content identity and schedule; shared instance IDs mean one process, never guessed thread layout. R8 records its light position, R9 its serial CPU. The intent freezes the content/configuration identities and requirement before execution; later configuration changes never reinterpret an in-flight trial.

### Shutdown reasons

`cycles` and `first_result` remain decode-only reasons written by Ruleset 12 sessions, never emitted by Ruleset 13. The [operator-ended night](runtime.md#night-declaration) uses the existing signal or reboot stop path. `command` remains for read-only commands.

### Ruleset 13 events

These kinds are additive. Their names and payloads must round-trip through the one typed payload enum; no meaning is inferred from `msg`. Each has a stranger-readable reason and `cause` sequences reaching its raw observations. All amounts are checked nonnegative durations/counts; unknown identity, edge, slope or observation is a distinct absent/unknown value, never zero. Payload `profile` means the complete CCD vector plus its per-core expansion; imported nonuniform profiles retain their original per-core shape.

The 11 removed per-core kinds are `tuner.decision`, `core.phase`, `checking.cycle`, `checking.step`, `checking.chain`, `hunt.start`, `hunt.group`, `hunt.end`, `hunt.skipped`, `combination` and `deepening.round`. New sessions emit none of them; historical readers retain their original meanings without folding them into CCD policy. `trial.carried`, `failure.carried` and `session.carried` are likewise historical formats after the [fresh transition](#transitions), not alternate new-policy inputs.

New kinds render plain except: `ccd.edge` with an observed failure, failed qualification and CPU-suspect `day.event` are red; `day.veto`, retreat/firmware-zero `day.step` and `ccd.cap` becoming shallower are yellow; successful qualification and promoting `day.step` are green. Color conveys no additional policy.

### Ruleset 14 events

These additive kinds preserve every released Ruleset 13 kind and field, including the distinct historical meanings of `ccd.edge` (U) and `ccd.cap` (statistical S). `SCHEMA` remains 1: old journals decode the same way; older strict readers still refuse unknown new kinds. The source fingerprint invalidates snapshots when the new decoder changes; snapshots are rebuilt from the authoritative journal.

Unit identities are externally tagged objects: `{"ccd":N}` or `{"core":N}`. `UnitMapping` contains `phase: "coarse"|"core"` and `units`, each with `unit`, physical `cores` and optional `parent`. A `UnitVector` always contains `cores` (the complete physical-core target-offset vector) and `mapping` (the complete unit mapping). A coarse offset expands uniformly to all its member cores; refinement retains each core's actual offset and coarse parent, never an averaged CCD approximation. Decoding preserves recorded discrepancies, as for `CcdVector`; consumers validate topology, exact membership/coverage and uniform coarse expansion before application.

### Trial activity

Ruleset 13 trial activities are `mapping`, `qualification`, `reproduction` and `control`. The intent names its night/task, exact requirement, class and actual applied profile. A re-qualification is qualification with its recorded purpose; filler is a distinct night task retaining its underlying mapping or qualification activity under [the filler rule](tuner.md#filler). An inconclusive retry keeps the same task/class and records `retry: true`; it does not erase consumed task time or unavailable-backend state. No intent carries a hunt, cycle or round. Stop/cleanup and recovery continue through the ordinary trial and transaction events.

`togi day` records raw daily observations in the existing session journal. These additive kinds retain their original observation meanings; Ruleset 13 consumes them through explicit [day events and intervals](#ruleset-13-events), never by pretending a daily boot was a tuning trial.

`day.unclean_end.evidence` has `crashed_mces` and `successor_mces`, each `{"kind":"unknown"}` (the log could not be read, which is not zero) or `{"kind":"read","corrected":N,"uncorrected":N}`, and `tail`, the crashed boot's kernel log tail: `{"kind":"missing"}` or `{"kind":"unreadable"}` (both unknown), `{"kind":"quiet"}` (read, no recognized error) or `{"kind":"faults","faults":[…],"logging_continued":bool}`. Each fault is `machine_check`, `graphics_timeout` or `graphics_reset` (with `driver`: `amdgpu`, `i915` or `xe`), `nvidia_xid` (with `code`), `oops` or `hung_task`, all with a `kind` field; each distinct fault appears once, ordered by its last occurrence, so the final entry is the last error logged; at most 16. `logging_continued` records whether the log held entries after the last error. Missing or unreadable evidence is never CPU evidence. The optional `asleep` (`suspend` or `hibernate`) is present when the crashed boot's log ended at a sleep entry with no exit after it; it is omitted otherwise and in records written before it existed.

Live faults. `day.fault` records a fault the kernel logged while the machine ran normally, once per boot: its identity is the `fault` and `monotonic_ns`; for a trap the fault part is its kind, `name` and `pid` alone, and a trap logged within 60 seconds of an earlier one of that identity is the same fault (the kernel line and the core dump record of one death), so a later crash that reuses the pid is another. The observer rebuilds the set it has recorded from the boot's `day.fault` events when it restarts. The envelope `boot` is the boot of the fault. Which faults are recorded, and when the log is read, is in [Live faults](runtime.md#live-faults); the [tuner](tuner.md#live-faults-and-load-mix) owns policy consumption of faults and checkpoint load mix. Adding the kind and the checkpoint field removed, renamed and retyped nothing, so the schema is unchanged.

Questions. Each `day.unclean_end` opens one question keyed by its `boot`. The first `day.answer` answers it; a later answer replaces the earlier classification input in journal order. An answer may name any recorded unclean end, pending or answered. Ruleset 13 derives the resulting event, veto, hold and provisional-retreat changes under [daily events](tuner.md#daily-events); raw ends and answers are never rewritten.

Crash records. `togi day record` appends `day.record` for a crash togi did not observe: a boot whose unclean end the journal holds, or an earlier crash it holds nothing about, such as a freeze before the day service existed. It is the one day kind a user writes by hand, so it refuses what the other kinds could not hold: no offsets, an offset outside [-50, 0], a boot with no `day.unclean_end`, and a boot a `day.record` already names (the first record per boot is the one that counts), and a second record of the same unobserved crash time, which with the boot identifies one crash. With `read_back` provenance the offsets are the ones the named boot's `day.unclean_end` holds and `at` is the time of that boot's last `day.boot_start`, `day.offsets_changed` or `day.checkpoint`; a boot with none of them cannot be recorded without entered offsets. Entered offsets must cover every core of the session's first `session.start`, so the record states a whole profile. The command prints the policy effect before appending; [the tuner consumes the record](tuner.md#manual-crash-records). A record answers no `day.unclean_end` question. It adds a kind and no schema bump.

Boot roles. An event's envelope `boot` is the boot it is recorded in, for every day kind. `day.unclean_end.boot` names the predecessor boot; `day.record.boot` names a crashed boot or unobserved crash time under its tagged payload. Each service invocation appends one `day.boot_start`, so one boot can hold several, and a later `day.boot_start` in a boot after a `day.clean_stop` reopens observation. `day.offsets_changed` is appended before the next `day.checkpoint`, and `day.clean_stop` after the final one. The interval that ends in a changed offset is ambiguous, so it is credited to no offset profile.

The observer holds the host lock and the state-directory lock, in the order of rule 5, for its whole life: `run` and `reset` fail with lock contention while it runs. `status` and `watch` read without locks.

Boot roles remain separate. Session recovery tracks a tuning boot only from tuning activity: day-only boots and their `journal.torn` are never `crash.detected` tuning crashes or same-boot tuning restarts. Day records cannot replace a tuning `shutdown` or close a pending trial. The tuner does consume them as **daily** evidence under Ruleset 13; imported records preserve their original role.

## Transitions

Ruleset 14 archives Ruleset 13 unchanged and starts the durably identified successor at verified stock under [the successor policy](tuner-ruleset14.md#10-journal-schema-and-architectural-record). `run` judges the first complete `session.start` before append: older dimensions with none newer archive unchanged; any newer dimension refuses unchanged. The day observer never transitions a session. S, old qualification conclusions and nonzero D never carry as permission.

Under the host lock then writer lock, durably record an archive/import-pending marker naming the immutable source session and destination identity before moving the journal; fsync marker and containing directories. Archive publication and new-session creation are recoverable separately. New IDs sort after existing source/marker IDs even if wall time moves backwards. A newer journal is never opened for tail repair or mutated before refusal. An older journal need not decode obsolete tuning kinds to be archived.

Create the successor with its build, actual context and verified all-zero baseline. Import original-identity raw daily observations and compatible `exposure.observed`, plus CPU-suspect events, stops and veto records needed to reconstruct the campaign. Preserve source identities and raw provenance; write `successor.imported` and `campaign.start {origin, history}` with complete/unreconstructible history. Missing history blocks nonzero exploration. A kill resumes the same manifest and appends only missing original identities; remove the pending marker only after durable commitment.

### Fact eligibility

Import only decodable eligible observations; unknown kinds/fields stay archived and are reported, never guessed into evidence. Deduplicate copies by original identity. Permanent reset boundaries stop raw tuning carry, but campaign ledger records are carried across them to preserve charges, stops and vetoes. Reset never renews allowance; missing reconstruction blocks nonzero exploration rather than supplying an unused ledger.

Imported all-zero intervals with matching firmware context and verified known duration form the CO-0 daily baseline. Nonzero records stay at their actual profiles, never get relabelled stock, and never supply synthetic exposure or a qualification. Missing interval/readback information is shown but earns no invented hours. In particular, pre-13 records journaled from #1224 onward remain available even though the tuning session starts over.

The three recorded freezes identified by [#1215 Q16](https://github.com/shgew/togi/issues/1215) are active whole-profile vetoes when imported or entered with `togi day record`, with their original provenance and nonuniform values retained. Import and manual entry of the same source must deduplicate rather than create additional strikes. Hardware acceptance still requires entering the records if they have not yet been journaled. An archived record's answers remain revisable in the new session through its original event identity.

### Decisions in the new session

Initialize applied D at verified stock with no imported hold or qualification conclusion. Recompute compatible raw night evidence under Ruleset 14; old-context facts remain history/hints and cannot bypass current controls. Reconstruct campaign events, stops and vetoes before nonzero exploration. `SCHEMA` remains 1 because the new kinds are additive; production reducer changes rebuild snapshots through their source-build fingerprint.

## Defects

Defect records retain their recorded build/fixes stamp, direction, affected identities and decision causes; observations and historical decisions are never rewritten. Older per-core defect answers remain archived history and cannot seed Ruleset 13. A too-aggressive unresolved finding blocks nonzero work; an explicit reset starts fresh under [Transitions](#transitions), rather than resurrecting removed per-core reset rules. The registry and renderer must name the actual CCD/profile decisions the new policy produces.

## Reset commands

Ruleset 13 removes `reset --core` with its policy and callers. `reset --all` records `command.reset` when the journal is append-compatible, establishes the permanent source boundary under the writer lock, then archives. A different-schema journal is archived unread. No reset emits `shutdown` on behalf of a hardware run it did not own. Archive errors preserve the recoverable pending state and release the lock; reopening completes the same operation or reports its failure. Reset never clears a daily event by relabelling it or fabricates clean-stop evidence.

## State file

`state.json` is the session's full folded state, as readable JSON ([ADR 0093](../adr/0093-journal-fold-and-snapshots.md#verified-read-cache)). Its top-level keys are `facts` (the journal's shared-facts `State`), `tuner` (the operator-facing projection), `recovery` (the run loop's recovery fold), `incremental` (the tuner's complete incremental state), `defects` (the defect index), `presentation` (watch's history and retained pre-end outcome), and `snapshot` (verification metadata). Runtime-only dependencies, such as the build's static defect registry, are rebound by the same build, not persisted.

The retained pre-end outcome contains only the last trial, its night/task/qualification view and tuner checkpoint needed for a forecast. It is cleared at the next `trial.intent`, `shutdown` or `crash.detected`. Deferred simulator publication may reconstruct that checkpoint once; a deferred marker is never persisted.

`snapshot` contains the source-build fingerprint, `prefix` (`last_seq`, raw byte length and SHA-256 of the complete journal prefix), and a SHA-256 binding the metadata and document. The fingerprint covers the production source of the reducers and their dependencies, not just a local `dev` version label. Modules that compile only under `cfg(test)` are left out, so a build that differs only in test code accepts the snapshot; any production change rejects it. Test-only files are named `tests.rs`, `*_tests.rs` or under a `tests` or `*_tests` directory in a crate's `src`, or listed in `crates/test-only.txt`. Checksums use deterministic JSON; map-entry sequences and sets have stable order, and shared evidence histories serialize as their logical sequence rather than their allocation layout. This state format has no migration or compatibility promise: a changed build replays the log instead. Neither the journal schema nor the tuner ruleset changes.

The journal never depends on the tuner; it publishes the document atomically: `StateDir::write_state` writes one compact JSON object and a newline to `.state.json.tmp`, fsyncs, renames it over `state.json` and syncs the directory. `jq . state.json` shows it indented. `read_state` is the raw document reader; verified readers check the build, document checksum and exact raw prefix before deserializing reducers.

Readers restore a verified snapshot and fold only events after its sequence. Missing or rejected snapshots fall back to full replay without creating, removing or rewriting files. A valid older snapshot is usable with its journal tail. Decoding, compatibility checks and history-only scans still inspect the journal: the cache does not hide an invalid line, replace archive evidence or answer a forecast anchored before the snapshot. Auditing independently checks the saved folds against the log; `run` never uses persistent cached reducers to skip its boot replay. Simulations started from copied state may restore the persistent folds; cold simulation remains the replay oracle.
The temp write must consume the complete projection before it can be renamed; a short write leaves the previous complete state in place.

The session publishes it under a typed policy chosen by the caller. `Live` (the default) publishes after every appended event. `OnFinish` (the simulator and benchmarks, which fold millions of events and read the projection only at the end) publishes once, as the last step of the run: after the final event (the `shutdown` or the dead end) and before the journal is handed back and closed, so a publication never follows the close. Both policies publish a last time at the end of the run. An exit that never appended an event publishes nothing, and a run that ended with the machine crashed or its journal latched publishes nothing, so a crash leaves the previous state in place for the next start to rebuild.

The `facts` projection owns schema/session/last sequence, topology, observed baselines, open intents, dead ends and backend content identities/provenance. `tuner` owns the [per-CCD and whole-profile state](tuner.md#per-ccd-state), with raw observation witnesses for D, S, U, holds and each coverage cell. It has no `phases`, `bios`, hunt, combination, round or checking-cycle policy projection.

A failed projection write appends `session.warning` with `operation: "write state projection"` and the error, then continues the session; it never triggers emergency zeroing by itself. The authoritative event is already durable. Persisting that warning does not attempt another projection write, so an unwritable state file cannot recursively generate warnings. A journal append failure, including failure to append the warning, remains fatal: after CPU family/model and driver codename validation it takes the emergency-zeroing path; before that boundary it exits without mailbox commands or SMN access (`runtime.md`, Preflight). Readers see either the previous complete state or the new complete state, never a torn file. On the next start, replay rebuilds a stale or missing projection and records `state.rebuilt` after a successful rewrite; if that rewrite fails, it warns and continues instead. A warning after a durable `shutdown` does not make the stopped boot a crash.

The projection exposes ordered tuning units with D/C/tagged U, qualification and outstanding coverage; whole-profile day state with successful applications, exact-profile holds, saved/proposed profiles, stops, events, vetoes and blockers; campaign consumption, provisional/reclassified counts and post-finish events; and night queues, measured time, mapping/filler cursors and qualification/reproduction progress. Any S/slope projection is labelled non-authorizing diagnostic. Unknown stays absent/tagged unknown rather than a zero sentinel; content identity remains distinct from path provenance.

`open` retains every intent without a result. An SMU intent is cleared by its citing write/error or a same-boot startup readback citing it; a trial intent by its end. Recovery closes prior-boot intents without manufacturing a completed workload. Dead-end evidence and the last decision's sequence/reason remain available even before their derived commitment is appended. The complete incremental state remains sufficient for replay to produce the same next query.

The journal's fold is fallible: `apply` returns an error, never panics, for a journal that cannot exist (a seq that does not follow the last, an event before `session.start`, a second `session.start`, a decision or baseline for a core the session lacks).

## Human-readable log

Each event's `msg` goes to stderr in an escaped representation, prefixed by local time and kind padded to 14 characters, so the system journal of a tuning boot reads as a narrative:

```
01:14:07 trial.intent   night mapping CCD0 offset -20 R8 light core 03, heavy neighbours
01:16:37 trial.end      trial 0413 PASS 120 s after warm-up
01:16:37 exposure.observed CCD0 R8 light core 03 at -20: 120 s eligible, no failure
```

Human rendering escapes untrusted controls before adding application-owned styling. C0 controls and DEL use visible `\xNN` escapes, except tab, newline and carriage return use `\t`, `\n` and `\r`. C1 controls (including U+009B CSI and U+009D OSC), Unicode line and paragraph separators, and bidi formatting controls and marks (U+061C, U+200E–U+200F, U+202A–U+202E and U+2066–U+2069) use `\uNNNN`; raw ESC is `\x1b`. Invalid UTF-8 bytes use `\xNN`. Other Unicode and already-visible escape text remain readable and unchanged, with one exception: the dashboard draws only its console character set ([runtime.md, Commands](runtime.md#commands)), so it writes `×`, `…`, en and em dashes and curly quotes as `x`, `...`, `-`, `'` and `"`, and any other character outside that set as `\uNNNN`. The same rule covers event kinds, including unknown kinds in read errors, journal-derived status fields (including BIOS context), archive notices, and dashboard messages and diagnostics, so one event cannot insert a terminal command, another rendered line or a bidi override. Application-owned ANSI styling and dashboard cursor controls remain active.

The journal's `msg`, other evidence fields, and raw `togi events --json` lines are never sanitized or restyled: the escaped text exists only at human rendering boundaries.

`togi events` renders the journal the same way:

```
togi events [--core <N>] [--kind <kinds>] [--trial <ID>] [--since <time>] [--until <time>] [--json]
```

- `--core N`: events that name core N in a typed field: `core`, `cores`, `class.cores`, `candidates`, a member's `core`, a `command.reset` target or the `core` of an SMU command. It also matches the `trial.end` of every trial whose `trial.intent` loads core N (its `core` or `cores`) and every `failure` of such a trial that names no `core`. A known-failure skip (a `failure` with `known_failure`) matches when the event it names matches, never by its `trial`. Session-wide events stay out. A trial that started before `--since` still counts: the filter reads the journal from its start and prints only the events inside the window.
- `--kind`: comma-separated known exact kinds, or a known group when the entry has no `.` (`trial` matches every `trial.*` kind). Names come from the binary's kind registry. An unknown name or explicitly empty list exits 2 with the error and valid names on stderr before reading the journal; a valid filter with no matches exits 0 with empty stdout.
- `--trial ID`: events whose `trial` is ID, or carried events whose original `source.trial` is ID. Source trial IDs can match copies from more than one source session.
- `--since` (inclusive) and `--until` (exclusive): a time window.
- `--json`: print the raw event lines instead.

All given filters must match. A torn tail is reported on stderr and left for the next `run` to record.

### Colors

The run log and `togi events` color the whole human-readable line according to its moment:

| Moment | Color |
|---|---|
| Trial ends with failure (`trial.end` outcome `failure`), `failure`, `crash.detected` | Red |
| Dead end (`deadend` event and `run` summary), incompatible-session refusal line (not an event) | Red, bold |
| Completed qualification or promoting day step | Green |
| Shallower cap, retreat/firmware-zero step, active veto, `tuner.warning`, `session.warning`, known defect or ruleset mismatch warning | Yellow |
| Inconclusive trial or `backend.retry` | Dim |
| Other new kinds and historical kinds not listed above | Plain |
| `unit.edge` observed failure | Red; other edge states plain |
| `climb.decision` promote/restore | Green; retreat/firmware-zero yellow; hold plain |
| `unit.stop` ceiling | Green; adverse/stopped/allowance-exhausted yellow |
| `campaign.charge` | Red; exhausted yellow |
| `campaign.reclassified` | Red when reclassified CPU-suspect; otherwise plain |
| `firmware.restoration` | Qualified/restored green; stepped-back yellow; saved/held plain |
| `unit.mapping`, `campaign.start`, `successor.imported` | Plain |

ANSI SGR is used when that output stream is a terminal (a character device such as `/dev/null` is not one) or `JOURNAL_STREAM` names that stream (its device and inode match, whatever the file type). A non-empty `NO_COLOR` disables ANSI even in the system journal. `events.jsonl`, `state.json` and `togi events --json` stay uncolored. When `JOURNAL_STREAM` names that stream, red and red-bold lines start with `<3>` so systemd stores them at priority err (`SyslogLevelPrefix=` is on by default), including with `NO_COLOR`; no other line gets a priority prefix, and terminals outside the system journal never get one. `togi events` uses the same rules on stdout.

Every new event kind names its row here, or plain.
