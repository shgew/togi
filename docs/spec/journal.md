# Journal and state

Normative rules for what togi records. Goal: anyone, human or agent, reading only the journal can reconstruct everything togi did and why, without reading code.

## Files

All files live in the state directory, default `/var/lib/togi`:

| Path | Role |
|---|---|
| `events.jsonl` | The journal of the current session: one JSON event per line, append-only, source of truth |
| `state.json` | The current state, a projection of the journal for readers |
| `trials/<trial-id>/` | Per-trial work directory: backend config files, raw stdout/stderr (`stdout.log`, `stderr.log` in each instance directory), backend result files |
| `trials/<trial-id>/samples.jsonl` (`.gz` once the trial ended) | Fsynced per-second conditions: milliseconds since trial timing began (`elapsed_ms`), optional `tctl_c`, CCD temperatures by label (`tccd_c`), all 16 physical cores' frequencies in whole MHz by core ID (`core_mhz`, idle cores included), cumulative worker CPU milliseconds by loaded core ID (`worker_cpu_ms`), package and aggregate CPU-core power in watts (`package_power_w`, `cores_power_w`), and decoded per-core SMU lanes (`pm_table`). Core power comes from the package's fixed `intel-rapl:0:0` subdomain, with its own baseline and wrap range; missing or invalid readings and unexplained decreases omit the value, never zero ([Conditions sampling](workloads.md#conditions-sampling)). |
| `archive/<session-id>.jsonl` | Journals of sessions ended by `reset --all` or by a transition |
| `archive/<session-id>-trials/` | The `trials/` directory of an archived session |
| `archive/<session-id>-compat-pending` | Crash-recovery marker while a journal this build cannot read is archived without being appended to (`reset --all` or a transition of an unreadable journal); removed on completion |
| `archive/<session-id>-carry-pending` | Marker that the session a transition archived has not yet seeded a new session; removed once a journal records its `session.carried` or passes the point where one applies |
| `archive/<session-id>-reset-all` | Permanent, empty reset boundary: this session and every older source are excluded from future fact, candidate-solo-limit and failure-point carry |
| `lock` | Held, exclusive and non-blocking, with `std::fs::File::try_lock` by the one process allowed to write the journal; a second writer fails at once with a contention error and never waits |
| `.events.jsonl.tmp`, `.state.json.tmp` | Temporary files of a torn-tail repair and of a `state.json` publication; a leftover is overwritten, never read as truth |

Optional `pm_table` contains six 16-element arrays indexed by physical core ID (0–15): `power_w`, `voltage_request_v`, `temperature_c`, `c0_pct`, `cc1_pct`, and `cc6_pct`. Residency units are percent. Voltage requests do not describe separate rails: both CCDs share VDDCR and the highest request wins. Only table version `0x620205` with the exact supported size and core IDs 0–15 in CCD/slot order (0–7 on CCD0, 8–15 on CCD1) is decoded (`workloads.md`, Conditions sampling). The sampler never waits for the single-flight background reader: a completed reading can be reused within two seconds of its read's start. Unavailable, unsupported, failed or overdue reads omit the entire field, never insert zero lanes; a read taking 100 ms or longer is discarded and readings older than two seconds are omitted.

Once per run, `preflight.check` with `check: "pm_table"` records in `detail` and `msg` the table version seen and whether per-core lanes decode. If no version can be read it says the version is unavailable; the simulator without `shared_voltage` says it reports no lanes, while an enabled machine identifies its synthetic voltage requests and clocks. The check uses the same single-flight reader with at most the remaining 100 ms read budget and explains pending/overdue reads or an unsupported topology. This informational check always has `ok: true`: unsupported or failed diagnostic reads are not preflight failures.

Retention: every trial directory is kept, whatever the trial's outcome; nothing prunes them. After its writers have stopped and before appending `trial.end`, the session gzip-compresses `samples.jsonl` to `samples.jsonl.gz` and each instance's `stdout.log` and `stderr.log` to `stdout.log.gz` and `stderr.log.gz`. Each file is written whole under a temporary name, fsynced, renamed into place and its directory fsynced before the plain file is removed; the removal is then synced too. A reader always finds one complete form. A crash in between leaves readable plain and/or compressed files; resume reads the samples, retries compression and closes the interrupted trial. All readers open the plain file first and fall back to the compressed one. Files remain plain when containment failed and writers may still be alive. Compression errors retain the plain file until the compressed form is durable and produce a nonfatal `session.warning`, not stability evidence (`runtime.md`, Exit codes). Simulations generate samples only when asked; in-memory simulations create no files, while `tools/sim --samples` compresses them on trial end too.

## Rules

1. **Everything is an event.** These are all events:
   - every action with an effect outside togi's memory: SMU command, process start, signal or stop, scope creation, file written for a backend, sysctl, GRUB change;
   - every observation that feeds a decision;
   - every decision.

    Exceptions: `SIGSTOP`/`SIGCONT` cycles too frequent to record one by one. R3 and R4 cycles are recorded as the schedule and seed at trial start and as counts at trial end. R6 bursts are recorded as a `trial.progress` when they begin and as counts in a `trial.progress` at trial end. R7 runs separate trials on each loaded set of cores, not in-trial CCD phases. A refusal of a journal written by a newer schema, ruleset or evidence epoch, or of a journal holding an event this build cannot decode, writes no event into the refused journal: the build that wrote it must remain able to resume it. The reason goes to stderr, which is the system journal in a tuning boot; persisting the leave reason in GRUB and clearing its saved entry for that refusal also write no event there. A later tuning-boot run with a writable journal imports the pending record as `boot.leave_reason` below. Restart-limit recovery likewise persists its record outside the journal because the failing service may never have opened one. A transition archives an older journal without writing to it, for the same reason (Transitions, below).
2. **Intent before action.** An action that may crash the machine, such as an SMU write or a trial start, is appended and fsynced before it happens. On the next boot the last intent without a matching result is the in-flight action. Every event is written with a single `write` of its whole line and fsynced before `append` returns, and only then is it published to the in-memory journal, so a crash loses at most the line being written (rule 6); closing the journal fsyncs it. Before the write, the line is decoded again: an event that would not read back (a payload the schema refuses) is an error, nothing is written and no seq is consumed; an invalid cause (not earlier than the event), an encoding error or a first event that is not `session.start` is refused the same way and does not poison the writer. Locking a state directory creates it and every missing ancestor durably, and opening the journal syncs the state directory after it creates `events.jsonl`, so a new journal file survives a crash. An ancestor may be a symlink to a directory, as `/var` is on macOS: the directory below it is synced in the directory the link names, while the state directory itself is never a link. `run` appends `shutdown` when it stops on a signal, at a dead end, or on reaching the requested cycles; other exits may record restoration but never `shutdown`, so a later boot whose journal ends without `shutdown` is treated as a crash (`workloads.md`, Failure signals). Simulated storage fsyncs nothing, because a simulated crash cannot lose written data (Simulated storage, below).
   A short write is an append failure. After a write or fsync error the journal is poisoned: every later append returns the first failure without touching the disk, until the state directory is reopened, because a complete line may have survived the error and the in-memory sequence is no longer authoritative. Reopen replays surviving complete lines and repairs a partial tail before assigning another sequence, so an event whose append failed is either absent or present once. Closing a poisoned journal does no I/O and hands back the locked state directory. Poisoning never blocks the session's emergency zeroing, which needs no journal.
   A `deadend` without its `boot.saved_entry` (for a GRUB action) or without `shutdown` is an interrupted dead-end action, not permission to resume tuning: the next `run` completes the missing action and records `shutdown` before doing other work; a `run` without `--tuning-boot` cannot clear GRUB's saved entry and only records `shutdown`. A `boot.saved_entry` tied to that dead end is not cleared again. Once `shutdown` is present, the next `run` starts normally and re-evaluates dead-end conditions.
   `smu.intent` and `smu.write` are not appendable through the generic `append`; it refuses them. `append_smu_intent` writes the durable `smu.intent` and only then returns a receipt, a value that cannot be built, cloned or copied outside the journal crate and is bound to the journal that minted it. `append_smu_write` consumes the receipt, writes `smu.write` caused by that intent, and returns a token whose seq the readback cites. A receipt from another or a reopened journal is refused, and a receipt is spent whether or not its write succeeds. A failed or poisoned journal mints no receipt. On the simulator's unsynced journal (`lock_unsynced`, below), whose files are never fsynced, `append_smu_intent` writes the buffered events through to the file before returning the receipt, so the receipt proves the intent's order and that it survives the process exiting, not a power loss; that journal's writes reach only a simulated SMU.
3. **Decisions name their cause.** A decision event carries `cause`: the `seq` numbers of the events it was derived from, plus a `reason` in plain words. A step-back that rests on two failures cites both, the later one first.
4. **The journal wins.** On start, togi rebuilds the state by replaying the journal. If `state.json` disagrees with the rebuild, it is rewritten and a `state.rebuilt` event records the difference: its `fields` holds each top-level key of `facts` that differs (`last_seq`, `cores`, …), `tuner` when the tuner projection differs and `state.json` when the file is missing or unreadable. A rebuild that names `last_seq` marks a snapshot that was behind the journal, as after a crash between two writes; the audit reads it as stale, not wrong.
5. **One writer.** `run` takes the host lock, then the state-directory `lock`, then prepares carry, and holds both locks through the session and its cleanup. The state-directory lock is held before any carry scan, archive or marker change, including a transition before its new journal exists. `reset` follows the same lock order and holds the state-directory lock through marker changes and archive completion; it refuses while a `run` holds it. The simulator takes the state-directory lock before carry and holds it through each simulated boot's session. Dropping the locked directory, or closing the journal and then dropping the directory it returns, releases the lock. `status`, `events` and `watch` only read, without the lock. `watch` projects the trial, progress, hunt groups, deepening checks and per-core replay, and logs `session.start` (`session.carried` is not a line of its own; the carried `core.phase` changes that follow count into it), a resume line for each `config.loaded` after the first, `trial.end` (a passing trial alone is left out; `trial.intent` only names the line), `failure`, `mce` between trials, `crash.detected`, `tuner.decision`, `core.phase`, `checking.cycle`, `checking.step`, `checking.chain`, `hunt.start`, `hunt.group`, `hunt.end`, `hunt.skipped`, `combination`, `deepening.round`, `backend.retry`, `session.warning`, `defect.found`, `deadend`, `command.reset` and `shutdown`. It does not log `host.ranking`, `tuner.warning` or `profile.change`. `reset --core` appends no `shutdown`. Archiving a session is one transaction. First the marker its kind needs becomes durable: for `reset --all` the permanent reset boundary, for a transition the carry marker (an earlier pending carry stays the source). Then the journal appends `command.reset` (for `reset --all`) and `session.archived`, fsynced, and the writer is spent. The state file is removed, `trials/` moves to `archive/<session-id>-trials/` and `events.jsonl` moves to `archive/<session-id>.jsonl`, each step synced before the next and each safe to repeat, with no-replace renames. The transaction refuses before appending anything when the archive journal or the archive trial directory of that session already exists. The session's own `reset-all`, `carry-pending` and `compat-pending` markers do not refuse it: they are what a retry after a failed or interrupted archive finds, and the retry completes the transaction. Opening a journal that records its own `session.archived` finishes that move first (it looks at the recorded events, not at whether the last line is `session.archived`, so a torn tail after it does not hide it) and continues with an empty journal. For a journal this build cannot read, `reset --all` cannot append: with the lock held it makes the kind's marker durable, writes and fsyncs a `compat-pending` marker, removes the state file, moves `trials/` and then `events.jsonl` without writing to the old journal, syncs both directories, and removes the marker. A following open or archive resumes an interrupted move only if that marker exists; an archive path collision without the marker is refused. If the archive exists but `events.jsonl` is already gone, the next journal open removes the marker and syncs the archive directory under the writer lock.
   `watch` also logs `checking.step` and `checking.chain`, including request-order provenance, and identifies active partial trials in plain words while showing their loaded cores.
   If an unreadable journal already recorded its own `session.archived`, `reset --all` completes that recorded move without creating a compatibility-pending marker, including when `trials/` was moved before the interruption, but still makes the permanent reset boundary durable at that session before the move completes.
6. **Torn tails are expected.** A crash can leave a partial last line: bytes after the last newline are a torn tail, never an event, even when they happen to parse as JSON. A complete line that does not decode, a gap in `seq`, a first event that is not `session.start` or a cause that does not precede its event is corruption, never repaired: opening fails and the file is not modified. Replay drops a torn tail and records a `journal.torn` event with the discarded bytes, hex-encoded, without ever losing them: opening the journal writes its complete lines followed by that event to `.events.jsonl.tmp` in the state directory, syncs it, renames it over `events.jsonl` and syncs the directory next to the rename, before appending anything else. Until the rename, `events.jsonl` still ends in the torn bytes, so a failure or crash at any step leaves either the torn bytes or their durable record, and the next open repeats an unfinished repair, recording the bytes exactly once. The open reports the repair record's seq. The first line is the exception: before any of this, the first-header check of `run`, `status`, `events` and `watch` reads it, terminated or not. A nonempty first line that does not decode as a header of this build's journal, truncated JSON with no newline included, is refused as another build's journal or a torn first header (the two cannot be told apart): it is never treated as a torn tail, never repaired or truncated, and the file is not modified. The operator keeps it aside by hand ([Go to Rust cutover](../howto.md#go-to-rust-cutover), [Reset and compatibility](runtime.md#reset-and-compatibility)). Only a first line that decodes as a complete header but has no newline is a torn first line. It leaves an empty journal: nothing happened before `session.start`, so nothing is recorded and the line is truncated in place and synced. A failed open leaves no writer and releases the lock.

Reading never needs the lock and never writes: `Recording::read` parses a whole journal (events, an O(1) lookup by seq, and the torn tail as a value) and `EventReader` streams complete lines, both checking the same promises (contiguous seq from 1, `session.start` first, causes before their events) and ending at the first error. Both decode strictly; their lenient forms (`Recording::read_lenient`, `StateDir::recordings_lenient`, `EventReader::lenient`) are what read-only consumers use (decoding rules below) and report what they skipped, as a `Skipped` value with one human line.

Simulated storage. Tests and simulations run in memory: `StateDir::simulated` takes a `MemFs`, a shareable in-memory filesystem whose handle a simulation keeps across simulated reboots and can dump to disk on request. It injects faults (fail the Nth write, sync or rename, short writes, fail the publication of `state.json`) for the crash-resume tests and counts every mutating operation. It keeps the ordered history of operations and reads only for a test that calls `MemFs::record_history` before the operations it inspects; ordinary simulations keep none. `tools/sim --state-dir` uses `StateDir::lock_unsynced`: a directory on disk whose files are never fsynced and whose journal buffers 64 KiB of events in memory, writing them when the journal is read back, archived or closed and whenever the buffer fills; a kill of the process loses the buffered tail. Both constructors and `MemFs::dump_to` are on clippy's `disallowed-methods` list and approved only for the simulator crates, `tools/sim` and the session's tests; `StateDir::lock` is the only constructor a real `run` uses. The fault matrices prove each failure path recovers, not that data survives power loss.

Simulations never sync files or directories, including sample compression with `--samples`; their disk output is an inspection artifact, not power-loss evidence. Tests replace durability operations with recording or fault-injecting adapters, including kernel filesystem tests, so no test flushes a real drive. Production journals, samples and compressed trial files retain the durability rules above.

Warm resume is the contract of `togi-simrun` and the session, not of the journal. A run that ends cleanly hands back a `ResumeCapsule` with its journal: every fold of the journal's events (the shared facts, the tuner state, the recovery fold and the defect state), bound to the journal's session and last event. A caller that runs the same journal again, as the simulator does after a simulated crash or restart, passes the capsule in, and the session adopts it instead of replaying the journal, only when the capsule's session and last event are the journal's and the defects it judged by are the run's; any other capsule is ignored and the journal is folded from its events. A run that ended with the machine crashed hands back its capsule, which holds what the crashed boot folded, while the state file stays as the last publication left it; a run whose journal latched hands back none. `ResumeCapsule::publish` writes, into the state directory, the state document a `Live` run would have left after the capsule's last event, for a caller whose `OnFinish` run crashed before publishing. A warm simulated reboot goes further and keeps the open journal: `Journal::reboot` writes its buffer through, sets the new boot and a new journal identity (receipts of the earlier boot are refused) and reads nothing from the file, and `togi_session::prepare_kept` makes `prepare`'s decisions from that journal's events. A run that adopts a capsule skips the saved-state check, since the run before it left `state.json` pending on purpose; every other startup step still runs on adopted state: compatibility, dead-end resume, crash recovery, the defect check, preflight, the sweep and same-boot resume. `ResumeCapsule::verify` replays the events into fresh folds and names the first part that differs (facts, tuner, recovery or defects), that the capsule's last event is not the events', or that the state document published from the capsule's folds does not survive a JSON round trip unchanged or differs from the cold fold's; the simulator verifies after every Nth crash with `--verify-every N` and when the invocation ends, and `--cold-boots` never passes a capsule, as `togi run` does not. A new invocation reads the journal from disk, and `togi run` replays at every boot and writes `state.json` after every append. The simulator's tests pin that warm and cold boots leave the same events and state.

## Event format

One JSON object per line:

| Field | Meaning |
|---|---|
| `seq` | Positive integer, +1 per event from 1 within a session |
| `time` | RFC 3339 UTC timestamp with as many fractional digits as it needs |
| `boot` | Kernel boot ID (`/proc/sys/kernel/random/boot_id`) |
| `mono_ms` | Boot-local CLOCK_MONOTONIC milliseconds, truncated; the event an append publishes is the one its line decodes to, so a live fold equals a replay. Absent when unknown (events `reset` appends are no trial evidence), and an explicit `0` is a real zero. Used to match evidence to trials despite wall-clock jumps |
| `cause` | Array of the `seq` this event follows from, each earlier than the event; omitted when empty |
| `kind` | Event kind from the catalog below |
| `msg` | Human-readable description generated by the journal from the payload when it appends, stored as evidence and never regenerated on read; producers never write it. Raw diagnostic text stays unsanitized; human output escapes controls |
| `data` | The kind's payload object |

Diagnostic error text names the failed operation, followed by its retained causes in order, separated by `: `. Error messages do not embed their source's message; `togi_machine::error_chain` (also exported by `togi-render`) renders the chain without suppressing equal or substring text. A transparent forwarding error adds no operation of its own. Multiple failures retain their order and render each member's chain. This changes diagnostic prose only, never event kinds or fields, and recorded messages remain unchanged on read.

Fields appear in the order above. Payload fields are snake_case and carry units in their names (`duration_s`, `period_ms`, `tctl_max_c`); values use the vocabulary in `GLOSSARY.md`. Cores are always `core` (the kernel `core_id`, 0–15); logical CPUs are always `cpu`. Values are typed and the schema refuses what does not fit: a core set (`cores`, `candidates`, `top_requesters`, a group) is a sorted array without repeats; a per-core value (`profile`, `offsets`, `voltage_requests_v`) is an object keyed by core ID; a workload (`workload`, `workloads`) is the id of a catalog workload and an id outside the catalog is a decode error (an idle class has no `workload`); an offset the session decided (a profile, a target, a failure point, a decision's offsets) is an integer within −50…0, while an offset only observed (the baseline, a readback) is any integer; ordinals (`cycle`, `step`, `hunt`, `group`, `round`, `combination`, `part`) and `seq` references are positive integers and are absent, never `0`, when they do not apply. Optional fields are omitted when absent and optional flags when false, so absence is never an empty string, `0` or an empty list standing for “none”. Four booleans are required instead and always written, `false` included: `config.loaded.file`, `preflight.check.ok`, `session.carried.failure_points` and `mce.corrected`; a payload without one is a decode error. Closed vocabularies (activity, decision, outcome, attribution, hunt stage and result, dead-end condition and action, shutdown reason, …) have no empty or unknown value. Nested exceptions are `session.start.cores` (per-core `core`, `ccd` and `cpus`), `session.carried.sources` and `session.carried.carried` (per-core carried limits and failure points, each with the `session` and `seq` it came from), `trial.start.instances` (per-core `core`, `cpus`, `pid` and `scope`), carried facts' `source` (original provenance) and `class` (trial-class identity), `hunt.group.probe` and `hunt.group.held` (core/offset members), the `members` of `hunt.end` and `combination`, and `checking.chain.groups` (top-requester tie groups).

`config.loaded` carries `config`, a journal-owned snapshot of the effective configuration, next to its `build` stamp, `path` (where the configuration was looked for), `file` (whether one was found) and the optional kernel-log cursor boundary. The snapshot is a type of the journal crate, not of `togi-config`, and its wire shape is pinned by a golden test, so a change to the configuration never changes the journal format silently: a change to the snapshot is a journal format change and follows [ADR 0009](../adr/0009-compatibility-across-updates.md)'s additive rule (a new optional field, like a new event kind, needs no schema bump, because read-only consumers ignore a field they do not know and skip a kind they do not know, as decoding rules below say; a change that renames, removes, retypes or tightens a field, or makes an optional one required, does). `config` holds `start_offsets` and `candidate_solo_limits` (core ID → offset), `durations` (`search_trial_s`, `short_trial_s`, `checking_trial_s`, `checking_idle_s`, `checking_all_core_s`), `evidence` (`miss`, `rate`), `checking.cycle` (the regimes of a checking cycle), `dead_ends` (`inconclusive_in_a_row`, `stray_crashes_in_a_row`), `backends` (`mprime` and `ycruncher` store paths) and `backend_user`; every setting is written, and an unset backend path or backend user is `null`. Decoding checks what the snapshot's own types check (core IDs, offsets, regimes, unsigned integers; an unknown field is refused by a writer and ignored by a read-only consumer, like any other) and records the values as written, without the configuration's policy ranges: a journal stays readable when the configuration later changes what it accepts. The consumers that rebuild a configuration from a recorded snapshot (`togi-config`'s `Config::from_snapshot`, used by the simulator's resume and the tuner's fold) validate it as a configuration file is validated and refuse one this build would refuse.

Every build stamp is a `build` object with `version`, `rev` (absent when unknown), `ruleset`, `schema`, `fixes` (absent means 0) and `evidence` (the evidence epoch). The first event is `session.start` with the build stamp, the session ID and the cores; `config.loaded` carries the build stamp at every start or resume. The first line of a journal, its `session.start` envelope with the build stamp, is the compatibility envelope: its shape never changes across schemas, so any build can read the stamp of any journal from that line alone (`StateDir::live_build`) and judge it before decoding the rest. The durable epoch, ruleset and schema of a session are those of `session.start`; a later `config.loaded` refreshes only `version`, `rev` and `fixes`. This build stamps its tuner ruleset, its tuner evidence epoch and `togi_journal::SCHEMA`. The Rust journal starts its own schema numbering at 1; the schema increases only when an existing kind or field is removed, renamed or retyped. Added kinds and fields do not bump it: an added field carries a serde default, so newer builds read older journals, and a journal of a newer schema is refused. Older journals are archived by transition and seeded with their eligible facts, solo limits and failure points as below.

`Build::verdict(recorded, operation)` compares the schema, ruleset and evidence epoch separately and answers `Use`, `Archive` (move the journal aside without appending to it) or `Refuse` naming the first dimension that settles it. Any newer dimension refuses a resume even when another is older.

| Operation | Use | Archive | Refuse |
|---|---|---|---|
| Resume (`run`, and `doctor`'s checks) | all three equal | an older dimension and no newer one | any newer dimension |
| Append (`reset --core`, `run` after a transition) | all three equal | never | any difference |
| ResetAll | same schema | a different schema | never |
| Inspect (`status`, `events`, `watch`) | same schema | never | a different schema |
| Replay (dashboard history, `tools/replay`) | schema not newer and same ruleset; the epoch is ignored | never | a newer schema or a different ruleset |
| History (archives, carry, facts, statistics) | a schema from 1 that is not newer | never | schema 0 or a newer schema |

Read-only dashboard replay accepts a recording whose schema is not newer than this build's and whose ruleset is the current one, and refuses any other ruleset before decoding its events, because the dashboard projection uses the current tuning rules. It ignores an incomplete final line without changing the journal. Every reader preserves the recorded `msg` unchanged, including diagnostic text and vocabulary from older builds; decoding a payload never regenerates its message.

There is no schema translation and no reading of journals written by the Go implementation: its journals, `state.json` and archives are not read, never archived and never carried from. Go and Rust cannot share a state directory. Before the first Rust boot the owner moves the Go directory aside (`/var/lib/togi` to `/var/lib/togi-go`) and the cutover starts a fresh session in a new `/var/lib/togi` ([Go to Rust cutover](../howto.md#go-to-rust-cutover)); there is no rollback to the Go build. A journal whose first line is not a complete header of this build, such as a Go one or a header torn by a crash, is refused by `run`, `status`, `events` and `watch` with exit 1 before any later line is decoded, any lock is taken or any file changes ([Reset and compatibility](runtime.md#reset-and-compatibility)). Carry, facts, defects, statistics and fitting read one vocabulary, that of `SCHEMA`.

Session IDs are `YYYYMMDDTHHMMSSZ`, a UTC second, optionally followed by `-N` with `N` ≥ 2, and are validated wherever they are parsed. While holding the state-directory writer lock, a collision with `archive/<id>.jsonl`, `archive/<id>-trials/` or any marker of that ID chooses the first free `-2`, `-3`, … suffix (checked arithmetic: running out of suffixes is an error). A new ID must also sort after the newest reset boundary: if its timestamp is at or before that boundary, allocation starts at the boundary and takes its next numeric suffix, including after a backwards wall-clock change or deletion of the discarded archives. IDs order by timestamp and then numerically by suffix: the unsuffixed ID first, then `-2` through `-10` and beyond. Archive and trial paths are derived from the ID; a path recorded in an event is never trusted, which is why `session.archived` carries only the session. `archives()` lists the regular `<id>.jsonl` files in that order, and markers are listed by session and kind.

Build compatibility diagnostics consistently identify the program as togi, regardless of the recorded version.

Decoding is strict for writers and lenient for read-only consumers; there are no opaque events. Both refuse what a type cannot hold: malformed JSON, a missing required field, a value outside its type (a seq of `0`, a core above 15, a decided offset outside −50…0), a word outside a closed vocabulary, a damaged envelope, a first event that is not `session.start`, a gap in `seq` and a cause that does not precede its event. Apart from the first-header refusal below, such an error names the line and, when the envelope names a kind this build knows, the kind.

Strict decoding serves `run`, `reset` and every path that appends, including the decode of a line before it is written (rule 2). A kind this build does not know, or an unknown field anywhere in an event (the envelope, the payload, a nested object, the members of an internally tagged enum such as `smu.intent` or the schedule of `trial.signal`), is a decode error that names the line, the kind and, for a field, its path (`data.cores[0].extra`; `extra` for an envelope field). A journal with such an event cannot be read by this build for writing: whether it is archived, refused or ignored is the `Build::verdict` of the operation (table above), and a current-ruleset, current-schema, current-epoch journal with an undecodable event is refused for `run` and `Append` with exit 16 even after a BIOS change. Older journals are archived without decoding their events; `reset --all` archives a journal of a different schema without appending; an undecodable same-schema journal is refused before it is modified. Refusals name the kind or field and, with the stamps read from `session.start`, the journal's and this build's build stamps.

Lenient decoding serves the read-only consumers that only display a journal: `status`, `events`, `watch` and the development tools that report on one (`audit`, `facts`, `stats`, `trialfacts`, `replay`, and `forecast` over an operator's state directory). They skip an event of a kind they do not know, ignore an unknown field at any depth, and say what they skipped in one line naming the lines, kinds and field paths involved. Everything else strict refuses is still an error, and a first line that is not a complete header of this build is refused before either mode decodes anything, so a lenient read never accepts another build's journal or a torn first header ([Reset and compatibility](runtime.md#reset-and-compatibility)); replay keeps its compatibility gates (another ruleset, a newer schema) before it decodes later events. A skipped event keeps its place in the journal: its envelope is read like any other, so its `seq` counts toward contiguity, later events may cite it as a cause, and looking it up by `seq` finds nothing. An unknown kind or field therefore never needs a `SCHEMA` bump ([ADR 0009](../adr/0009-compatibility-across-updates.md)): an older build still reads a newer journal for display, and never appends to one it cannot read whole.

The consumers that resume from, replay into or score the journals a simulator writes stay strict: the simulator (its resume, its history and its read of the simulated journal) and `bench` (its read of the journals its simulators wrote and the forecast scoring over them). They refuse an unknown kind or field as `run` does, because skipping an event they cannot read would let them act on a journal they do not understand, so a passive display never loosens the integrity of a journal something else will write. Tools that only measure or report on a journal, such as `stats`, stay lenient, and so does the `audit` the bench runs over a run's state directory after that strict read: it only reports, and what it skipped is a warning.

A historical `tier.change` event (removed by [ADR 0028](../adr/0028-remove-tiers.md)) is an unknown kind like any other, and this section is its rule. [ADR 0028](../adr/0028-remove-tiers.md) says read-only commands treat it as an opaque event; that describes the Go reader, which kept unknown kinds as opaque events, and the native decoder has none ([ADR 0058](../adr/0058-native-rust-rewrite.md): journals of the Go build are not read). A read-only consumer here skips it and reports it as skipped. The writers follow their own verdicts (runtime.md, Reset and compatibility): `run` refuses a current-ruleset, current-schema, current-epoch journal that holds one and archives an older one, which has no newer dimension, without appending; `reset --core` and a same-schema `reset --all` refuse it whatever the ruleset or epoch; a different-schema `reset --all` archives without reading it.

When a trial is closed on resume, its `trial.end` message names the last evidence rather than implying its `duration_s` measured the full run, and its `last_evidence` flag says so. After a crash, the last complete line of its samples (`samples.jsonl` or `samples.jsonl.gz`) adds optional `last_sample_s` (elapsed milliseconds rounded down to seconds), `last_sample_tctl_c`, `last_sample_min_mhz` and `last_sample_max_mhz` (minimum and maximum of the available loaded-core frequencies). A torn last line is skipped. Missing files or sensors leave their fields absent. For example, a crashed trial says `trial 0889 FAIL crash, last evidence 0 s after start, last sample 3 s: Tctl 71°C, 5420-5610 MHz`; without samples it retains `trial 0330 FAIL crash, last evidence 0 s after start`. An interrupted trial without a failure says `trial 0331 INCONCLUSIVE, last evidence 0 s after start: togi stopped during the trial`. A trial ended while togi watches it, including an orderly stop by signal, keeps its existing message and measured duration.

Failed trials with two or more loaded cores also carry optional `stalled_core` and `worker_stalled_ms` when persisted worker CPU times distinguish a unique first terminal stall (`workloads.md`, Trial outcome). The latter is milliseconds since trial timing began at the first observed unchanged reading. Both fields are absent for R6, whose workers are suspended by design, and for missing or ambiguous evidence, including ties and workers that advanced until the final sample. The message adds `, core NN worker CPU time stopped advancing at N ms after start (evidence only)` when both fields are present. This does not set the attribution field `core` or alter `duration_s`. For an unattributed multi-core R7 failure, `stalled_core` restricts top-requester attribution to that core's CCD; it does not attribute the failure to the stalled core.

Every trial with loaded cores (R1–R7), whether watched through its end or closed on resume, carries optional `voltage_request_median_v` and `voltage_request_min_v`. For each complete persisted conditions sample with `pm_table` lanes, take the highest `voltage_request_v` among only that trial's loaded cores, then record the median and minimum over those maxima in volts. An even number of samples uses the mean of the two middle maxima as its median. Samples without lanes are skipped; no decoded samples leaves both fields absent, as on unsupported tables and on a simulator without its shared-voltage model; a shared-voltage simulator supplies the lanes and fills both. Both CCDs share VDDCR and the highest request wins: these fields describe the loaded cores' request, not an observed rail voltage, and exclude requests from idle cores outside the trial. The message adds ` | loaded voltage request median X.XXX V, min Y.YYY V` only when both fields are present. These measurements do not change trial outcomes or tuning decisions, and do not bump the journal schema.

The same trials also carry optional `voltage_requests_v` (loaded core ID → median request in volts), `top_requesters` (each loaded CCD's highest requesters, sorted by core ID, including cores within 1 mV of that CCD's highest median) and `ccd_mhz` (loaded CCD ID → median clock in whole MHz). Their window includes only complete samples with decoded `pm_table` lanes and `elapsed_ms >= 5000`. Fewer than 20 such samples omits all three fields. For each qualifying sample and CCD, take the median of the available loaded-core clocks; then take the median of those sample medians, rounded to the nearest whole MHz. A CCD with fewer than 20 available sample medians has no clock entry. Even medians use the mean of the two middle values. Session topology maps loaded core IDs to CCDs; unloaded cores never count. The message appends ` | top requester NN X.XXX V`, with several requesters comma-separated. These added fields bump neither the schema nor the ruleset, and the existing whole-trial voltage median and minimum remain unchanged. Tuning decisions use them to order R7 partial parts, attribute multi-core R7 failures and size voltage-targeted backoffs (`tuner.md`).

A conditions-file open, read, gzip or complete-line decode failure omits every sample-derived field above, together with `tctl_max_c`, and appends `session.warning` with `operation: "read conditions samples"`, the `trial` and the error, citing the durable `trial.end`. This warning does not change the trial's outcome. A missing file remains absent telemetry, and an unterminated final line remains a torn tail, not a decode failure (`workloads.md`, Conditions sampling).

Event kinds and event fields keep their names once released. A change of vocabulary in `GLOSSARY.md` renames prose, messages, help and docs, never the wire, and never bumps `SCHEMA` on its own. Configuration keys follow the same rule (`runtime.md`, Configuration).

`crash.detected.pstore`, when present, contains `path` (the absolute location of the archived dmesg record) and `lines` (its bounded tail). Recovery reads at most 128 prefix bytes per candidate to identify its full dump count and chunk part, then at most the final 3968 bytes of the selected record, keeping each record's raw reads within 4096 bytes and retaining at most 32 lines. It discards a partial first tail line when a newline follows it, otherwise keeps the bounded suffix of a long line without splitting a UTF-8 rune. Lines retain raw diagnostic text in JSON, escaped by JSON encoding like MCE lines; terminal renderers escape the message's path like other raw diagnostics. The message names the record but does not repeat its lines; `togi events --json --kind crash.detected` exposes them. This optional diagnostic never changes crash classification, attribution or replay decisions. No matching record leaves `pstore` absent. Archive or boot-span read failures append `session.warning` with `operation: "read saved pstore"` and the failed operation, then recovery continues without `pstore`; failure to append that warning remains fatal under the journal-write rules.

`boot.leave_reason` imports a pending tuning-boot recovery or refusal explanation from GRUB's `togi_leave_reason`, a compact JSON record with `id`, `count` and `reason`. Its journal fields are `reason_id` (the record's unique ID), `restart_limit_count` (0-3; 0 means unknown for the shell fallback), and `reason` (the bounded single-line explanation). It is informational evidence, not a tuning decision, and adds no journal schema bump. Importing it after `shutdown` does not turn a cleanly completed boot into a crash.

Before its first append, `run --tuning-boot` reads the pending record. Its first successful durable append resets GRUB's `togi_restart_count` once for that run. It imports the pending record as `boot.leave_reason` unless the current or an archived journal already contains the same `reason_id`, and clears the record only after that acknowledgement is durable. When resuming an interrupted dead end, it completes this handoff before replacing the pending record with the new dead-end reason; importing an unacknowledged record is itself the first durable append, while an already-acknowledged record can be cleared without another append. A durable preflight refusal resets the count just as any other durable append does; merely launching a process or opening the journal does not. Ordinary in-session runs and read-only commands neither reset the count nor import the record.

If a crash happens after `boot.leave_reason` is durable but before the GRUB record is cleared, or if clearing fails, the record remains pending. The next tuning-boot run finds its ID in the current or archived journal and clears it without appending a duplicate, including when a startup transition archived the original acknowledgement. One record is journaled once. A reason left by a return to the normal system remains in GRUB until the operator selects the tuning boot again. A count-reset, acknowledgement-lookup or reason-clear error retains the pending record and is an ordinary run error with journaled cleanup, not a journal-write emergency. When a dead-end reason cannot be written, `boot.saved_entry.reason_error` and its message preserve that diagnostic independently of the saved-entry clear result; the clear is still attempted.

Backend computation errors, early exits and stalls are recorded as `trial.progress` with their typed `signal`, affected `core` and signal-specific human detail as soon as they are classified, before `trial.end`. Recovery retains this durable evidence if the machine crashes before the trial ends; a recorded backend failure outranks the reset reason. `trial.signal` records load-step signalling, not backend failures.

Kernel-log cursor persistence uses additive `kernel_cursor` and `kernel_error` fields on the already-existing `config.loaded`, `trial.intent`, `trial.end` and `shutdown` boundary events; it adds no boundary events or kinds. Replay keeps the newest cursor separately for each event's `boot`. A failed read retains the prior cursor, and its diagnostic stays with the intersecting trial even if teardown or same-boot resume later succeeds. An unresumable cursor records the lost interval and may persist a fresh anchor, without clearing that trial's error. A torn or interrupted boundary resumes the previous durable cursor and deduplicates already-recorded MCEs.

`trial.start.window_start_ns` records the boot-local monotonic instant after profile readback, before workload startup, so the evidence window does not depend on wall time or backend setup duration. If startup is interrupted before `trial.start`, readiness is reconstructed from the latest target readback's `mono_ms`, or the intent timestamp when the profile needed no target write.

Each `mce` records `monotonic_ns`, its boot-local kernel-log timestamp in nanoseconds, including zero. Its clock belongs to `from_boot` when present, otherwise the event's `boot`; it is not the time recovery appended the event. The field is additive under ADR 0009, with no schema or ruleset change. Events without it, including those written by 0.5.0, retain their previous attribution behavior.

An MCE whose timestamp is inside the inclusive profile-applied through teardown window names its `trial` on a normal boundary read; an outside-window MCE has `between_trials: true`, no trial, and the message suffix `between trials (recorded only)`. These events are visible in `events`, in `status`'s between-trial evidence and in `watch`'s recent log, but supply no trial outcome or failure decision. Crash-recovery MCEs retain `from_boot`; replay checks previous-boot timestamps against that boot's open trial, while uncorrected MCA evidence retained into the next boot is associated with the preceding crash without comparing the two boot clocks.
Recovery records MCEs decoded before a kernel-log read error before its `backend.retry` wait, deduplicating them on retries and resumed recovery; their evidence eligibility is unchanged by the read error.
`trial.end.containment_error` records unconfirmed trial cleanup, including partial-start rollback. Such a trial is inconclusive as stability evidence and leads directly to the existing `containment` dead end, even if the trial was interrupted or produced a computation error. Replay retains this evidence if the process stops before recording the dead end; no next trial or tuning profile write follows.

When trial setup fails and its rollback reports further errors, such as output-cleanup diagnostics, `trial.end.reason` retains each error in occurrence order with its underlying causes, whether rollback confirms cleanup or cannot confirm it. If rollback cannot confirm cleanup, `trial.end.containment_error` retains the same errors and causes.

`trial.intent.cores` lists exactly the loaded cores for R6 and R7. `profile` always lists applied offsets for every core in core-id order. `tuner.decision` with `decision: check_solo_limit` has the frozen two `workloads`; its message says `checks candidate solo limit` and, when the candidate differs from `from_offset`, `(from N; reason)`. `step_deeper` and a search `backoff` say the offset the core `searches ... on its next turn`, separate from the session's next trial; `deepen` says `deepened from N to M`, `yield` says `yielded from N to M`, `hold` says `failure held; tuning stays at N`, and checking, hunt and deepening `backoff` say `backed off from N to M`. `core.phase` uses `search`, `has_room` or `at_limit`, while `activity` on `trial.intent` and `tuner.decision` is `search`, `checking`, `hunt` or `deepening`. An equal `profile.change` message does not say checking restarts.

Trial writers encode a single-core load in `core` with no `cores`, or a set load in `cores` with no `core`. Readers normalize both through the same tuner operation: a named `core` takes precedence if both fields are present; otherwise `cores` is the load. Validated decoding refuses an empty load or a loaded core outside the session topology rather than substituting another core.

A `checking` decision that holds a later failure is a `hold`, with equal `from_offset` and `to_offset` and the message `failure held; tuning stays at N (reason)`; nothing infers a hold from an equal-offset `backoff` or from the reason text. Its reason names the held failure. A step-back that a second failure causes is a `backoff` whose reason ends `second failure within 5 cycles: #A (cycle a, held) and #B (cycle b)` and cites the held failure last in `cause` ([Later failures](tuner.md#later-failures)).

A `trial.intent` with condition `parked`, `rerun` and no `hunt` is the all-zero rerun before a `failure_at_zero` dead end (`tuner.md`, Dead ends): its `profile` is all 0, it cites the failure it reruns, and its message ends `rerun with every core at offset 0`. A `failure_at_zero` `deadend` that follows a failed all-zero rerun cites both failures, and its detail says `the rerun with every core at CO 0 failed too (#<seq>)` before `so the instability is not caused by Curve Optimizer`.

An unattributed multi-core R7 `backoff` that a located hunt could still follow says which backoff of its load it is since the load's last passing trial and that a located hunt follows only after two. A voltage-targeted R7 `backoff` names measured failing and target requests in volts with three decimal places, matching `trial.end`, and the rounded-up counts, or explains the one-count fallback when no qualifying passed voltage exists. If the failing request already meets the passed target, the message says so and explains the one-count move. A carried failure's message names its failing request and says that a carried failure takes no voltage target. With no request telemetry, the message instead says the order came from offsets, names the failing CO offset and explains the one-count fallback; it does not print an offset-derived pseudo-voltage. When measurements cover other loaded cores but not the moved one, it names those measurements, says they do not cover the moved core and explains the one-count fallback. Causes include the failure, request measurements and trials defining the target. A CO-0 top-group stepdown explains why the next movable group on the same CCD was selected, and a failure naming a CO-0 core whose CCD had no loaded core explains why it counts against the loaded CCD's top group. A `failure_at_zero` dead end distinguishes a named core that was top in its trial from an unattributed failure with every loaded core of its affected CCD at 0.

A requester probe after repeated unattributed R7 charges is also a together `checking` trial with `rerun: true` and no cycle, hunt or round. Its loaded set is the source load minus the charged CCD's selected tied group. The charge decision's reason names that group and why the experiment is due; the probe intent cites the failure first and its charge decisions. Distinguishing it from the full-load rerun requires those causes, not a new event or flag ([tuner.md](tuner.md#testing-a-repeatedly-charged-requester)).

A `trial.carried` message names the source trial, session and build, the class and loaded cores, the outcome (including its signal on failure), the full profile, measured and intended duration, evidence epoch, and top requester cores when measured. These kinds are plain in human rendering. Their replay does not restore tuning offsets or cycles. The tuner consumes partial facts as ordinary evidence. Decisions answered by carried facts cite their new-journal sequences in `cause` and name original source sessions in `msg`; the new journal alone explains the answer. `togi-facts` returns a session's own facts separately from its carried copies so readers traversing every session do not double count.

A `failure` decision with optional `known_failure` names the existing decisive failure sequence in this journal and activates it instead of recording a newly observed failure. Its `reason` and `msg` explain the skipped scheduled class and profile, why the source failure remains valid, and any carried source session; `cause` cites that source sequence. Its optional `round` identifies the skipped deepening check so replay ends that round before its backoff. It supplies no new fact, trial or exposure. A subsequent `hunt.start.failure` and its cause retain the known failure sequence, not the skip decision's sequence; optional `hunt.start.reason` explains the skipped trial in its message.

A skipped parked trial records an inferred-failure `hunt.group` with the running group's number, citing both its original plan and the known failure. Replay supersedes that group's active outcome rather than adding another group; both journal events and their causes remain intact, and member probes continue from the inferred failure.

| `hunt.end` | `hunt`, `result` (`culprit`, `combination`, `fallback`, `direct`, `loaded` (a located hunt keeps the failure on its loaded `cores`), `cancelled`), optional `cores`, `members` (each member's shallowest failing `core` and `offset`, on a probed `combination` or singleton `culprit`), `groups`, `reason` | `hunt 3 found core 13 after 4 groups` or `hunt 3 ended after 1 group: the failure stays with loaded cores 00, 01, …, 07 (…)` |
| `hunt.skipped` | `failure` seq, `reason` | `failure #904 is not hunted: <reason>`; a held later failure says `held: first unattributed failure loading cores [00, 01, …] since the profile passed cycle 14 (#790); a second failure loading any of them by cycle 18 (K = 5) is hunted` |
| `combination` | `combination`, `members` (`core`, `offset` pairs), optional `fallback`, `hunt`, `reason` | `combination C2: core 03 -40 + core 11 -30, observed in hunt 4` (or `…, fallback over every candidate of hunt 4`) |
| `deepening.round` | `round`, `event` (`start`, `end`); start: `base` (phase 1's passed full-cycle profile), `base_seq` (its cycle-end sequence), `target` (the solo limit of each round core, the current offset of the others), the moved `profile`, `cores` (the moved cores plus any mover carried over from a round that ended unpassed without a blame), `ranking`, `trials`, `trial_s`; end: optional `passed`, `reason` | `deepening round 2 start: 5 cores toward their solo limits …` / `deepening round 2 end: passed` |
| `tuner.warning` | `warning` (`monotonicity`), `trial`, `passes` (contradicted live or carried pass seqs), `detail` (failed profile, class and valid-pass count, plus carried source sessions when present) | `monotonicity: <detail>` |
| `backend.retry` | `backend` (`mprime`, `ycruncher` or `kernel_log`), `attempt` (1–3), `wait_s` (60, 300, 1800), `reason` | `backend mprime: retry 2 of 3 after 300 s: setup failed: …` |

### Trial activity

A `trial.intent` names the activity that asked for the trial through these fields, all from the event itself except the hunt stage and the requester-probe distinction:

| Activity | `activity` | `condition` | Identifying fields | Absent |
|---|---|---|---|---|
| Search | `search` | `alone` | `core`, `offset` | `cycle`, `hunt`, `round` |
| Checking cycle trial | `checking` | `together` | `cycle`; R7 parts also `step` | `rerun`, `hunt`, `round` |
| Backoff rerun or requester probe in checking | `checking` | `together` | `rerun: true`; a requester probe is identified through its charge causes | `cycle` (the rerun belongs to no cycle) |
| Hunt group trial | `hunt` | `parked` | `hunt`, `group` | `cycle`, `round`, `rerun` |
| Located hunt trial | `hunt` | `parked` | `hunt`, `group`, as for any hunt trial; no flag marks it | `cycle`, `round`, `rerun` |
| Deepening check | `deepening` | `alone` for R1/R2, `together` for R7 | `round` | `cycle`, `hunt` |
| All-zero rerun before `failure_at_zero` | `checking`, or `hunt` when the failure came from a parked trial | `parked` | `rerun: true`, `profile` all 0 | `hunt`, `cycle` |
| Retry of an inconclusive trial | the original's | the original's | `retry: true` plus the original's fields | |

A located hunt has `hunt.start.regime: R7`, at least two loaded `cores`, and no overlap between its `candidates` and those loaded cores. Its `reason` explains the location and why the failure was located: it cites the load's backoffs in `cause` and names them, or says that every loaded core on the affected CCDs is at CO 0. Its first `hunt.group` has stage `locate`; there is no located-hunt flag. A hunt trial's stage, granularity and candidate set are not on the `trial.intent`: join its `hunt` and `group` to the `hunt.group` event with the same numbers.

## Transitions

A transition archives a journal whose `Resume` verdict is `Archive`: an older ruleset, schema or evidence epoch and no newer dimension, before opening it. It also archives a compatible journal when the recorded BIOS context differs from the current one. An evidence-epoch-only increase therefore starts a new session even when ruleset and schema are unchanged. The new session carries eligible same-BIOS failures from every epoch and passes only from its current evidence epoch. The durable epoch is `session.start.build.evidence`; later `config.loaded` stamps do not change it. An epoch-only increase requires neither a schema nor a ruleset increase. The same carry marker, lock and crash-recovery protocol apply. A BIOS change carries candidate solo limits only, not failure points or combinations. A newer journal remains a refusal. Before the move, `run` writes and fsyncs `archive/<session-id>-carry-pending` (and syncs the archive and state directories) without appending to the old journal. A previously archived last `session.archived` move is completed without carry. `reset --all` writes and fsyncs a permanent `archive/<session-id>-reset-all` boundary before removing carry markers or moving a journal. The ID is the newest live, archived or marked source, using numeric session-ID order; an existing boundary is never moved backwards, and there is no operation that removes it. The marker file, archive directory and state directory are synced under the writer lock. Compatible resets still record `command.reset`; pending-carry drops, recovered archives and schema-mismatch archives need not append to a journal to establish the same durable boundary. Every later transition excludes sources at or before it, including copied facts, candidate solo limits and failure points with discarded original provenance. An interruption after the boundary but before carry-marker removal resumes by discarding those pending sources, not by carrying them. If the live journal still names a session at or before the boundary, carry preparation archives that journal unchanged and clears its pending carry before the journal can open for session resume, even when its schema, ruleset and BIOS context are compatible.

`togi_session::prepare` performs the transition before the journal is opened for the run: it judges the live journal's `session.start` build alone (so undecodable later events never block the archive), archives it as a transition when the verdict is `Archive`, archives a live journal at or behind the reset boundary unread and drops the carry marker, clears a carry marker the boundary passed or the live journal already committed, and selects the carry from the archives. A compatible journal whose recorded BIOS context differs from the current one is archived through its own `session.archived` event. When the verdict is `Refuse` (a newer dimension), `prepare` returns the refusal before opening anything: opening would replace a torn tail with a `journal.torn` event and decode events only the build that wrote the journal may read, so the live journal stays byte for byte as it was for that build to resume.

An older journal may contain events this build cannot decode: the transition still archives it unchanged, without decoding them, and they supply no carry evidence. A journal with this build's ruleset, schema and evidence epoch must decode completely before `run` can append to it or archive it for a BIOS change.

While a carry marker exists and the current journal holds neither a `session.carried` whose first source is the marked session nor any `core.phase`, the next `run` computes the carry from the archives. After `session.start`, `session.context`, the baseline and its notice, and before any phase or decision, it appends each eligible fact as `trial.carried` or `failure.carried`, in original source-session order then source sequence, followed by the existing `session.carried` commitment. An interruption among these facts retains the marker; resume appends only missing original identities (`source.session`, `source.seq`), never duplicates. Afterwards the marker is removed. A crash between `session.carried` and the phases resumes from the recorded events, never from the archives.

Fact eligibility must be evaluated against the new session's known current BIOS context before `session.carried` commits the transition. If the early BIOS lookup is unavailable, preparation is deferred until the session records its actual context or validates its recorded context during preflight. The archived context is never substituted for the current one. If that validation cannot complete, no carry commitment is written and the pending marker remains for resume.

If a further transition archives an interrupted new session that recorded neither `session.context` nor `session.carried`, the earlier pending source is retained instead of being replaced by that incomplete session. Its candidate solo limits, failure points, BIOS context and original provenance seed the eventual session. Once context or carry is recorded, normal source chaining, per-core reset epochs and `reset --all` apply. An explicit `reset --all` still drops every pending source.

Archives and history are read with the lock-free readers, which decode every event with the current schema and write nothing; torn tails are reported, not read as events. The live-session compatibility check still refuses an older schema: the next `togi run` archives that session unchanged and starts a new session carrying eligible candidate solo limits, failure points and facts. Carry takes each source's decoded events and folds them once, in one pass, reading a source only while a walk needs it and never one behind the permanent reset boundary; it reads no file itself. History readers keep the same two parts of `config.loaded`: the build stamp and the backend store paths.

Sources, newest first: the archived session, then, when it holds no `session.carried` and no `reset --all` and recorded a BIOS context, each older archive in turn, for as long as the archive recorded the same BIOS context and either a different ruleset or a different evidence epoch from the source read before it. Equal ruleset and epoch stop this walk. An interrupted epoch-only transition that recorded context but no `session.carried` therefore still reaches the preceding epoch's candidate solo limits and failure points. A walked archive that holds a `session.carried` or a `reset --all` is the last source. Per source, a value recorded before a `reset --core` of its core in that source, or before a `reset --all` in it, is dropped, so a `reset --all` never lets an older source's values come back:
- **Candidate solo limit:** the deepest offset of a passing `trial.end` whose `trial.intent` is alone with one core and an offset.
- **Carried failure point:** the shallowest offset of a newly observed attributed `failure` of one core at a known offset, or a `hunt.end` `culprit` for core c at the offset the end's `members` give core c (the shallowest reproduced failure of a probed singleton, so a refined offset such as -23 rather than the original -30), else, for an end naming no member for c (an older or unprobed end), at the `hunt.start` failing profile's offset c; the source is the hunt end alone and its decision is never consulted, so an interrupted transition carries the refined offset whether or not the culprit backoff was recorded. The point carries the cited source's signal and hunt-end sequence. Offset 0 counts only for a confirmed failure: its failing profile was all at CO 0 (a trial alone at 0 is; an idle failure's recorded profile is used), or its all-zero rerun (a `trial.intent` with condition `parked`, `rerun`, no `hunt` and an all-zero profile, citing that failure; `tuner.md`, Dead ends) ended in a failure. An unconfirmed failure at 0 carries only its fact, which the new session routes like any carried failure, so no `failure_at_zero` dead end rests on it without a failed all-zero rerun. That source can be a `failure`, a failed `trial.end`, a failed `trial.carried`, or a `failure.carried`; a known-failure skip activates its original decisive sequence instead of making a new failure point or observation. Both follow the same reset epoch. Only an attributed `failure` is checked against defect exclusions; a `hunt.end` culprit candidate is not; direct hunt failures already appear as attributed `failure` events. Combinations are not carried. A nonzero trial run alone left in flight after the last shutdown also counts as a crash failure.
- **Carried values:** the candidate solo limits and failure points of a `session.carried` in the source, dropped by a later `reset --core` of their core or `reset --all` in that source. A failure point at 0 is written into `session.carried` only when confirmed by the rule above, so a carried one is confirmed by construction and no original archive is read for it.

Across sources the deepest candidate solo limit and the shallowest failure point win; on a tie, the first found. Profile offsets and passed cycles are never carried. Candidate-solo-limit and failure-point derivation remain unchanged by carried facts.

A held later failure ([Later failures](tuner.md#later-failures)) records no failure point in its own session. It is still a newly observed attributed `failure` of one core at a known offset, so a later seeded session carries it as a failure point, and a held unattributed failure is carried as a failure fact like any other.

`session.carried` has no cause and carries `sources` (each with `session`, `schema` and `ruleset`; the archive path is derived from the session), `failure_points`, an optional `detail`, and `carried`: one entry per core of this machine that has a candidate solo limit or a failure point, with `core`, and `candidate_solo_limit` (the `offset` and its `from`: the `session` and `seq` of the passing `trial.end`), and `failure_point` (the `offset`, its `from` and the `signal`) where present. `failure_points` is false, and `detail` says why, when the archived session recorded no BIOS context or a different one from this machine's; the failure points then stay behind and only candidate solo limits are carried. Its `msg` is `carried N candidate solo limits and M failure points from session <id> (schema S, ruleset R), …`, or, without failure points, `carried N candidate solo limits from …; failure points stay behind: <detail>`. `status` prints it as `carried: [#seq] <msg>`. How the new session starts from these values is in `tuner.md`, Session start.

### Fact eligibility

The live journal being archived is the newest source. Facts have their own same-BIOS walk, independent of the legacy solo-limit/failure-point ruleset-and-epoch boundary above:

1. Walk archives newest first, stopping at a BIOS mismatch; across a BIOS change only candidate solo limits carry.
2. Exclude sources at or before the newest permanent reset boundary, without reading their journals. Also stop at the newest recorded `command.reset` with `all: true`; in that session, only facts after that event remain eligible, and no older session contributes.
3. Stop after the first archive holding both carried facts and their `session.carried` commitment. Copy its own eligible facts and eligible carried copies, preserving the original provenance; do not walk behind it. A copied prefix without that commitment continues traversal and deduplicates by original source session and sequence. Legacy commitments containing only candidate solo limits and failure points do not by themselves stop the initial fact walk.
4. Keep failures from every visited session. Keep passes only when their original evidence epoch equals the current epoch and they ran under the backend identity the new session records: the store path in the new session's latest `config.loaded` for the backend of the pass's workload (`tuner.md`, Evidence). A live pass's identity is the path the `config.loaded` before its `trial.intent` recorded in its original session. A carried pass's identity is the `source.backend` it records, its original backend and store path; it is compared as recorded, never looked up in the original archive or replaced by the path of a session that copied it. Failures are kept whichever backend build ran them.
5. Drop any fact from before a `reset --core N` that loads core N, including carried copies discarded by a later reset.
6. Drop failures behind a defect-matched decision using the existing `togi-defect` matching and the original source session's own fixes stamps, as with failure points. Re-check carried copies against their original `archive/<source.session>.jsonl`, caching exclusions per source session; reading that journal for defect matching does not resume fact collection beyond the copy-forward boundary. If the original archive is missing, retain the copied failure without changing its carried-event message; other archive read errors stop preparation.

The result is recorded chronologically, oldest original source session first and then source sequence. Copy-forward always keeps the first source session and sequence, including through consecutive transitions. An interrupted transition may already contain a prefix of these facts; that prefix is evidence, not the `session.carried` commitment.

Facts preserve the source `trial.end`'s `voltage_requests_v`, `top_requesters`, `ccd_mhz` and diagnostic `stalled_core`; a stalled core is not attribution. The request fields come only from the recorded `trial.end` and are never recomputed from `samples.jsonl`: absent fields stay absent. Each decisive fact takes the full applied profile recorded in its `trial.intent`, never one rebuilt from `profile.applied`, `profile.change` or `smu.readback`. A copy keeps all of these, and a copied pass its `source.backend`, verbatim, so copy-forward never reads an original archive to recover them. Interrupted carry retains already written facts and computes only missing copies from the same immutable source evidence.

### Decisions in the new session

The tuner can answer candidate-solo-limit checks in their frozen R1/R2 classes, hunt groups (planning, outcome and projected pass count), reruns and deepening checks with carried passes across their local evidence boundaries. Ordinary search steps still need live trials. A checking cycle fulfills its requirements only with live passes since its start; cycles do not carry. Carried failures count everywhere a failure counts, including invalidation and, outside multi-core R7, monotonicity warnings; a core reset invalidates carried evidence under the same rules as live evidence (`tuner.md`, Evidence). Carried facts influence decisions as ordinary outcomes, including R7 self-sufficiency and voltage-targeted backoff. Each multi-core R7 failure is processed once, before the first live trial when carried, not replayed as repeated known-failure skips. Candidate solo limits and failure points still seed where search starts; facts answer whether a class has passed or failed. A carried pass belongs to the backend identity its `source.backend` records: it counts only while the session's latest `config.loaded` records that store path for its backend, so a later `config.loaded` with a new path stops it counting, like a live pass.

The [recorded-state transition inspection recipe](../reviewing.md#inspecting-a-transition-on-recorded-state) shows how to inspect eligible facts and simulate a transition on a temporary copy. The fact-eligibility rules above determine which sources contribute; inspection does not supply new hardware evidence.

## Defects

The build's defect registry gives each entry an increasing integer `id`, short `title`, fixing pull request `pr`, `direction` (`too_cautious` or `too_aggressive`) and clauses. A clause names an affected decision (`kind` and `decision`) and the kind its direct cause must have; clauses are data, with no predicate over surrounding events. The Rust registry starts empty, so its `fixes` stamp, the highest ID, is 0. A decision uses the most recent `session.start` or `config.loaded` `fixes` before it (absent means 0). A decision recorded with fixes below an entry's ID that matches one of its clauses, by kind, decision and at least one direct cause of the clause's kind, is not recomputed or removed: on resume, the build appends one `defect.found` per defect per session, aggregating the affected `cores` and `decisions` (their `seq`s); `cause` lists those decision sequences. A prior `defect.found` suppresses another finding for that ID. Every `failure` that took part in a decision's match, that is, every direct cause of the clause's cause kind when that kind is `failure`, is excluded from carry, before and after the finding is recorded, not only the first; a failure cited beside a match on another cause kind is not excluded.

The Go build's only entry, ID 1, the false failure on power-off fixed in [#14](https://github.com/shgew/togi/issues/14), is history: Rust sessions never read Go journals, so the Rust registry does not carry it. A `defect.found` whose ID this build does not list is still a finding, with the direction it recorded; a too-aggressive one is never skipped.

`defect.found` carries `id`, `title`, `detail` (why), `pr`, `direction`, `cores` and `decisions`. `defect.answered` carries `id`, `cores` and `answer` (`yes` or `no`), with `cause` citing the finding. The answer is appended and fsynced first. A yes then appends one `command.reset` per affected core, each citing the durable answer, not the finding; a no records only the answer. On resume, a recorded yes queues only cores still lacking a reset caused by that answer, before queued resets or tuning decisions are consumed. Manual resets and resets caused by another finding or answer do not satisfy that missing work. Either answer prevents another prompt for that ID; an answer does not hide a too-cautious finding from `status`. `status` keeps showing the finding's reset command for each affected core until a later `command.reset` for that core or `reset --all`. The original decisions and every journal line remain unchanged.

## Reset commands

`reset --core N` appends one `command.reset` and nothing else: no `shutdown`, because the command never owned the hardware and a `shutdown` would hide a crashed tuning boot from the next crash recovery. It refuses, before folding the journal, a journal this build may not append to; it refuses an empty journal (no session) and a core the session was not recorded on; a journal that cannot be folded is a fold error. On every error the journal holds what it held.

`reset --all` spends the journal on every outcome: the command takes the journal by value and never folds it. A journal of a different schema, which this build cannot read, is archived unread (`archive_unreadable`); a journal of this schema, whatever its ruleset or evidence epoch, appends `command.reset` for all cores and archives the session (`ResetAll` in the compatibility table: same schema → Use, different schema → Archive). An archive failure terminates the command with an error and releases the state-directory lock; the session stays wherever the failed step left it, and the caller reopens the state directory (which finishes an interrupted archive) to see which. A journal this build refuses for `ResetAll` is an error that likewise releases the lock.

## State file

`state.json` is a document the session composes: one object with two keys, `facts` (the journal's shared-facts `State`) and `tuner` (the tuner's projection). The journal never depends on the tuner; it only publishes the document, atomically: `StateDir::write_state` serializes it to one compact JSON object followed by a newline (`jq . state.json` shows it indented), writes it whole to `.state.json.tmp`, fsyncs, renames it over `state.json` and syncs the directory. `read_state` returns nothing when there is no file and an error when the file does not decode. Unknown keys are refused.
The temp write must consume the complete projection before it can be renamed; a short write leaves the previous complete state in place.

The session publishes it under a typed policy chosen by the caller. `Live` (the default) publishes after every appended event. `OnFinish` (the simulator and benchmarks, which fold millions of events and read the projection only at the end) publishes once, as the last step of the run: after the final event (the `shutdown` or the dead end) and before the journal is handed back and closed, so a publication never follows the close. Both policies publish a last time at the end of the run. An exit that never appended an event publishes nothing, and a run that ended with the machine crashed or its journal latched publishes nothing, so a crash leaves the previous state in place for the next start to rebuild.

The keys below are the union of the two halves: `schema`, `session`, `last_seq`, `open`, `dead_end`, `backends` and the facts of each core belong to `facts`; everything else is the tuner's projection under `tuner`.

Two keys project the operator's view of the method. `phases` is null before the session has cores, else `phase` (1, 2, or 0 once phase 2 concluded), `phase_1_end`, `concluded` (the sequences of the cycle ends that ended phase 1 and concluded phase 2, 0 before), `confirming`, `round`, and in phase 2 `rounds_left` (the rounds that would still run if none failed, an open one included, before one full cycle) and `candidates` (`core`, `offset`, `solo_limit`, `gap`, `carried`, `moving`). `bios` is null until phase 1's first passed cycle, else the profile to enter in BIOS in core-id order: `offsets`, `confirmed` (the sequence of the confirming cycle end), `unconfirmed` (cores shown stepped back, ascending) and `since` (the earliest event that left it unconfirmed, 0 when confirmed). Both are derived by [BIOS profile](tuner.md#bios-profile) and [Phase 2](tuner.md#phase-2); neither is an event, and adding them does not change `schema`. The first start of a build that writes them on a session whose `state.json` lacks them records one `state.rebuilt` event.

A failed projection write appends `session.warning` with `operation: "write state projection"` and the error, then continues the session; it never triggers emergency zeroing by itself. The authoritative event is already durable. Persisting that warning does not attempt another projection write, so an unwritable state file cannot recursively generate warnings. A journal append failure, including failure to append the warning, remains fatal: after CPU family/model and driver codename validation it takes the emergency-zeroing path; before that boundary it exits without mailbox commands or SMN access (`runtime.md`, Preflight). Readers see either the previous complete state or the new complete state, never a torn file. On the next start, replay rebuilds a stale or missing projection and records `state.rebuilt` after a successful rewrite; if that rewrite fails, it warns and continues instead. A warning after a durable `shutdown` does not make the stopped boot a crash.

It is shaped so a reader finds each part under one key:

- `schema` (`SCHEMA`), `session` (id, start time, build stamp, BIOS context, baseline), `last_seq`;
- `phase`: activity `search`, `hunt`, `deepening` or `checking`;
- `cores[]`: core identity, offset, baseline, phase (`search`, `has_room`, `at_limit`), pass, `failure_point`, `combinations` IDs, queued reset and last decision;
- `cores[]` also carries, from the journal's facts, the core's `ccd`, `cpus`, observed baseline and last decision (`seq` and the decision's `msg`; a `tuner.decision`, `core.phase` or `deadend` naming the core);
- `open`: every intent without a result, `in_flight` being the newest. An SMU intent is cleared by the `smu.write` or `smu.error` that cites it, and a newer SMU intent replaces an older one (one command is in flight at a time); a `trial.intent` is cleared by the `trial.end` of its trial; `crash.detected` clears every intent of its previous boot;
- `dead_end`: condition and sequence, or null (cleared on the next `config.loaded`);
- `backends`: the `mprime` and `ycruncher` store paths of the latest `config.loaded`, the backend identity a pass is valid under;
- `combinations[]`: `combination`, `members` (core/offset pairs), `fallback`, `hunt`, `seq`;
- `hunt`: null or `hunt`, `seq`, `failure`, `regime`, `trial`, `parked`, `parked_seq`, `candidates`, `escalated`, `groups[]` (`group`, `seq`, `cores`, optional `probe` and `held`, `outcome` running/pass/failure/skipped, `passes`, `needed`);
- `deepening`: null or `round`, `seq`, `target`, `profile`, `cores`, `checks[]` (`regime`, `workload`, `cores`, `passes`, `needed`);
- `checking`: null before the first `profile.change`; then `cycle`, `cycle_open`, step progress, profile, `profile_seq` (latest `profile.change`), `full`, `missing`, `clean_cycles` (passed full cycles ending at or after phase 2's conclusion), `last_clean_cycle`, `exposure[]` (`regime`, `workload`, `trials`, counting valid passes), `tctl_max_c`, the highest Tctl over passes together since `profile_seq`, and `tctl_max_seq`, the event sequence of the pass that set it; the source trial is not persisted.

The journal's fold is fallible: `apply` returns an error, never panics, for a journal that cannot exist (a seq that does not follow the last, an event before `session.start`, a second `session.start`, a decision or baseline for a core the session lacks).

## Human-readable log

Each event's `msg` goes to stderr in an escaped representation, prefixed by local time and kind padded to 14 characters, so the system journal of a tuning boot reads as a narrative:

```
01:14:07 trial.intent   trial 0413 core 07 offset -32 R2 mprime AVX2 36K-248K 90 s alone
01:15:37 trial.end      trial 0413 PASS 90 s | Tctl max 71°C
01:15:37 tuner.decision core 07 passed R1+R2 at -32; searches -37 on its next turn (coarse, no failure point yet)
```

Human rendering escapes untrusted controls before adding application-owned styling. C0 controls and DEL use visible `\xNN` escapes, except tab, newline and carriage return use `\t`, `\n` and `\r`. C1 controls (including U+009B CSI and U+009D OSC), Unicode line and paragraph separators, and bidi formatting controls and marks (U+061C, U+200E–U+200F, U+202A–U+202E and U+2066–U+2069) use `\uNNNN`; raw ESC is `\x1b`. Invalid UTF-8 bytes use `\xNN`. Other Unicode and already-visible escape text remain readable and unchanged, with one exception: the dashboard draws only its console character set ([runtime.md, Commands](runtime.md#commands)), so it writes `×`, `…`, en and em dashes and curly quotes as `x`, `...`, `-`, `'` and `"`, and any other character outside that set as `\uNNNN`. The same rule covers event kinds, including unknown kinds in read errors, journal-derived status fields (including BIOS context), archive notices, and dashboard messages and diagnostics, so one event cannot insert a terminal command, another rendered line or a bidi override. Application-owned ANSI styling and dashboard cursor controls remain active.

The journal's `msg`, other evidence fields, and raw `togi events --json` lines are never sanitized or restyled: the escaped text exists only at human rendering boundaries.

`togi events` renders the journal the same way:

```
togi events [--core <N>] [--kind <kinds>] [--trial <ID>] [--since <time>] [--until <time>] [--json]
```

- `--core N`: events that name core N in a typed field: `core`, `cores`, `class.cores`, `candidates`, a member's `core`, a `command.reset` target or the `core` of an SMU command. It also matches the `trial.end` of every trial whose `trial.intent` loads core N (its `core` or `cores`) and every `failure` of such a trial that names no `core`. A known-failure skip (a `failure` with `known_failure`) matches when the event it names matches, never by its `trial`. Session-wide events stay out. A trial that started before `--since` still counts: the filter reads the journal from its start and prints only the events inside the window.
- `--kind`: comma-separated known exact kinds, or a known group when the entry has no `.` (`trial` matches every `trial.*` kind). Names come from the binary's kind registry. An unknown name or explicitly empty list exits 2 with the error and valid names on stderr before reading the journal; a valid filter with no matches exits 0 with empty stdout.
- `--trial ID`: events whose `trial` is ID, or carried events whose original `source.trial` is ID. Source trial IDs can match copies from more than one source session.
- `--since` (inclusive) and `--until` (exclusive): a time window.
- `--json`: print the raw event lines instead.

All given filters must match. A torn tail is reported on stderr and left for the next `run` to record.

### Colors

The run log and `togi events` color the whole human-readable line according to its moment:

| Moment | Color |
|---|---|
| Trial ends with failure (`trial.end` outcome `failure`), `failure`, `crash.detected` | Red |
| Dead end (`deadend` event and `run` summary), incompatible-session refusal line (not an event) | Red, bold |
| Search step passed (`step_deeper`), deepening `deepen`, or `hunt.end` result `culprit` or `direct` | Green |
| Core reaches its limit, search ends with room, passed `deepening.round` end, or passed full `checking.cycle` end | Green, bold |
| `combination`, `hunt.start`, `hunt.end` result `combination`, `fallback` or `loaded`, `tuner.warning`, `session.warning` (including state projection write failures), `backoff` or `yield`; known defect or ruleset mismatch warning | Yellow |
| Inconclusive trial or `backend.retry` | Dim |
| `hunt.group`, `deepening.round` start, `hunt.skipped`, `hunt.end` result `cancelled`, `host.ranking`, passed non-full cycle, and everything else | Plain |

ANSI SGR is used when that output stream is a terminal (a character device such as `/dev/null` is not one) or `JOURNAL_STREAM` names that stream (its device and inode match, whatever the file type). A non-empty `NO_COLOR` disables ANSI even in the system journal. `events.jsonl`, `state.json` and `togi events --json` stay uncolored. When `JOURNAL_STREAM` names that stream, red and red-bold lines start with `<3>` so systemd stores them at priority err (`SyslogLevelPrefix=` is on by default), including with `NO_COLOR`; no other line gets a priority prefix, and terminals outside the system journal never get one. `togi events` uses the same rules on stdout.

Every new event kind names its row here, or plain.
