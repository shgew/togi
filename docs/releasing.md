# Releasing

The owner decides when to release. `version.txt` is the single source of the package version. togi uses Semantic Versioning: before 1.0, a breaking change bumps MINOR and every other release bumps PATCH. From 1.0 onward, a breaking change bumps MAJOR, otherwise entries under `### Added` bump MINOR and other releases bump PATCH. An entry beginning `- **BREAKING**` makes the release breaking.

Pending entries live in `changes/`, one file per pull request named by its number ([ADR 0033](adr/0033-changelog-fragments.md)); `changes/README.md` states the format and `just changes` checks it. The release assembles them into the new version's section of `CHANGELOG.md`: sections in the order Added, Changed, Removed, Fixed, breaking entries first in each, then by pull request number, each entry linked to its pull request. The release commit deletes the files it assembled.

Releasing needs permission to start workflows in the repository ([ADR 0014](adr/0014-release-from-a-workflow.md)). The workflow pushes the release commit with a deploy key that has write access: its private key is the repository secret `RELEASE_DEPLOY_KEY`, and the `main` ruleset lists deploy keys as a bypass actor, since it otherwise requires a pull request and a passing `check`.

Before releasing a change to `tuner.Ruleset` or `journal.Schema`, simulate the transition on a copy of the target machine's state directory, as [Inspecting a transition on recorded state](reviewing.md#inspecting-a-transition-on-recorded-state) describes, with `--simulate` on a copy that includes the trial sample directories. The simulated session must get past its carried decisions without a dead end and reach a passed full cycle. The bench starts from fresh sessions, so it cannot show how the new rules treat the evidence the next run will carry in.

1. Run `just release-preview` to see the version, the reason for the bump and the release notes the release would get from `origin/main`. Preview leaves the checkout's branch, HEAD, index and worktree unchanged, including when a release needs publishing again.
2. Run `just release`. It starts the `release` workflow on `main` with `gh workflow run` and follows the run until it ends, so it can be started right after a merge. The workflow first waits for the `check` workflow's push run on `main` HEAD to finish, looking it up every 30 seconds while the run has not started yet, is queued or is in progress, and printing the run each time its state changes. It goes on once that run succeeded. It refuses if the run failed or was cancelled, or if it has not succeeded an hour after the wait began, naming the run, or the commit if no run had started by then; a check run takes about ten minutes, so the hour leaves room for runs waiting on a runner. After a cancellation, rerun the check run with `gh run rerun`; after a timeout, follow the named run with `gh run watch`, or, if no run had started, find the commit's run with `gh run list --workflow check.yml --event push --branch main` once it appears and follow that; then run `just release` again once it passes. It then computes the next version from the entries in `changes/` and commits `Release x.y.z` on top of `main`, updating `version.txt` and `CHANGELOG.md` and deleting the assembled files together; with no files in `changes/` and no dated section for the current version, it fails at that step. It builds `packages.x86_64-linux.default` (the package with its tests) on that commit and pushes it to `main`; if `main` moved since the run started, the push is refused and the run fails, and running `just release` again starts over. Last, it creates the `v<version>` tag and the release on that commit, with that version's changelog section, including its pull request links, as the notes.

If a run pushed the release commit but failed to publish, run `just release` again: with `changes/` empty, it finds the dated version and retries publishing without a new commit. Publishing checks for the GitHub Release, not just the tag: an existing tag on the release commit gets its missing Release created, and an existing Release is a no-op. A tag pointing at another commit fails with both commit IDs, rather than silently skipping publication.

Releases carry no binary artifacts. Flake users build from a tag. Dev builds of `packages.default` report `x.y.z+rev` (or `x.y.z+rev-dirty` for dirty flakes). An explicit revision supplied with `-X github.com/shgew/togi.rev=...` wins; otherwise `go build` uses Go's VCS build information: the first seven characters of the commit hash, with `-dirty` when the checkout is modified. Builds without a revision, including `go run`, report `x.y.z+dev`; the flake checks explicitly supply `dev`. `togi --version` prints the build version and revision.
