# Releasing

The owner decides when to release. `version.txt` is the single source of the package version. togi uses Semantic Versioning: before 1.0, a breaking change bumps MINOR and every other release bumps PATCH. From 1.0 onward, a breaking change bumps MAJOR, otherwise entries under `### Added` bump MINOR and other releases bump PATCH. A changelog line beginning `- **BREAKING**` makes the release breaking.

A pull request marked breaking merges only after the current `[Unreleased]` changes have been released. This ensures every downgrade target has a version.

Releasing needs permission to start workflows in the repository ([ADR 0014](adr/0014-release-from-a-workflow.md)). The workflow pushes the release commit with a deploy key that has write access: its private key is the repository secret `RELEASE_DEPLOY_KEY`, and the `main` ruleset lists deploy keys as a bypass actor, since it otherwise requires a pull request and a passing `check`.

1. Run `just release-preview` to see the version, the reason for the bump and the release notes the release would get from `origin/main`. Preview leaves the checkout's branch, HEAD, index and worktree unchanged, including when a release needs publishing again.
2. Run `just release`. It starts the `release` workflow on `main` with `gh workflow run` and follows the run until it ends. The workflow first refuses unless the `check` workflow run for `main` HEAD succeeded, naming the run if it is still going or failed; if that run was cancelled, rerun it with `gh run rerun` and run `just release` again once it passes. It then computes the next version from `[Unreleased]` and commits `Release x.y.z` on top of `main`, updating `version.txt` and `CHANGELOG.md` together; with nothing under `[Unreleased]` and no dated section for the current version, it fails at that step. It builds `packages.x86_64-linux.default` (the package with its tests) on that commit and pushes it to `main`; if `main` moved since the run started, the push is refused and the run fails, and running `just release` again starts over. Last, it creates the `v<version>` tag and the release on that commit, with that version's changelog section, including its pull request links, as the notes.

If a run pushed the release commit but failed to publish, run `just release` again: with an empty `[Unreleased]` section, it finds the dated version and retries publishing without a new commit. Publishing checks for the GitHub Release, not just the tag: an existing tag on the release commit gets its missing Release created, and an existing Release is a no-op. A tag pointing at another commit fails with both commit IDs, rather than silently skipping publication.

Releases carry no binary artifacts. Flake users build from a tag. Dev builds of `packages.default` report `x.y.z+rev` (or `x.y.z+rev-dirty` for dirty flakes). An explicit revision supplied with `-X github.com/shgew/togi.rev=...` wins; otherwise `go build` uses Go's VCS build information: the first seven characters of the commit hash, with `-dirty` when the checkout is modified. Builds without a revision, including `go run`, report `x.y.z+dev`; the flake checks explicitly supply `dev`. `togi --version` prints the build version and revision.
