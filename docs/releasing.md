# Releasing

The owner decides when to release. `version.txt` is the single source of the package version. togi uses Semantic Versioning: before 1.0, a breaking change bumps MINOR and every other release bumps PATCH. From 1.0 onward, a breaking change bumps MAJOR, otherwise entries under `### Added` bump MINOR and other releases bump PATCH. An entry beginning `- **BREAKING**` makes the release breaking.

Pending entries live in `changes/`, one file per pull request named by its number ([ADR 0033](adr/0033-changelog-fragments.md)); `changes/README.md` states the format and `just changes` checks it. The release assembles them into the new version's section of `CHANGELOG.md`: sections in the order Added, Changed, Removed, Fixed, breaking entries first in each, then by pull request number, each entry linked to its pull request and its `../` links rewritten to resolve from `CHANGELOG.md`. The release commit deletes the files it assembled.

Releasing needs permission to start workflows in the repository ([ADR 0014](adr/0014-release-from-a-workflow.md)). The workflow pushes the release commit with a deploy key that has write access: its private key is the repository secret `RELEASE_DEPLOY_KEY`, and the `main` ruleset lists deploy keys as a bypass actor, since it otherwise requires a pull request and a passing `check`.

Before releasing a change to `togi_tuner::RULESET` or `togi_journal::SCHEMA`, simulate the transition on a copy of the target machine's state directory, as [Inspecting a transition on recorded state](reviewing.md#inspecting-a-transition-on-recorded-state) describes. The simulated transition must archive the source journal unchanged and commit `session.imported` with the expected `day.imported` records ([Transitions](spec/journal.md#transitions)). The imported daily events must fold into the expected vetoes and pending questions ([Fact eligibility](spec/journal.md#fact-eligibility)). The simulated first night must complete its [CO-0 controls](spec/tuner.md#co-0-controls) without a dead end. The bench starts from fresh sessions, so it cannot show how the new rules treat the day records the next run will import.

No release is cut while work waits on the target machine ([ADR 0043](adr/0043-record-work-that-waits-on-the-target-machine.md)): an issue labeled `needs-hardware` holds a change merged before its run on the target machine, and `just board` lists such issues under "Waiting on the target machine". Run each issue's steps on the machine first; the agent there removes the label once they pass, and closes the issue when its Acceptance is met. The release workflow enforces this: when it would commit a new release, it lists the issues labeled `needs-hardware`, open or closed, and refuses while there is any, naming each by number and title and marking the closed ones. `just release-preview` reads nothing from GitHub and does not show this refusal. Publishing again a release whose commit is already on `main` is not refused.

1. Run `just release-preview` to see the version, the reason for the bump and the release notes the release would get from `origin/main`. Preview leaves the checkout's branch, HEAD, index and worktree unchanged, including when a release needs publishing again.
2. Run `just release`. It starts the `release` workflow on `main` with `gh workflow run` and follows it until it ends, so it can start right after a merge. The workflow first refuses while any issue, open or closed, is labeled `needs-hardware`, as above. It then dispatches `check.yml` on `main` and waits for the full `workflow_dispatch` run whose `head_sha` is that `main` HEAD, reusing an existing dispatch run for the same commit instead of starting another ([ADR 0074](adr/0074-pull-request-ci-gates-landing-on-main.md)). That run selects every Linux flake check, discovered from the flake rather than a list: including the four grouped VM checks (`vm-grub`, `vm-runtime`, `vm-display` and `vm-efi`), and no simulator suite ([ADR 0087](adr/0087-simulations-are-research-tools-not-checks.md)); a check already in Cachix, such as one the pull request's own CI built or the owner's gate published ([ADR 0085](adr/0085-the-gate-publishes-and-pull-request-ci-runs-every-check.md)), needs no build job and counts as passed. The release looks up the run every 30 seconds until it ends, printing state changes, and proceeds only on success. It refuses on failure or cancellation, or after an hour without success, naming the run or the commit if the run never appeared. After cancellation, rerun the named check with `gh run rerun`; after timeout, follow it with `gh run watch`, or find it with `gh run list --workflow check.yml --event workflow_dispatch --branch main`; then run `just release` again once it passes. The release computes the next version from `changes/` and commits `Release x.y.z` on top of `main`, updating `version.txt` and `CHANGELOG.md` and deleting the assembled fragments together; with no fragments and no dated section for the current version, it fails at that step. It builds `packages.x86_64-linux.default` and every `nextest-<group>` check (the package and its tests) on the release commit and pushes it to `main`; if `main` moved since the run started, the push is refused and the run fails, and running `just release` again starts over. Last, it creates the `v<version>` tag and the release on that commit, with that version's changelog section, including its pull request links, as the notes.

`just check-main` dispatches the same full check on `main` by hand, follows it until it ends and exits non-zero unless it passes. Pull request CI is the landing gate and selects every flake check too, behind the same Cachix prefilter; this exact-head dispatch remains the release gate, and pushes to `main` start no check run. The release waits on the newest dispatch run for its commit, so after a failure that a rerun can clear, run `just check-main` and then `just release` again.

If a run pushed the release commit but failed to publish, run `just release` again: with `changes/` empty, it finds the dated version and retries publishing without a new commit. Publishing checks for the GitHub Release, not just the tag: an existing tag on the release commit gets its missing Release created, and an existing Release is a no-op. A tag pointing at another commit fails with both commit IDs, rather than silently skipping publication.

Releases carry no binary artifacts. Flake users build from a tag. `togi --version` prints the build version and revision ([Commands](spec/runtime.md#commands) states the format).
