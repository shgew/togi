# Releasing

The owner decides when to release. `version.txt` is the single source of the package version. togi uses Semantic Versioning: before 1.0, a breaking change bumps MINOR and every other release bumps PATCH. From 1.0 onward, a breaking change bumps MAJOR, otherwise entries under `### Added` bump MINOR and other releases bump PATCH. An entry beginning `- **BREAKING**` makes the release breaking.

Pending entries live in `changes/`, one file per pull request named by its number ([fragment policy](../changes/README.md)); that guide states the format and `just changes` checks it. The release assembles them into the new version's section of `CHANGELOG.md`: sections in the order Added, Changed, Removed, Fixed, breaking entries first in each, then by pull request number, each entry linked to its pull request and its `../` links rewritten to resolve from `CHANGELOG.md`. The release commit deletes the files it assembled.

Releasing needs permission to start workflows in the repository ([release policy](development.md#releases-and-changelog)). The workflow pushes the release commit with a deploy key that has write access: its private key is the repository secret `RELEASE_DEPLOY_KEY`, and the `main` ruleset lists deploy keys as a bypass actor, since it otherwise requires a pull request and a passing `check`.

Before releasing a compatibility switch, simulate the transition on a copy of recorded state as [Inspecting a transition](reviewing.md#inspecting-a-transition-on-recorded-state) describes. For Ruleset 14, archive the Ruleset 13 source unchanged, verify the successor's stock baseline, original-identity daily and compatible night observations, `successor.imported` and `campaign.start {origin, history}`. Check reconstructed allowance, stops, vetoes and pending questions, including unreconstructible-history blocking and campaign preservation across reset.

The first night must run **no all-zero trial**, begin mapping at −5 and journal
the current firmware's [`stock.attested`](spec/journal.md#stock-attestation)
from the normal night confirmation. Starting without that attestation must
stop at stock before nonzero work. Fresh-session benchmarks cannot prove
imported-state behavior.

No release is cut while any issue carries `needs-hardware` ([policy and rationale](development.md#work-that-waits-on-the-target-machine)): the label holds a change merged before its run on the target machine, and `just board` lists such issues under "Waiting on the target machine". Run each labeled issue's steps on the machine first; the agent there removes the label once they pass, and closes the issue when its Acceptance is met. A run blocked by an open bugfix has already dropped the label and is listed under "Blocked" ([Issues](issues.md#work-that-waits-on-the-target-machine)), so it does not hold the release that ships its fix. The release workflow enforces this: when it would commit a new release, it lists the issues labeled `needs-hardware`, open or closed, and refuses while there is any, naming each by number and title and marking the closed ones. `just release-preview` reads nothing from GitHub and does not show this refusal. Publishing again a release whose commit is already on `main` is not refused.

1. Run `just release-preview` to see the version, the reason for the bump and the release notes the release would get from `origin/main`. Preview leaves the checkout's branch, HEAD, index and worktree unchanged, including when a release needs publishing again.
2. Run `just release`. It starts the `release` workflow on `main` with `gh workflow run` and follows it until it ends, so it can start right after a merge. The workflow first refuses while any issue, open or closed, is labeled `needs-hardware`, as above. It then dispatches `check.yml` on `main` and waits for the full `workflow_dispatch` run whose `head_sha` is that `main` HEAD, reusing an existing dispatch run for the same commit instead of starting another ([CI and release gates](development.md#ci-and-release-gates)). That run selects every Linux flake check, discovered from the flake rather than a list: including `quality`, all nextest checks and the four grouped VM checks (`vm-grub`, `vm-runtime`, `vm-display` and `vm-efi`), and no simulator suite ([research policy](development.md#simulations-and-research)); a check already in Cachix, such as one the pull request's own CI built or the owner's gate published ([cache publication](development.md#check-cache)), needs no build job and counts as passed. The release looks up the run every 30 seconds until it ends, printing state changes, and proceeds only on success. It refuses on failure or cancellation, or after an hour without success, naming the run or the commit if the run never appeared. After cancellation, rerun the named check with `gh run rerun`; after timeout, follow it with `gh run watch`, or find it with `gh run list --workflow check.yml --event workflow_dispatch --branch main`; then run `just release` again once it passes. The release computes the next version from `changes/` and commits `Release x.y.z` on top of `main`, updating `version.txt` and `CHANGELOG.md` and deleting the assembled fragments together; with no fragments and no dated section for the current version, it fails at that step. It builds `packages.x86_64-linux.default`, `quality` and every check named `nextest` or `nextest-*` on the release commit and pushes it to `main`; if `main` moved since the run started, the push is refused and the run fails, and running `just release` again starts over. Last, it creates the `v<version>` tag and the release on that commit, with that version's changelog section, including its pull request links, as the notes.

`just check-main` dispatches the same full check on `main` by hand, follows it until it ends and exits non-zero unless it passes. Pull request CI is the landing gate and selects every flake check too, behind the same Cachix prefilter; this exact-head dispatch remains the release gate, and pushes to `main` start no check run. The release waits on the newest dispatch run for its commit, so after a failure that a rerun can clear, run `just check-main` and then `just release` again.

If a run pushed the release commit but failed to publish, run `just release` again: with `changes/` empty, it finds the dated version and retries publishing without a new commit. Publishing checks for the GitHub Release, not just the tag: an existing tag on the release commit gets its missing Release created, and an existing Release is a no-op. A tag pointing at another commit fails with both commit IDs, rather than silently skipping publication.

Releases carry no binary artifacts. Flake users build from a tag. `togi --version` prints the build version and revision ([Commands](spec/runtime.md#commands) states the format).
